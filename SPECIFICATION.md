## Problem statement
Инженеры-проектировщики тратят значимое время на ручной поиск по разрозненным исходным данным (сетевые папки, PDF/сканы, Word, Excel); знание проекта не накапливается, а новые редакции заданий легко пропустить. AECPilot — desktop-приложение с агентом (ядро hermes-agent), который отвечает по источникам со ссылками, ведёт вики проекта, контролирует изменения и готовит черновики документов; система расширяется через skills и MCP.

## Goals
- G1. Ответ на вопрос по исходным данным проекта со ссылками на конкретный файл (и страницу, где применимо) — эталонный сценарий (skill `aec-qa`).
- G2. Агент строит и поддерживает вики проекта из источников (skill `aec-wiki`); вики читаема и редактируема в приложении.
- G3. Генерация черновиков документов (skill `aec-docgen`) — базовый уровень. Проверка комплектности/противоречий ИД (`aec-id-check`) выведена из MVP (решение владельца 2026-07-08 — см. N9).
- G4. Возможности Hermes доступны из GUI — ориентир: функциональный паритет с Hermes Desktop. Охват: сессии (вкл. журнал/resume/branch), стриминг, approvals и прочие интерактивные запросы агента, персона (SOUL), skills, MCP/plugins, инструменты, cron, субагенты, выбор LLM-провайдера/endpoint. Основа — инвентарь поверхности tui_gateway (PLAN §Data/API); неприменимое к продукту помечается «не переносим» и утверждается владельцем.
- G5. Управление проектом без терминала: vault, подключение read-only источников, просмотр PDF/DOCX/TXT/XLSX/CSV, .md с рендерингом и редактированием.
- G6. Изменения источников детектируются автоматически (хэши, без LLM) и предлагаются к обработке; выполняются только по команде.
- G7. Языки: UI en+ru; язык вики — настройка проекта; язык общения агента — настройка пользователя; кросс-языковой поиск.

## Non-Goals
- N1. Разбор DWG/IFC — не в MVP.
- N2. САПР/BIM-функции и автономные инженерные решения — исключены (человек в контуре всегда).
- N3. Запись агента в источники — запрещена всегда; операции записи не существуют в инструментальном слое источников.
- N4. Серверные компоненты (СУБД, отдельные сервисы) — не в MVP.
- N5. Одновременная совместная работа с одним vault — не в MVP.
- N6. Межпроектная база нормативки — не в MVP (архитектурная закладка «глобальных источников» — да).
- N7. Автономные фоновые LLM-задачи (cron-сценарии) — не в MVP.
- N8. AGPL/GPL-зависимости — исключены.
- N9. Контроль комплектности/противоречий ИД (`aec-id-check`) — не в MVP: выведен решением владельца 2026-07-08 (концепция дозревает; вероятная форма — skill). `specs/id-check.md` сохраняется замороженной базой для возврата после MVP.

## User-facing requirements
- UR1. Проекты: создать/открыть проект (vault-директория); проект можно инициализировать и в непустой папке (существующие файлы пользователя не изменяются — Obsidian-style, детали в specs/workspace-sources.md); создание вложенных папок/файлов; .md создаются и редактируются с рендерингом.
- UR2. Источники: подключить/отключить директорию (локальную/сетевую); единое дерево-проводник (vault + источники), папки источников разворачиваются на любую глубину как обычное дерево; источники помечены read-only; у любого узла дерева — «показать в системном проводнике» и «копировать путь», у файлов — «открыть во внешнем приложении».
- UR3. Вьюеры: PDF (вкл. сканы), DOCX, TXT/MD, XLSX/CSV открываются в приложении; цитата агента открывает документ на указанном месте (для PDF — страница).
- UR4. Чат с агентом: сессии, стриминг ответов и вывода инструментов, approvals, история; настройки модели/endpoint; язык агента — из профиля пользователя.
- UR5. Skills: три базовых предустановлены (`aec-qa` — эталонный, `aec-wiki`, `aec-docgen`); добавление собственных skills доступно пользователю; управление skills — из UI (UR10).
- UR6. Вики: страницы (md + wikilinks) рендерятся, навигация по ссылкам, ручное редактирование; агент обновляет вики только по команде.
- UR7. Изменения: уведомление со списком изменённых файлов источников и предлагаемыми действиями (re-ingest, обновить вики) — исполнение по подтверждению.
- UR8. Индексация: команды ingest (первичный/повторный) с прогрессом; видимый статус индекса (что проиндексировано, что устарело).
- UR9. Переключатель языка UI (en/ru); язык вики — настройка проекта (default: язык источников).
- UR10. Hub «Агент» — отдельная активность UI: персона (SOUL.md), skills (список/вкл-выкл/установка/перезагрузка), MCP-серверы и plugins, инструменты (tools/toolsets), cron-задачи и хуки (уровень «продвинутое»), полный журнал сессий (история/resume/branch/usage). Параметры приложения (LLM endpoint/ключи/модели, языки, интервал скана, embedding, тема) — в Settings.
- UR11. Режимы одобрений (approvals): пользователь выбирает режим работы агента — `manual` (человек одобряет рискованные действия; **дефолт**), `smart` (LLM авто-одобряет безопасное и авто-отклоняет опасное) или `off` (без одобрений). Текущий режим виден в UI (индикатор), переключение применяется без перезапуска агента. Режим `off` — явный осознанный выбор пользователя (ослабляет митигацию R7). Гарантия N3 (RO-источники) от режима НЕ зависит — write-операций в источники нет в инструментальном слое при любом режиме.

Детали поведения — в specs/: `specs/workspace-sources.md` (UR1–UR2, UR7–UR8), `specs/qa-over-sources.md` (G1, UR3-цитаты), `specs/wiki.md` (G2, UR6), `specs/docgen.md` (G3; `specs/id-check.md` — заморожена, N9), `specs/agent-memory.md` (память, G4).

## Constraints
- C1. Ядро — hermes-agent (MIT), **без форка**; интеграция только через публичные поверхности (tui_gateway JSON-RPC/WS; OpenAI-совместимый API-сервер при необходимости); версия пиннится.
- C2. AEC-специфика — собственные skills и MCP-серверы (переносимый слой).
- C3. Зависимости — только permissive-лицензии (MIT/Apache-2.0/BSD); AGPL/GPL исключены.
- C4. Хранилище embedded: файлы — источник истины; SQLite (+FTS5) и LanceDB — производные индексы; серверов нет.
- C5. LLM/эмбеддинги — vendor-agnostic через OpenAI-совместимые endpoint; MVP — облачные; переход в закрытый контур поддерживается архитектурно, эмбеддинг-индексы при этом пересоздаются.
- C6. Desktop: Windows — первичная платформа; macOS/Linux — поддерживаемые сборки (Electron); GUI без терминала.
- C7. Языки данных: документы первых внедрений преимущественно русские — OCR и поиск обязаны работать с русским; UI en+ru.

## Assumptions
- A1. Облачные LLM/эмбеддинг-API доступны и оплачены на период MVP.
- A2. Источники доступны как файловые пути ОС (локальные/сетевые диски/UNC); коннекторы к СЭД/облакам не требуются.
- A3. Масштаб проекта MVP: порядка сотен–2000 файлов на проект; уточняется нагрузочной проверкой (Phase 2).
- A4. tui_gateway покрывает нужную GUI функциональность (официальный десктоп Hermes работает на нём); известный риск SOUL.md-в-gateway проверяется в Phase 0.
- A5. Для эталонного эвал-набора доступен реальный завершённый/текущий проект отдела.

## Acceptance criteria
- AC1. Сквозной сценарий на чистой Windows-машине: установка → создание проекта → подключение ≥2 источников (сетевой + локальный) → ingest → вопрос → ответ со ссылкой → клик открывает PDF на нужной странице.
- AC2. Эвал `aec-qa`: набор ≥30 вопросов по эталонному проекту; доля правильных ≥ порога (порог фиксируется после baseline — см. Open questions O1); 100% содержательных ответов содержат валидные ссылки на источники; на вопросы вне источников — явное «не найдено», без выдуманных фактов и ссылок.
- AC3. Вики: по команде агент создаёт вики эталонного проекта; страницы рендерятся, wikilinks работают, ручная правка сохраняется; lint-команда выдаёт отчёт.
- AC4. `aec-docgen` проходит smoke-эвал (≥5 сценариев; критерии — в specs/docgen.md).
- AC5. Детект изменений: изменение файла источника обнаруживается в пределах настроенного интервала сканирования и показывается уведомлением; без подтверждения ничего не переиндексируется и не переписывается.
- AC6. Read-only: попытка записи агента в источник отклоняется инструментальным слоем и логируется (негативный тест).
- AC7. Полевое использование: ≥2 инженеров используют систему на реальном проекте ≥2 недель и продолжают добровольно.
- AC8. Все заявленные форматы открываются во вьюерах; повреждённый/заблокированный файл даёт понятную ошибку, а не падение приложения.

## Risks
- R1. Молодость и темп hermes-agent (churn API). Митигация: pin версии, интеграция только через gateway, контрактные smoke-тесты; фоллбэк-ядра (Goose/OpenCode) как страховка переносимого слоя skills/MCP.
- R2. Баг gateway↔SOUL.md (hermes-agent issue #26596) — затрагивает механизм языка/персоны агента. Проверка в Phase 0; workaround — identity через параметры gateway-сессии.
- R3. Масштаб file-based хранилищ LightRAG (в доках помечены «development/testing»). Нагрузочная проверка в Phase 2; fallback в рамках C4 — ограничение объёма проекта в MVP; серверные backends — только как опция больших внедрений вне MVP.
- R4. Качество OCR русских сканов. Замер на реальных сканах в Phase 2; выбор OCR-движка Docling (EasyOCR/Tesseract/RapidOCR) по результатам.
- R5. Упаковка Electron + Python-рантайм (hermes + MCP) в один инсталлятор; размер, антивирусы Windows. Референс — apps/desktop Hermes.
- R6. Токен-стоимость графовой индексации LightRAG на больших проектах. Оценка стоимости в Phase 2; инкрементальный ingest обязателен.
- R7. Промпт-инъекции из документов источников (внешний контент = данные, не инструкции). Системные правила + негативные сценарии в эвале (тип injection); одобрения рискованных действий (UR11, дефолт `manual`) — дополнительная митигация; режим `off` её снимает и выбирается пользователем осознанно.
