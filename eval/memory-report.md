Задача 5.1 (⚠️ гейт зависимостей). Замер 2026-08-26, ядро на `DONOR_SHA`, плагин

Решение владельца 2026-07-28 задало направление: память строится **двумя слоями** —
записка ядра плюс их провайдер Mem0 локально, а не собственный MCP `aec-memory`.
Здесь не решается «двумя ли слоями»; здесь замеряется **цена второго слоя** и
проверяется единственное допущение, на котором он держался: что Mem0 умеет работать
локально. Умеет — но не так, как мы предполагали.

## Как мерили

Изолированный venv в scratchpad, вне репозитория и вне рабочего venv:

```
uv venv --python 3.12 <scratch>/mem0probe/.venv     # 3.12.13, чистый: 1 МБ
uv pip install "mem0ai>=2.0.10,<3"                  # диапазон из plugin.yaml
```

В рабочий venv не ставилось ничего; влияние на него снято `uv pip install --dry-run`.
Хранилище замерено настоящим локальным qdrant, слой 1 — чтением кода ядра.

## Слой 1 — записка ядра. Уже работает, стоит ноль

`tools/memory_tool.py`: два файла в профиле, `$HERMES_HOME/memories/MEMORY.md` и
`USER.md`, один инструмент `memory` с действиями `add` / `replace` / `remove` и целью
`memory` | `user`. Правка адресуется **подстрокой**, не идентификатором. Содержимое
целиком уезжает в системный промпт каждый ход — это не извлечение, а постоянный
контекст.

| Что | Значение | Откуда |
|---|---|---|
| Пакетов доставить | 0 | входит в ядро |
| Сеть | не нужна | файлы на диске |
| Предел `MEMORY.md` | **2200 символов** | `memory_tool.py:178` |
| Предел `USER.md` | **1375 символов** | `memory_tool.py:179` |
| Цена контекста | ~3575 символов ≈ 900 токенов на ход | сумма пределов |
| Область | **профиль**, не проект | `get_hermes_home()/"memories"`, резолвится динамически |

Два факта отсюда определяют всё остальное.

**Первый: 2200 символов — это буквально записка.** Двадцать-двадцать пять коротких
фраз на весь проект. При переполнении ядро не обрезает, а возвращает агенту отказ с
требованием сначала consolidate («merge overlapping entries … then retry this add —
all in this turn»). То есть слой 1 физически не может держать накопленное знание
проекта, и никакой настройкой это не лечится — предел зашит в конструктор.

**Второй: область — профиль.** Раз каждому проекту мы и так даём свой профиль ядра
(PLAN §«Что оставляем открытым для многопользовательского сервера», пункт 1),
`MEMORY.md` оказывается проектным **сам собой, бесплатно**. Но тем же движением
`USER.md` перестаёт быть пользовательским: он тоже профильный, а значит «я веду
раздел ОВ» не переедет из проекта A в проект B. Это дыра в сценарии
«Автозапись пользовательского предпочтения», и её надо закрывать нам, а не Mem0.

## Слой 2 — Mem0. Четыре числа, которые просили

### Вес пакета

В чистый venv `mem0ai` тянет 35 пакетов и 114 МБ. Но это не наша цена: `openai`,
`numpy`, `pydantic`, `httpx` у нас уже стоят. Настоящая дельта — `uv pip install
--dry-run` против рабочего venv:

```
Resolved 35 packages ... Would uninstall 1 package, would install 12 packages
```

| Пакет | МБ |
|---|---|
| grpcio 1.83.0 | 11.9 |
| sqlalchemy 2.0.52 | 8.5 |
| qdrant-client 1.19.0 | 2.5 |
| posthog 7.44.1 | 2.5 |
| mem0ai 2.0.19 | 1.2 |
| greenlet, h2, hpack, portalocker, backoff, hyperframe | 1.3 суммарно |
| **итого** | **27.9 МБ, 11 новых пакетов** |

Плюс **обмен**: `protobuf` **7.35.1 → 6.33.6**, потому что `mem0ai` требует
`protobuf<7.0.0,>=5.29.6`. Это не поломка — в нашем дереве protobuf просят
`google-api-core`, `googleapis-common-protos`, `proto-plus` (все `<8.0.0,>=6.33.5`) и
`onnxruntime` (без ограничений), и 6.33.6 удовлетворяет всех. Но следствие
записать надо: **весь venv остаётся на ветке protobuf 6 до тех пор, пока стоит
Mem0**, и это ограничение унаследует OCR-конвейер, который к памяти отношения не имеет.

### Вес хранилища

Настоящий локальный qdrant, 1000 фактов, 1536 измерений (умолчание Mem0 —
`text-embedding-3-small`):

```
store bytes=16491047  MB=15.7
per fact bytes=16491
```

**16,5 КБ на факт; 15,7 МБ на тысячу.** Для сравнения: то же знание в записке ядра
весит около сотни байт на факт и не имеет векторов вовсе. Разница в двести раз —
это плата за поиск по смыслу.

### Стоимость извлечения

`plugins/memory/mem0/__init__.py`, на каждый ход диалога:

- `prefetch(query)` → семантический поиск, то есть **вызов эмбеддера** на текст
  вопроса, с горячим ожиданием `_PREFETCH_WAIT_SECS` и молчаливым пропуском
  инъекции, если бэкенд не успел;
- `sync_turn(user, assistant)` → `backend.add(messages, …, **`infer=True`**)`, то есть
  **вызов LLM для извлечения фактов** плюс ещё один вызов эмбеддера на запись.

Итого до трёх сетевых обращений на ход, из них одно — к языковой модели. Ядро
экономит на тривиальных ходах (`is_trivial_prompt`: «ок», «спасибо», слэш-команды
recall не вызывают), но на содержательных платится всегда.

### Работа без сети

Здесь предположение не подтвердилось. OSS-режим Mem0 знает ровно двух поставщиков
LLM и эмбеддера — `openai` и `ollama` (`_oss_providers.py`), и в умолчательной
конфигурации **не поднимается вовсе**:

```
init FAILED: OpenAIError Missing credentials. Please pass an `api_key` ...
```

Это падение на `Memory.from_config`, до первого факта — не деградация под нагрузкой,
а отказ конструктора. Значит «локально» у Mem0 означает одно из двух:

1. **openai** — ключ и сеть.
2. **ollama** — отдельный локальный сервер на `:11434`, который пользователь ставит
   и держит запущенным сам. Это прямо против C4 («серверов нет») и означает, что
   инженер-проектировщик перед первым использованием памяти ставит себе Ollama и
   выкачивает модель.

Третьего варианта нет: хранилище (`qdrant` локально) действительно встраиваемое, а
вот мозги — нет.

**Важная поправка к пункту 1, и она меняет вес всего вывода.** Первым заходом это
читалось как «Mem0 приносит второго адресата, которому уезжает текст». Проверка
показала, что это неверно с двух сторон.

Со стороны Mem0: `mem0/llms/openai.py:51` и `mem0/embeddings/openai.py:23` читают
`openai_base_url`, и `_oss_providers.py` этот ключ объявляет. То есть Mem0 можно
направить **на тот же endpoint и тот же ключ**, которые уже настроены у ядра
(`config.yaml`: `provider: openai-api`, `model: gpt-5-mini`; для своего сервера —
`base_url` + `key_env`, строка 121). Нового вендора не появляется.

Со стороны продукта: мы **уже не работаем без сети**. `rag_index.py:32` —
эмбеддер по умолчанию `text-embedding-3-large`, то есть содержимое всех
проиндексированных документов уже уходит на endpoint эмбеддингов. Это ровно та
граница, которую владелец разобрал и принял в находке D-52.

И сама спека это предусмотрела: сценарий «Локальность» говорит «не покидает машину,
**кроме штатных вызовов настроенного LLM-endpoint**». Оговорка уже стоит.

Значит вариант с openai **не требует переписывать локальность** — при условии, что
Mem0 направлен на настроенный endpoint. Что он приносит на самом деле: умолчание
`https://api.openai.com/v1`, которое сработает молча, если `openai_base_url` не
задать (вот это — настоящий подводный камень), и вторую копию настроек модели,
которая может разъехаться с первой.

## Чего в плане не было

Три вещи всплыли при замере, и ни одна не следует из документации плагина.

**Телеметрия включена по умолчанию, и донор её не выключает.**
`mem0/memory/telemetry.py`: `MEM0_TELEMETRY` по умолчанию `"True"`, адрес
`https://us.i.posthog.com`, ключ проекта зашит в код. Событие `mem0.init` —
жизненного цикла, то есть **обходит выборку и уходит всегда**, вместе с версией ОС,
её сборкой, процессором, архитектурой, версией Python и устойчивым анонимным
идентификатором. Поиск по всему дереву донора (`plugins/memory/`, `memory_manager.py`)
не нашёл ни одного места, где `MEM0_TELEMETRY` ставится — **выключать это придётся
нам**, одной переменной окружения, и это должно быть в коде, а не в инструкции.

Само содержимое памяти в свойствах событий по умолчанию не передаётся, но сценарий
«Локальность» из `specs/agent-memory.md` обещает, что содержимое **не покидает
машину**, — а факт установки, машина и её отпечаток покидают её с первого запуска.

**Второе векторное хранилище.** У нас уже есть NanoVectorDB внутри LightRAG (решение
владельца 2026-08-15). Mem0 приносит qdrant. Два разных векторных движка в одной
поставке — это две модели данных, два формата на диске, две вещи в резервной копии и
два кандидата при разборе «почему поиск не нашёл».

**Второй конфиг модели.** Ядро уже знает, к какой модели ходить. Mem0 не спрашивает
ядро — у него свой блок `llm` и свой `embedder` в `$HERMES_HOME/mem0.json`. Указать
там наш endpoint можно (см. поправку выше), но это будет **вторая копия** тех же
настроек, и разъедется она молча: несовпадение заметно не по ошибке, а по тому, что
факты вдруг перестали извлекаться.

## Что это складывается

Слой 1 бесплатен, работает уже сейчас, проектную область даёт даром — и вмещает
двадцать фраз. Как единственный слой он не годится: 2200 символов не переживут
и одного месяца работы над разделом.

Слой 2 даёт поиск по смыслу, автоизвлечение и консолидацию противоречий. Стоит:
27,9 МБ и одиннадцать пакетов, пин protobuf на ветку 6 для всего venv, второй
векторный движок рядом с NanoVectorDB, вторая копия настроек модели, выключение
чужой телеметрии нашими руками — и до трёх обращений к endpoint на каждый
содержательный ход, из них одно к языковой модели.

Чего он **не** стоит, вопреки первому впечатлению: нарушения локальности. Оговорка
про штатный endpoint в спеке уже есть, а документы туда уже уходят.

## Что решать владельцу

Замер не выбирает; выбор из трёх, и он ваш.

**A. Берём Mem0, направив его на наш настроенный endpoint.** Получаем всё
обещанное, спеку править не нужно. Платим 27,9 МБ, вторым векторным движком, пином
protobuf, LLM-вызовом на ход и обязанностью не забыть две вещи, каждая из которых
молча ломает обещание: `MEM0_TELEMETRY=false` и `openai_base_url`. Обе должны
стоять в коде регистрации провайдера, а не в инструкции для пользователя.

**B. Берём Mem0 на ollama.** Сеть не нужна вообще, ни для памяти, ни для
эмбеддинга фактов. Платим тем, что пользователь ставит и держит отдельный сервер, —
C4 надо переписывать, установку усложнять. Выигрыш по сравнению с A невелик:
документы всё равно уходят на endpoint эмбеддингов, так что офлайн получается только
у памяти, а не у продукта.

**C. Не берём Mem0; слой 2 делаем на том, что уже стоит.** У нас есть LightRAG,
NanoVectorDB, эмбеддер, SQLite и весь конвейер индексации — то есть все части, из
которых Mem0 собран, кроме LLM-извлечения фактов, а модель для извлечения у ядра уже
настроена. Плата: пишем сами автоизвлечение, консолидацию противоречий и
дедупликацию — то, что у Mem0 отлажено. Выигрыш: ноль новых пакетов, ноль новых
хранилищ, ноль чужой телеметрии, один конфиг модели вместо двух.

**Рекомендую A.** Порог, который я сначала считал решающим — локальность, — при
проверке оказался не порогом: он уже пройден индексацией и уже оговорён в спеке.
Оставшаяся разница между A и C — это «27,9 МБ и два конфига» против «сами пишем
консолидацию противоречий», и второе дороже. B стоит брать, только если появится
требование работать без сети целиком, — но тогда его надо ставить и RAG-конвейеру,
а это отдельный и гораздо больший разговор.

Отдельно и вне зависимости от выбора: дыру `USER.md` (пользовательские факты не
переживают смену проекта, потому что записка привязана к профилю) закрывать нам в
любом из трёх вариантов.
