# Мини-проект для эвала вики (задача 4.14)

Шесть документов, придуманных целиком. Настоящий эталонный проект для этого
эвала не годится по двум причинам, и обе выяснились измерением:

1. **Материал слишком велик.** Десять фрагментов настоящего проекта — это
   297 тысяч знаков; судья, которому дают такой объём, судит по тому куску,
   что поместился, и объявляет выдумкой всё остальное. На мини-проекте
   материал целиком помещается и в модель, и в судью.
2. **Противоречия там может не быть.** Сценарий «две редакции с разными
   числами» нельзя проверять надеждой, что такая пара найдётся: здесь она
   заведена нарочно — 250 кВт в первой редакции против 320 кВт во второй.

Факты придуманы, но правдоподобны. Ни один документ не списан с настоящего.

## Как это собирается

В git лежат только `src/*.md` — их читает и правит человек. Индексатор берёт
`.pdf/.docx/.xlsx/.csv`, поэтому `.docx` собираются из исходников скриптом
`build_docs.py`; `eval/ingest_wiki_fixture.py` вызывает его сам. Сами `.docx` не
отслеживаются: они пересобираются побайтово другими при каждом запуске, и их
версии — чистый шум в истории.

## Что на этой фикстуре нашлось

**Сквозной прогон (`eval/wiki_e2e.py`) поймал то, чего не видел эвал по тексту.**
При обновлении агент читал снимок из `wiki/raw/` и переписывал страницу тем же,
что в ней уже было, отчитываясь «обновлено 5 страниц». Снимок — это старый текст
по определению, он для сравнения по `sha256`. Правило порядка («сначала обновить
снимок, потом взять новый текст через `rag_query`») дописано в скилл, после чего
переизданное значение доехало до страницы.
