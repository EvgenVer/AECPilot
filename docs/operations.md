# Эксплуатация

Как запустить, настроить, проверить и собрать AECPilot, где журналы и что делать, когда
что-то не работает. Точные команды для агентов — `AGENTS.md` §Project commands; здесь —
то же с пояснениями. Пользовательская инструкция установленной программы —
[быстрый старт](quickstart.ru.md).

## Что нужно для разработки

- Windows 10/11 x64 (единственная платформа поставки).
- Node.js с corepack: pnpm 11 вызывается только как `corepack pnpm`, глобального pnpm нет.
- `uv` 0.11 и `git` на PATH: ядро ставится из git, Python — через uv.
- Git Bash: набор тестов запускается из него (см. «Ловушки окружения»).

## Установка рабочей копии

```bash
corepack pnpm install
```

```bash
uv sync
```

```bash
node runtime/setup.mjs
```

`uv sync` ставит корневой `.venv` (Python 3.12) с нашими MCP-серверами и инструментами
разработки. `setup.mjs` ставит ядро на пине в `runtime/.hermes-venv`, готовит профиль
`runtime/dev-profile` и собирает оба payload поставки (`runtime/core`, `runtime/mcp`) —
это минуты; `--no-payload` пропускает сборку payload. Повторный запуск безопасен.
Подробно — [ядро и его запуск](components/core-runtime.md).

## Запуск

| Команда | Что делает |
|---|---|
| `corepack pnpm dev` | приложение в режиме разработки с горячей перезагрузкой окна; профиль `runtime/dev-profile` |
| `corepack pnpm build`, затем `corepack pnpm app` | сборка и запуск собранного приложения из рабочей копии — так владелец проводит ручную приёмку |
| `AECPilot.exe` | установленная программа (режимы «всё» и «только приложение») |
| `AECPilot.exe --server` | серверная установка: ядро без окна, значок в трее; обычно запускается задачей Windows при входе |

После каждого запуска Electron или Playwright не должно оставаться процессов
`electron.exe` и `gateway run` ядра (правило «No orphans» в `AGENTS.md`).

## Настройка

Провайдер модели, ключи, провайдеры индекса и памяти, веб-поиск, подключение к серверу
настраиваются в окне приложения: ключи уходят в safeStorage, а не в файлы
([данные](data.md)). Переменные окружения нужны только разработке и автотестам:

| Переменная | Что делает |
|---|---|
| `AEC_HERMES_HOME` | другой профиль ядра для всего стека; автотесты и зонды — на временной копии `runtime/e2e-profile` |
| `AEC_SERVE_PORT` | порт `hermes serve` вместо 18789 (второе приложение рядом на приёмочном стенде) |
| `AEC_GATEWAY_URL` | подключиться к готовому шлюзу (mock-шлюз e2e) и не запускать ядро |
| `AEC_SMOKE=1` | быстрый smoke окна без ядра |
| `AEC_SKILLS_DIR` | копия `skills/` для живых автотестов, где агент может править навыки |

Адрес файла последней версии для уведомления об обновлении — `aecpilot.updateFeedUrl` в
`apps/desktop/package.json` (файл `latest.json` последнего релиза на GitHub); пустой адрес
выключает проверку.

## Проверки

| Команда | Что проверяет | Стоимость |
|---|---|---|
| `corepack pnpm test` | модульные тесты: Vitest (`apps/desktop`, `runtime/*.test.mjs`) и pytest (MCP-серверы, плагин) | бесплатно; ~10 минут, запускать из Git Bash |
| `corepack pnpm lint` | eslint, типы TypeScript, prettier, ruff (проверка и формат), `pnpm audit --prod` | бесплатно |
| `corepack pnpm e2e` | сборка и Playwright по живому окну: smoke и приёмка на mock-шлюзе | бесплатно, без модели |
| `corepack pnpm e2e:acceptance` | приёмка с живым ядром и моделью плюс настоящие окна ОС; затем `corepack pnpm -C apps/desktop e2e:acceptance:report` пишет отчёт в `docs/acceptance/<дата>/` | **платно** — только с согласия владельца и бюджетом |
| эвалы `eval/` | качество ответов `aec-qa`, вики, память на живой модели (AC2) | **платно** — только с согласия владельца |

Состояние на 2026-10-26: полный `corepack pnpm test` зелёный; под нагрузкой машины
возможны тайм-ауты отдельных тестов окна — их перезапускают по одному. `corepack pnpm
parity` проходит (расхождений 0). `corepack pnpm lint` пока не проходит из-за
неотформатированных файлов и новой уязвимости zod — долг в [TASKS](TASKS.md).

Разбор красного e2e: Playwright перезапускает рабочий процесс после **каждого** падения,
и тесты после первого падения идут в заведомо пустом приложении — разбирать надо только
первое. Для явлений, зависящих от времени, меньше трёх прогонов на одной сборке вывода не
дают; мелкую правку проверяют одним целевым прогоном.

## Сборка установщика

```bash
corepack pnpm -C apps/desktop run dist:win
```

Собирает интерфейс и складывает установщик NSIS и zip в `apps/desktop/release` — 30–60
минут. Перед этим нужны свежие payload (`node runtime/setup.mjs`). Проверка «чистой
машины» — только под `D:\AECPilot-cleantest` (проект `clean-machine` Playwright).
Подробно — [установка и поставка](components/packaging.md).

## Выпуск версии

Установщики выкладываются в GitHub Releases публичного репозитория
`github.com/EvgenVer/AECPilot`; лицензия остаётся закрытой, подписи нет (PRODUCT A7, A8).
Выпуск — публикация от аккаунта владельца, поэтому каждый делается с его согласия.

1. Поднять `version` в `apps/desktop/package.json`, собрать установщик (выше) и проверить
   его на чистой машине.
2. Создать релиз с тегом `v<версия>` и приложить к нему два файла: установщик
   `AECPilot-<версия>-win-x64.exe` и `latest.json`:

    ```json
    {
      "version": "<версия>",
      "url": "https://github.com/EvgenVer/AECPilot/releases/download/v<версия>/AECPilot-<версия>-win-x64.exe"
    }
    ```

3. Проверить: адрес из `aecpilot.updateFeedUrl` открывается и отдаёт этот `latest.json`.
   Приложение предыдущей версии при запуске показывает уведомление о новой.

GitHub принимает в релиз файлы до 2 ГБ; установщик 0.1.0 весит 840 МБ.

## Журналы

| Что | Где |
|---|---|
| Журнал приложения (главный процесс) | `<userData>/logs/desktop.log`: в разработке `%APPDATA%\@aecpilot\desktop\logs`, в установке `<root>\data\userData\logs` |
| Вывод `hermes serve` | `<профиль>/serve.log` |
| Журналы ядра (агент, ошибки, шлюз) | `<профиль>/logs/` |
| Отклонённые попытки к источникам | `<проект>/.aecpilot/logs/sources-rejected.jsonl` |
| Состояние сервера для клиента | `<проект>/.aecpilot/server-state.json` |

Токен шлюза в журналы не пишется: адрес WebSocket с токеном остаётся в памяти главного
процесса.

## Когда что-то не работает

| Признак | Причина и что делать |
|---|---|
| Белый экран при запуске | почти всегда осиротевшие окна `electron.exe` от фоновых dev- или Playwright-прогонов, а не дефект кода: завершить их |
| `port 18789 … already in use` | на порту живёт осиротевший `hermes serve` или `gateway run`: завершить процесс; ядро на занятом порту не стартует |
| «Ядро не поднялось» после смены модели | холодный старт ядра — до 30 с, первый запуск после установки дольше; ожидание — 2 и 4 минуты |
| Агент не видит источники нового проекта | ядро держит MCP-сервер до `reload.mcp`; главный процесс отправляет его при открытии проекта, а если ядро ещё не было готово — сразу после подключения |
| `pytest`: 100+ ошибок `PermissionError` на setup | папка `%LOCALAPPDATA%\Temp\pytest-of-<пользователь>` без прав; запустить с `--basetemp` во временную папку |
| `cron-prompt.test.ts` красный только из PowerShell | в PowerShell нет `sh` на PATH; тесты запускать из Git Bash |
| Сервер не отвечает клиенту | значок в трее сервера, поднят ли SSH-туннель, свежий ли токен |

## Ловушки окружения

Проверенные факты о машине разработки и инструментах (перенесены 2026-10-26 из прежнего
`MEMORY.md`).

- pnpm 11 блокирует postinstall: сборка разрешена только `electron` и `esbuild`
  (`onlyBuiltDependencies` в `pnpm-workspace.yaml`). Свежеопубликованный пакет pnpm
  молча дописывает в `minimumReleaseAgeExclude` того же файла — смотреть этот список в
  диффе.
- После смены версии Electron `corepack pnpm install` (и `pnpm rebuild electron`) может
  оставить пакет без бинарника: в его папке нет `dist/`, приложение не запускается
  (замер 2026-10-26, 43.7.11 → 43.8.3). Чинится запуском его установщика напрямую:
  `node install.js` в `node_modules/.pnpm/electron@<версия>/node_modules/electron`;
  проверка — файл `dist/version` с нужной версией.
- Поиск по каталогу (ripgrep) не видит gitignored-папки вроде `runtime/.hermes-venv` —
  искать по прямому пути к файлу.
- Компонентные тесты: в `apps/desktop/vitest.config.ts` два проекта, среда выбирается
  расширением (`*.test.tsx` → jsdom, `*.test.ts` → node). Автоочистка Testing Library не
  работает (`globals: false`) — `afterEach(cleanup)` пишется явно. Проекту `dom` заданы
  `maxWorkers: 4` и `testTimeout: 15000`, у проектов разный `sequence.groupOrder` — без
  этого компонентная часть нестабильна под нагрузкой.
- Корневой `pytest -q` падает на **сборе**, если в двух пакетах `mcp/*/tests/` есть
  файлы с одинаковым именем (каталоги без `__init__.py`); отдельный файл при этом
  проходит. Имя нового теста сверять с соседями. `--import-mode=importlib` не подходит —
  ломает импорты `mcp_harness` и фикстур.
- `hermes tools` интерактивна и на EOF переписывает `config.yaml` профиля. Проверять
  MCP-сервер — `hermes mcp test`.
- LightRAG по умолчанию велит модели называть сущности по-английски
  (`DEFAULT_SUMMARY_LANGUAGE = "English"`): на русских документах одна сущность
  появлялась дважды — переводом и транслитерацией. Язык задан явно и записан в отпечаток
  индекса; граф на другом языке — только полной переиндексацией.
- `opencv-python` (тянет `rapidocr`) и `opencv-python-headless` (тянет `easyocr`) владеют
  одним модулем `cv2`. Удаление одного уносит файлы другого, а uv считает его
  установленным — импорт молча ломается («RapidOCR is not installed»). Лечится
  `uv sync --reinstall-package opencv-python`.
- `awk '/\r$/'` в Git Bash не видит CR. Концы строк проверять `git ls-files --eol <файл>`
  или подсчётом байтов 13 и 10 в Python. Признак беды в диффе — сотня удалений в
  `git diff --stat` при одних вставках в `git diff -w --stat`.
- Вес зависимости меряется двумя командами: `uv pip install <пакет>` в одноразовый venv
  даёт полный вес с цепочкой, `uv pip install --dry-run <пакет>` против рабочего venv —
  настоящую дельту (у `mem0ai` 114 МБ против 27,9). Решению обычно нужна вторая.
- Корневой `pyproject.toml` исключает часть зависимостей из окружения
  (`[tool.uv] exclude-dependencies`, T43.1), и `uv pip install` в `.venv` это соблюдает:
  инструменты с такими зависимостями (сайт документации — `jinja2`) ставятся отдельно,
  через `uvx`.
- `validateProjectConfig` пересобирает `settings` из известных ему полей, и незнакомое
  поле теряется при записи — новое поле настроек сначала добавлять в проверку (долг в
  [TASKS](TASKS.md)).
- `getByLabelText`: `<label>`, обнимающий и подпись, и подсказку, склеивает их в одно
  доступное имя — разводить `<label htmlFor>` и поле, подсказку выносить соседом.
- Правило eslint `react-hooks/set-state-in-effect`: не засевать состояние ответом запроса
  через эффект, а показывать `state ?? loaded`, где `undefined` значит «человек поле не
  трогал».
- Обычная установка Hermes на той же машине допустима: её `install.ps1` пишет
  `HERMES_HOME=%LOCALAPPDATA%\hermes` в переменные пользователя, добавляет `hermes` в PATH
  и ставит свой Node первым, только если системный ниже порога. Нас это не задевает —
  все запуски ядра передают `HERMES_HOME` явно. Два правила: после чужой установки
  `node -v` должен остаться того же мажора; любой новый скрипт, запускающий Python ядра,
  передаёт `HERMES_HOME` и `memoryEnv(home)` из `runtime/memory-config.mjs`, иначе ядро
  заведёт профиль в `%LOCALAPPDATA%\hermes`, а Mem0 — журнал в `~/.mem0`.
- Буфер обмена Windows недоступен процессам, запущенным агентом; словарь орфографии
  общий с ОС — слово, добавленное тестом, убирать до и после.

## Подъём пина ядра

Ядро выходит раз в 1–2 месяца; пин ставится только на последний стабильный тег `vX.Y.Z`
и записывается коммитом ([решение 0012](decisions/0012-core-0-22-2.md)).

1. Снять поверхность новой версии (`node runtime/contract-snapshot.mjs`) и сравнить с
   прежней (`runtime/contract-diff.mjs`); посчитать, какие файлы донора изменились
   (`node runtime/donor-report.mjs <старый SHA> <новый SHA>`). Разбор записать в
   `runtime/contracts/reading-<версия>.md` и `donor-move-<версия>.md`; точка входа
   следующего подъёма — разборы 0.22.2.
2. Сменить пин в `runtime/hermes-env.mjs`; при смене версии Python — отложить старый
   `.hermes-venv` как `.hermes-venv-<версия>` (это и есть откат). Запустить
   `node runtime/setup.mjs`.
3. Перенести файлы донора заново с нового `DONOR_SHA` и повторить правки по их
   заголовкам — не патчить старые файлы к новой версии.
4. Проверить машиной всё заново: `corepack pnpm e2e` трижды и `corepack pnpm
   e2e:acceptance` (платно — с согласия). Руками — только задетый остаток `[человек]`
   чек-листа, а задетое считать по отчёту `donor-report.mjs`, а не по памяти.
5. Найти в e2e ожидаемо красные тесты (`test.fail`, `test.fixme` с пометкой «снять после
   подъёма»): `test.fail` молча зеленеет, пока дефект жив, и так же молча прячет
   исправление апстрима.

## Ручная приёмка

- Чек-лист — [manual-checklist.md](manual-checklist.md); машинная часть проходится
  автоприёмкой, человеку остаётся раздел `[человек]` отчёта ([отчёты](acceptance/README.md)).
- Запуск для владельца: `corepack pnpm build` и `corepack pnpm app` на профиле
  `runtime/dev-profile` (его и `%APPDATA%\@aecpilot\desktop` автоматические прогоны не
  трогают).
- Проверку владельцу выдают одной пошаговой инструкцией на один прогон: «что сделать →
  что увидеть (✓)».
- Владелец сообщает только замечания: молчание по блоку чек-листа означает «прошло».
- Журналы прогона владелец не присылает — их читает агент сам.

## Сайт документации

```bash
uvx --with-requirements requirements-docs.txt zensical serve -a localhost:8137
```

```bash
uvx --with-requirements requirements-docs.txt zensical build --strict
```

`serve` открывает сайт на `http://localhost:8137` (порт 8000 по умолчанию на машине
разработки занят другой программой); `build --strict` должен проходить без
замечаний — битая ссылка или фрагмент кода, указывающий на несуществующий файл или
область, его роняют. Zensical ставится в отдельное окружение `uvx`, а не в `.venv`: ему
нужен `jinja2`, который корневой `pyproject.toml` исключает.
