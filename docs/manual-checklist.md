# Ручная приёмка

Один прогон на всё. Формат: **что сделать → что увидеть (✓)**.
Докладывайте **только замечания**: молчание по блоку = «прошло».

Что именно проверяется: интерфейс целиком заменён на код Hermes Desktop, а наши
собственные поверхности (проект, проводник, источники, откат, специалисты)
написаны заново на их стеке. Поэтому чек-лист не про «работает ли кнопка» — он
про то, **не потерялось ли поведение**, которое у нас было измерено, и **не
приехало ли лишнее** из их продукта.

## С чего начать

### Шаг 0. Что должно быть на машине

Один раз, если этого ещё не делали:

```bash
corepack pnpm install
```

```bash
node runtime/setup.mjs
```

✓ Обе команды заканчиваются без ошибок.
✓ Вторая ставит ядро hermes-agent по закреплённому коммиту в
  `runtime/.hermes-venv` и заводит изолированный профиль `runtime/dev-profile`.
  Ваш личный `~/.hermes`, если он есть, **не трогается** — это разные папки.

Ключ провайдера заранее заводить не нужно: его спросит мастер первого запуска
(блок 14). Без ключа проходятся все блоки, **кроме** тех, где отвечает модель:
6, 15, 22, 37.4, 38, 39.

### Шаг 1. Закрыть прошлые окна

Осиротевшие процессы Electron дают «белый экран», и это **не баг кода** — окно
от прошлого запуска держит порт. Перед началом проверьте, что их нет:

```bash
powershell -Command "Get-Process electron -ErrorAction SilentlyContinue | Select-Object Id,StartTime"
```

✓ Пусто. Если что-то нашлось — закройте окна или снимите процессы, иначе первый
  же запуск покажет белый экран, и вы потратите час не туда.

### Шаг 2. Машинный прогон

С 2026-09-17 (SPEC AC15) позиции `[e2e]` и `[live]` проходит машина — руками их
повторять не нужно. Гейт на подменённом шлюзе, три раза зелёный — это норма:

```bash
corepack pnpm e2e
```

Приёмка целиком — одним вызовом: `[e2e]`, `[live]` на настоящем ядре (с ходами модели,
это стоит денег) и протокол рабочего стола. Один вызов, потому что Playwright стирает
свидетельства прошлого прогона при каждом запуске:

```bash
corepack pnpm e2e:acceptance
```

✓ Прогон дошёл до конца. Он открывает на экране настоящие окна (проводник, диалог
  сохранения, плавающую ленту) — **экран не запирайте**: на запертом позиции рабочего
  стола пропускаются с причиной, и отчёт покажет их жёлтыми.

### Шаг 3. Отчёт

```bash
corepack pnpm e2e:acceptance:report
```

✓ В `docs/acceptance/<дата>/report.md` таблица «позиция → вердикт → снимок →
  стенограмма», итоги по меткам и расход модели. Как её читать — `docs/acceptance/README.md`.
✓ Красных строк нет — или у каждой есть задача в `TASKS.md` с номером позиции, или
  запись «недетерминизм модели, стенограмма приложена».
✓ Строки «к владельцу» (🟡) прочитаны: это позиции качества — вердикт машины только
  предложение, решение ваше.

### Шаг 4. Остаток `[человек]`

Только то, чего машина проверить не может; список с текстом шагов стоит в конце
отчёта. Запуск приложения — как обычно:

```bash
corepack pnpm dev
```

| Очередь | Что | Нужен |
|---|---|---|
| 1 | 7.1 — ввод ключа провайдера (мастер, блок 14) | ваш ключ |
| 2 | 11 — голос | микрофон и колонки |
| 3 | 34 — слово-активатор | микрофон |
| 4 | 52 — Graph с живым входом (по желанию) | учётная запись Microsoft |
| 5 | 39 — сквозной прогон AC3 на **настоящем** проекте (задача 4.15) | ключ и ваш проект |

Первый запуск после установки ядра **долгий** — холодный старт шлюза замерен в 29,6
секунды. Окно пустое дольше двух минут — это замечание; вывод ядра лежит в
`runtime/dev-profile/serve.log`, приложите последние строки.

### Шаг 6. Когда закончили или если сломалось

```bash
powershell -Command "Get-Process electron -ErrorAction SilentlyContinue | Measure-Object | Select-Object Count"
```

✓ `Count : 0` после закрытия приложения. Оставленный процесс сломает следующий
  запуск, и это будет выглядеть как новый баг.

Не начинайте заново с первого блока — почти всегда чинится на месте.

1. **Окно побелело или не отвечает.** Закройте приложение, проверьте процессы
   (шаг 1) и запустите снова. Блок, на котором это случилось, пройдите повторно.
2. **Шлюз отвалился** (полоса состояния говорит об отказе). Его вывод лежит в
   `runtime/dev-profile/serve.log` — последние строки приложите к замечанию.
3. **Приложение само жалуется на ошибку.** Журнал приложения открывается из
   интерфейса (блок 28); путь к файлу показан там же.
4. **Состояние профиля испортилось** (пропали сессии, настройки ведут себя
   странно). Профиль — это папка `runtime/dev-profile`, и она ваша: можно закрыть
   приложение, переименовать её и начать с чистого листа. Ваш личный `~/.hermes`
   при этом не затрагивается. После такого сброса заново пройдите блок 14 — ключ
   спросят снова.
5. **Машинный прогон красный там, где вчера был зелёным.** Разбирается только
   **первое** падение: после каждого падения Playwright перезапускает рабочий процесс,
   и следующие тесты идут в заведомо пустом приложении. Вывод по одному прогону не
   делается — нужно три на одной сборке.

## Метки и нумерация позиций

С 2026-09-17 (решение владельца, SPEC AC15) чек-лист проходит **машина**, а
человеку остаётся то, чего машина проверить не может. Поэтому каждая позиция «✓»
несёт метку — кто её проверяет:

| Метка | Кто проверяет | Где смотреть результат |
|---|---|---|
| `[e2e]` | Playwright по живому окну приложения на подменённом шлюзе; **входит в гейт** (`pnpm e2e`) | прогон падает — значит позиция не прошла |
| `[live]` | Playwright по живому окну с **настоящим ядром** во временном профиле; часть позиций — с ходами модели | отчёт прогона: `docs/acceptance/<дата>/report.md` |
| `[человек]` | **вы** — микрофон и голос (11, 34), настоящий ключ провайдера (7.1), вход в учётную запись Microsoft (52), настоящий проект (39) | ваши замечания |
| `[фаза 6]` | отложено: вторая машина, задача `6.17` | — |
| `[дефект ядра]` | не проходится, пока не починен дефект подписи A2A (задача `3.11`) | — |

Счёт на 2026-09-25: **173 `[e2e]`, 220 `[live]`, 39 `[человек]`**, плюс 19
отложенных в фазу 6 и 3 упирающихся в дефект ядра. Итого 454.

**Нумерация позиций** — `<блок>.<шаг>.<порядковый ✓ внутри шага>`: например
`3.5.2` — блок 3, шаг 5, вторая галка. Номер не пишется в тексте: он считается
по файлу и служит для связи с тестами. Имя теста начинается с этого номера
(`38.10.1 ответили минимум двое`), поэтому отчёт прогона и этот файл сходятся
строка в строку. Сверяет связь `node runtime/checklist-coverage.mjs`: он падает
на позиции без метки, на метке `[e2e]`/`[live]` без теста и на тесте, которому
не соответствует ни одна позиция.

**Если вы правите чек-лист** — добавили, убрали или переставили позицию:
поставьте метку новой позиции и прогоните счётчик. Вставка галки в середину шага
сдвигает номера следующих в этом шаге, и счётчик назовёт тесты, которые теперь
указывают в пустоту.

## Что перепроходить после подъёма пина донора

Подъёмы периодические, раз в 1–2 месяца. После каждого машина проходит **всё заново**:
`pnpm e2e` ×3 и `pnpm e2e:acceptance` на новой сборке. Стоит это часы и расход модели, а не
ваш день, поэтому разностный выбор блоков больше не нужен. Отчёт сравнивается с
прошлым: позиция, которая была зелёной и стала красной, — находка подъёма, а не «так
было всегда». Руками после подъёма перепроходится только тот остаток `[человек]`, чей
код задет. Задетое считается по списку изменившихся файлов `node runtime/donor-report.mjs
<старый SHA> <новый SHA>`, а не по памяти: голос и слово-активатор (11, 34) — если
изменились `app/chat/composer/**` или наш главный процесс; Graph (52) — если изменились
`app/messaging/**`; сквозной прогон (39) — если изменилось ядро, то есть почти всегда.
