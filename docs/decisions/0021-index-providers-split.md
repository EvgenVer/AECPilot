# 0021 — Эмбеддинги и модель разбора от разных провайдеров, локально и по подписке

- Date: 2026-11-17 (интервью владельца по итогам эксплуатации 0.1.0)
- Status: accepted
- Approved by: owner
- Changes: UR53 и уточнение C5 в [PRODUCT](../PRODUCT.md); задачи T80–T83

## Context

Пример: агент работает по подписке ChatGPT. Индексу нужны две модели — эмбеддинги (числовые
«отпечатки» фрагментов для поиска) и модель разбора (выделяет сущности и связи для графа).
Сейчас настройка «Индекс и память» (D-172) даёт одного провайдера на обе модели: «как у агента»
или Gemini / OpenAI / свой адрес по ключу (`apps/desktop/src/main/provider-presets-pure.ts`).
Отсюда три ограничения, которые владелец встретил на 0.1.0:

- подписка не даёт ни адреса с ключом, ни эмбеддингов — с агентом по подписке индекс строить
  нечем, пока не заведён второй провайдер целиком;
- «свой адрес» требует переменную с ключом, а у локального сервера (Ollama, LM Studio) ключа
  нет — локальный сервер отклоняется;
- локальные модели ядра (UR39: загрузка с Hugging Face, сборка llama.cpp) запускаются только как
  чат-модели, режима эмбеддингов у рантайма ядра нет (проверено по коду ядра 0.23.0).

Индекс (`mcp/aec_rag`) зовёт обе модели через один OpenAI-совместимый адрес и ключ
(`rag_index.py`). Ядро умеет делать служебные вызовы через подписку
(`agent/auxiliary_client.py` в `runtime/.hermes-src`).

## Options

1. **Один провайдер, как сейчас.** Ничего не меняется. Не решает ни одной из трёх проблем.
2. **Раздельно эмбеддинги и разбор, без подписки.** Два выбора; свой адрес без обязательного
   ключа; локальные эмбеддинги. Просто, но с агентом по подписке разбор всё равно нужен по
   ключу.
3. **Раздельно, плюс разбор по подписке через ядро, плюс локальные эмбеддинги в приложении
   (выбрано).** Модель разбора может быть «как у агента» и при подписке: индекс отправляет
   вызов разбора не напрямую провайдеру, а через ядро, которое уже держит вход по подписке.
   Локальная модель эмбеддингов скачивается средствами ядра и запускается его же сборкой
   llama.cpp в режиме эмбеддингов, отдельным локальным процессом.
   Плюсы: всё, что просил владелец. Минусы и цена: переходник индекс → ядро (новая связь между
   частями); новый локальный процесс; расход лимита подписки — граф большого документа это
   сотни вызовов, чат с агентом может встать до сброса лимита; условия подписки могут не
   допускать массовую обработку.

## Decision

Вариант 3. Порядок: сначала раздельный выбор и свой адрес без ключа (T80), затем проверка
подписки — условия и бесплатный для денег, но расходующий лимит замер на одном документе с
согласия владельца (T81), и только по её итогу разбор по подписке с предупреждением (T82);
локальные эмбеддинги — замер кандидатов на русских документах и кнопка «Скачать» (T83).
Если T81 покажет, что условия подписки не допускают такую нагрузку, — вернуться к владельцу с
вариантами, а не строить в обход.

## Consequences

- В [ARCHITECTURE](../ARCHITECTURE.md) появятся переходник «индекс → ядро» для разбора и
  локальный процесс эмбеддингов — описываются при реализации T82 и T83.
- Смена модели эмбеддингов по-прежнему перестраивает индекс; приложение говорит об этом до
  сохранения.
- Загрузки моделей идут только с Hugging Face и релизов llama.cpp и только по явному действию
  человека (как UR39); проектные данные наружу не уходят.
