# 0014 — Хранение учётных данных по типу

- Date: 2026-08-17 (SPEC C10); 2026-10-09 (ключи при нескольких профилях, D-195)
- Status: accepted
- Approved by: owner

## Context

Ядро умеет хранить ключ провайдера само — `model.save_key` пишет его открытым текстом в
`.env` профиля, а `POST /api/env/reveal` отдаёт его обратно. Вход через браузер (OAuth)
целиком ведёт ядро и хранит токен в `auth.json` профиля. С двух профилей (главный +
специалист) ядро включает мультиплекс и читает ключи только из секретов профиля —
окружение процесса для профилей закрыто.

## Options

### API-ключ — в safeStorage ОС и в ядро через наш источник секретов; OAuth — у ядра, различие записано — chosen

- Advantages: ключ, введённый в нашем интерфейсе, не ложится на диск открытым текстом;
  кнопки «показать ключ» нет; работает в каждом профиле, включая специалистов.
- Limitations: OAuth-токен зашифровать нельзя — поток ведёт ядро, токен через приложение не
  проходит; для провайдеров вида `external` токен держит чужой CLI.
- Changing it later: costly.

### Ключ в `.env` профиля, как у ядра

- Limitations: открытый текст на диске; против правила R2.

## Decision

API-ключ шифруется safeStorage ОС (всегда; переключатель шифрования донора не берём, HX20) и
попадает в ядро плагином `aec_secret_filter` как внешний источник секретов (их контракт
`SecretSource`, как у 1Password и Bitwarden) — в каждый профиль. `.env` профиля, если в нём
есть ключ, главнее. `model.save_key` и `POST /api/env/reveal` главный процесс не пропускает
никогда. Токен шлюза клиента — в safeStorage клиента; ключи моделей сервера — окном из трея
сервера, шифрованно на сервере.

## Consequences

- Отказ пропуска — `DENIED_RPC_METHODS` и `DENIED_REST_ROUTES` в
  `main/gateway-passthrough-pure.ts`; гейт `provider-key-guard.test.ts`.
- Секрет в тексте не уходит в память агента (тот же плагин, [0006](0006-memory-mem0.md)).
- Подробно — [plan-details.md](../plan-details.md) §«Приёмка владельца 2026-10-09 — ключи при
  нескольких профилях», [THREAT_MODEL.md](../THREAT_MODEL.md).
