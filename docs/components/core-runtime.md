# Ядро и его запуск

## Что делает

Ядро — агент hermes-agent (Nous Research, MIT): разговор с моделью, вызовы
инструментов, сессии, память, навыки, расписания, внешние каналы. Мы его не форкаем и не
правим ([решение 0001](../decisions/0001-core-without-fork.md)): ставим ровно известный
коммит из git и с версии 0.2 поднимаем его **единым шлюзом** — отдельным процессом, который
ведёт окно, сеансы, групповые чаты и расписания ([решение 0017](../decisions/0017-single-gateway.md)).
Главный процесс запускает его командой ядра `hermes gateway ensure` и останавливает
`hermes gateway stop`. `hermes serve` остался только у серверной установки — рядом со шлюзом,
для клиентов по SSH-туннелю. Наша часть — каталог `runtime/`: установка ядра на пине, его
запуск, профиль и инструменты подъёма пина.

## Место в архитектуре

```mermaid
flowchart LR
  main[Главный процесс] -->|gateway ensure / stop, окружение с ключами| core[Единый шлюз ядра<br/>127.0.0.1, порт выбирает ядро]
  main -->|билет по именованному каналу| core
  main -->|WebSocket /api/ws + REST, билет| core
  core -->|HTTPS| llm[(Провайдер модели)]
  core -->|stdio MCP| mcp[aec-sources, aec-rag, aec-roster]
  core -->|чтение и запись| home[(Профиль HERMES_HOME)]
  core -->|bash терминала агента| gate[runtime/bin/hermes<br/>наш шлюз команд]
```

Как читать: главный процесс поднимает шлюз, берёт у ядра одноразовый билет и с ним
подключается; всё остальное ядро делает само — ходит к модели, запускает MCP-серверы как дочерние процессы, читает и пишет
свой профиль. Команда `hermes` в терминале агента попадает в наш шлюз команд, а не в
настоящий CLI ядра.

## Как устроено внутри

### Пин и два варианта раскладки

Версия и коммит ядра записаны в одном месте:

```js title="runtime/hermes-env.mjs"
--8<-- "runtime/hermes-env.mjs:core_pin"
```

Пин ставится на коммит, а не на тег: тег можно передвинуть, коммит — нет. Автор перестал
публиковать колёса на PyPI, а его сборщик отказывается собирать колесо, поэтому
`runtime/hermes-env.mjs` описывает две раскладки:

| | Разработка (рабочая копия) | Установленная программа |
|---|---|---|
| Исходники ядра | `runtime/.hermes-src` — неглубокий клон на `HERMES_SHA`, не редактируется | `runtime/core/` — снимок того же коммита в payload |
| Python ядра | `runtime/.hermes-venv` (CPython 3.14.6, установка `-e` из `.hermes-src`) | интерпретатор payload, собранного их менеджером пакетов (PM) |
| Признак | есть `.git` в корне | есть `runtime/core/manifest.json` или `install-mode.txt` |
| Профиль | `runtime/dev-profile` | `<root>/data/profile` |

`node runtime/setup.mjs` готовит разработку за 8 шагов: venv, исходники на пине,
ограничения версий из `uv.lock` ядра, установка `hermes-agent[mcp,ddgs]` и зависимостей
плагина Mem0, профиль разработки, затем сборка обоих payload поставки (`runtime/core`,
`runtime/mcp`) и сверка их хешей с записью `runtime/payload/payload-versions.json`. Так
рабочая копия работает ровно на том, что получит инженер. Сборка payload описана на
странице [установка и поставка](packaging.md).

### Профиль

Профиль ядра (`HERMES_HOME`) — каталог с конфигом, сессиями, памятью, навыками и
плагинами одного агента. Где он лежит, решает одна константа:

```js title="runtime/hermes-env.mjs"
--8<-- "runtime/hermes-env.mjs:profile_dir"
```

`AEC_HERMES_HOME` направляет весь стек — главный процесс, шлюз и `serve.mjs` — на другой
профиль: так автотесты работают на временной копии `runtime/e2e-profile`, не задевая
профиль ручной приёмки. Профиль никогда не лежит в домашнем каталоге человека и не
пересекается с обычной установкой Hermes на той же машине.

### Запуск единого шлюза

`ensureGateway` в `runtime/serve.mjs` готовит профиль так же, как `startServe` (наш `SOUL.md`,
предупреждение об урезанных наборах инструментов), и вызывает `hermes gateway ensure --json`.
Команда находит работающий шлюз этого профиля или запускает новый и отвечает адресом без
секретов (`api_origin` на 127.0.0.1, номер экземпляра, возможности). Шлюз получает окружение
клиента `ensure` один раз, при старте:

```js title="runtime/serve.mjs"
--8<-- "runtime/serve.mjs:gateway_env"
```

- `HERMES_GATEWAY_LOCK_DIR` — свой каталог блокировок в профиле: шлюз не пересекается с
  отдельной установкой Hermes на той же машине (D-164).
- `GATEWAY_MULTIPLEX_PROFILES` — шлюз обслуживает и профили специалистов: групповой чат
  собирается только из профилей этой машины.
- `extraEnv` — расшифрованные ключи провайдеров; поэтому смена ключа — это `gateway stop` и
  снова `ensure`.

Сроки замерены в T53.1 (`runtime/contracts/single-gateway-0.23.0.md`): холодный старт 5,5–30 с
(первый после установки бывает дольше — окно тогда догоняет подключение в фоне), `ensure` на
работающем шлюзе ≈1 с, остановка 6,5–18,5 с. Шлюз отцеплен от Electron и переживает его
падение, поэтому выход из приложения всегда идёт через `gateway stop`, а автотесты после
прогона останавливают шлюз временного профиля сами. Обе команды пишут строку в
`<профиль>/serve.log` (`gateway ensure: exit 0 in … ms`).

Билеты выпускает Python-клиент самого ядра (`_session_ticket` в `hermes_cli/gateway_client.py`),
которого главный процесс держит дочерним процессом (`apps/desktop/src/main/local-gateway-python.ts`
— перенос их кода). Назначение билета говорит, на что он годен: `interactive` — сокет,
`native-http` — один REST-запрос. Билет проходит только в главном процессе.

### Запуск `hermes serve` (только сервер)

С версии 0.2 `serve` запускает только серверная установка — рядом с единым шлюзом, для
клиентов по SSH-туннелю; вызовы групповых комнат `serve` сам пересылает шлюзу (замер T50).
`startServe` в `runtime/serve.mjs` перед запуском кладёт в профиль наш `SOUL.md` (если
своего там нет) и предупреждает, если наборы инструментов урезаны. Затем:

```js title="runtime/serve.mjs"
--8<-- "runtime/serve.mjs:spawn_serve"
```

- `--isolated` — без него второй `serve` на том же профиле «присоединился» бы к живому
  процессу-сироте и вышел, не открыв порта.
- `HERMES_DASHBOARD_SESSION_TOKEN` — токен шлюза задаём сами (24 случайных байта или
  постоянный токен серверной установки); он входит в адрес WebSocket и не покидает
  главный процесс.
- `HERMES_TUI_CHECKPOINTS=1` — снимки файлов перед правкой агентом (откат, UR14): путь
  шлюза читает этот переключатель из окружения, а не из конфига.
- `memoryEnv` — выключенная телеметрия Mem0 и каталог Mem0 внутри профиля.
- `extraEnv` — расшифрованные ключи провайдеров и настройки индекса; на диск они не
  пишутся.

Порт — 18789 (`AEC_SERVE_PORT` меняет его для приёмочного стенда), адрес — только
127.0.0.1. `waitHealthy` ждёт первого кадра шлюза (`gateway.ready`): холодный старт ядра
замерен в 29 с, поэтому окно ожидания — 2 минуты. Вывод процесса пишется в
`<профиль>/serve.log`. `stopServe` даёт ядру 5 с на мягкую остановку.

### Что продукт держит в профиле сам

Главный процесс перед каждым запуском дописывает в `config.yaml` профиля свои
умолчания (правила — `apps/desktop/src/main/agent-defaults-pure.ts`): границу голоса
(слово-активатор выключен; распознавание — только местное, русское и только с нашей моделью на
диске, `dictation-pure.ts`), бюджеты хода, отказ от самопроверки обновлений и телеметрии ядра, веб-поиск DuckDuckGo
без ключа, режим подтверждений команд, выключенные наборы инструментов, регистрацию наших
MCP-серверов и плагинов. С ядра 0.23 к ним добавились отказы от самообновления плагинов
(`plugins.auto_apply`), веб-приложения (`webapp.enabled`), Daybreak (`agent.daybreak`) и
ленивой доустановки пакетов (`security.allow_lazy_installs`) — `apps/desktop/src/main/agent-defaults-pure.ts`.
С T53 закреплён и предел обмена между ботами без человека в комнатах:
`gateway.bot_loop_guard.enabled: true` и `max_hops: 4` — как у ядра, но смена их умолчания
не снимет предел молча (UR47).
Большинство правил дописывает умолчание, не трогая уже
выбранного человеком (`applyConfigDefault` в `apps/desktop/src/main/index.ts`).

### Память Mem0

С версии 0.22 провайдер Mem0 — внешний плагин. `setup.mjs` держит его исходники на
`MEM0_PLUGIN_SHA` (версия 1.3.0) в `runtime/.mem0-plugin-src`, а главный процесс при
старте копирует плагин в `plugins/mem0` каждого профиля
(`runtime/register-mem0-plugin.mjs`). Хранилище — локальный qdrant внутри профиля
([решение 0006](../decisions/0006-memory-mem0.md)).

### Маршруты субагентов

С версии 0.2 агент может поручить подзадачу субагенту на другой модели («быстрый поиск» на
дешёвой, ответ на сильной) или в профиле специалиста (UR48). Это официальный плагин ядра
`advanced-delegation`: режимы `delegation.backend: model_map` (маршруты по моделям) и
`profile_routes` (маршруты по профилям). Модель видит только имена маршрутов и их описания.

Плагин не ставится из сети. `setup.mjs` держит его на `DELEGATION_PLUGIN_SHA` — том коммите,
который проверил каталог самого ядра, — в `runtime/.delegation-plugin-src`, а главный процесс
при старте копирует его в `plugins/advanced-delegation` каждого профиля и включает в
`plugins.enabled` (`runtime/register-delegation-plugin.mjs`, вызов из
`register-secret-filter.mjs`). Плагин, выключенный человеком (`plugins.disabled`), обратно
не включается.

Маршрут ссылается на настроенного провайдера, ключ берётся из его настроек. Сам плагин умеет
хранить `api_key` маршрута в `config.yaml` открытым текстом — у нас это закрыто в мосте
(`guardDelegationRouteKeys` в `apps/desktop/src/main/gateway-passthrough-pure.ts`): маршрут с
настоящим ключом не сохраняется, а из общего сохранения настроек ключи раздела `delegation`
вырезаются. Окно маршрутов донора ключ и не вводит — оно возвращает маску ядра. Проверка на
ядре без модели — `runtime/delegation-routes-probe.mjs`.

### Шлюз команд `hermes`

Расписания специалистов донора запускают `hermes -p <специалист> chat …`, поэтому
`hermes` должен быть на PATH процессов ядра. Но та же команда меняет настройки ядра —
агент однажды поставил MCP-сервер в обход карточки согласия. Поэтому первым на PATH
стоит `runtime/bin/hermes` → `hermes_gate.py`: пропускает только `chat` (с `-p`),
`--version` и `--help`, остальное отклоняет понятным агенту сообщением.
Одно исключение (T66, решение [0019](../decisions/0019-documents-environment.md)):
на команду навыков документов `hermes pm environment documents --extra documents --extra
documents-pdf` шлюз сам, без ядра, отвечает путём к запускателю `runtime/core/docs-env/python`
— так навык находит свои библиотеки без сети.

### Подъём пина

Ядро выходит раз в 1–2 месяца. Подъём — это измерение, а не правка по памяти:

- `runtime/contract-snapshot.mjs` записывает поверхность ядра (методы шлюза, маршруты
  REST, умолчания конфига) и то, чем из неё пользуется наш код, в
  `runtime/contracts/hermes-<версия>.json`; `contract-diff.mjs` сравнивает две версии;
- `runtime/donor-report.mjs <старый SHA> <новый SHA>` показывает, какие перенесённые
  файлы донора изменились (сначала — файлы с нашими правками);
- разбор каждого подъёма лежит в `runtime/contracts/reading-<версия>.md` и
  `donor-move-<версия>.md`.

Порядок и проверки после подъёма — [эксплуатация](../operations.md), раздел «Подъём пина ядра»;
факты о ядре, проверенные по коду, — [core-facts](../core-facts.md).

## Ключевой код

| Файл | Что там |

| `runtime/serve.mjs` | единый шлюз (`ensureGateway`, `stopGateway`, `ticketRuntime`) и `hermes serve` сервера (запуск, готовность, остановка); `node runtime/serve.mjs smoke` |

## Данные

Профиль ядра: `config.yaml`, `SOUL.md`, база сессий `state.db`, память (записка ядра и
хранилище Mem0), навыки, плагины, журналы, `serve.log`. Подробно — [данные](../data.md).

## Тесты

23 теста `runtime/*.test.mjs` (Vitest) проверяют наши модули: регистрацию серверов,
SOUL, шлюз команд, разбор контрактов. Поведение самого ядра проверяется живыми зондами
`runtime/*-probe.mjs` и живой приёмкой — они запускают настоящее ядро с моделью и стоят
денег, поэтому идут только с согласия владельца.

## Ограничения и известный долг

- T49: подпись A2A не работает из-за дефекта ядра (`eval/reports/a2a-signature-defect.md`)
  — ждёт исправления у авторов.
- `pnpm parity` (реестры паритета, инструментов и платформ) сверяет таблицы кода с
  исключениями HX в [PRODUCT](../PRODUCT.md) и с задачами из [TASKS](../TASKS.md) и
  завершённых этапов `docs/history/stage-*.md`; задачу он понимает и строкой таблицы
  этапа, и пунктом `- [x] T44` журнала. Код: `runtime/parity-registry.mjs`,
  `readTasksText`.
- Зонды без `AEC_HERMES_HOME` пишут в `runtime/dev-profile` — профиль ручной приёмки.
