# Разбор `contract-diff` 0.20.4 → 0.20.5

Задача 3.B1, 2026-08-23. Источник — `node runtime/contract-diff.mjs`
(`hermes-0.20.4.json` → `hermes-0.20.5.json`).
Пин: `e624e9fd` (v2026.8.18) → `fcbd1076` (v2026.8.19).

Слепок 0.20.5: методов 167 в 27 модулях, маршрутов 243, дефолтов конфига 789.
Наша поверхность: методов 45, маршрутов 10 — **все на месте**, ни одного
`ВНИМАНИЕ, метод не найден`.

Итог одной строкой: контракт двинулся мало, но **третья категория принесла три
позиции, каждая из которых меняет поведение молча**, и одна из них — про то,
куда уходит звук с микрофона.

---

## 1. Сломалось — 1 позиция

```
дефолт конфига stt.provider — было в "local"
```

**Касается нас, и это главная находка разбора.** Ключ не переименован и не
перенесён — он **убран намеренно**. Их собственная записка на месте удаления:

> `NOTE: no seeded "provider" key. Strict selection semantics treat a stored
> stt.provider as an explicit user pick; seeding "local" here made a fresh
> install indistinguishable from a user choice. The autodetect ladder covers
> unset.`

Замысел здравый: раньше нельзя было отличить «человек выбрал local» от «так
легло умолчание». Но следствие для нас — смена поведения без единой ошибки.

**Что было (0.20.4).** `stt.provider: "local"` приезжал умолчанием, то есть
выбор считался ЯВНЫМ. При отсутствии `faster-whisper` ядро писало
предупреждение и возвращало `none`: голосовой ввод не работал, но **звук
никуда не уходил**.

**Что стало (0.20.5).** Ключа нет → выбор не явный → работает лестница
автоопределения. Их докстринг `_get_provider`:

> `When no provider is configured, auto-detect tries: local > groq (free) >
> openai (paid).`

**Замерено на нашей установке:** `faster-whisper` в `runtime/.hermes-venv`
**не стоит** (`ModuleNotFoundError`) — экстра `[mcp]` его не тянет. Значит на
этой машине лестница проходит первую ступень мимо и приходит к облачному
провайдеру, если у человека настроен ключ groq или OpenAI. А ключ провайдера
настраивают все — он нужен самой модели.

**Итог: запись голоса на машине без `faster-whisper` меняет адресата с «никуда»
на «в чужое облако», и ни одна строка интерфейса об этом не говорит.** Наш код
`stt.*` не трогает вовсе (проверено по `main/`, `aec/`, `shared/`), то есть
защиты у нас сейчас нет никакой.

Это решение владельца, а не наше: см. задачу 3.B1д.

## 2. Молча сменило умолчание — 15 позиций

Из них `_config_version 37 → 38` — их собственный счётчик миграций, не
поведение. Двенадцать — «тело метода изменилось». Настоящих смен умолчания
две, и обе разобраны ниже.

### 2.1 `agent.max_turns`: 500 → `null` (без предела)

Их основание записано прямо в конфиге: «предел ходов приносил больше проблем,
чем решал — тихое усечение на середине задачи».

**Чем это опасно у нас.** Предел ходов был единственной встроенной границей
цикла. Без него зациклившийся агент считает деньги на платной модели, пока
человек не остановит его руками.

**Что смягчает — и что появилось в этом же релизе.** Два новых ключа:

- `agent.stall_guards` (**true** по умолчанию) — два консервативных сторожа:
  прерыватель цикла на 3+ одинаковых вызовах инструмента с одинаковым
  результатом и повторный запрос, когда модель говорит «продолжаю», но
  ничего не делает. **Никогда не блокирует**, только дописывает пометку.
- `agent.run_budget_seconds` (**null**, то есть выключен) — бюджет по часам на
  прогон, с предупреждением агенту на 80% и урезанием таймаутов провайдера под
  остаток.

То есть замена пределу ходов у них есть, но она **выключена**, а сторожа
цикл не останавливают. Решение — задача 3.B1д.

### 2.2 `gateway.scale_to_zero.idle_timeout_minutes`: 5 → 2

**Не касается нас.** Ключ из блока `gateway` — их мессенджер-шлюза, который мы
не поднимаем (замер 3.6: под `hermes serve` их планировщик не тикает именно
поэтому).

### 2.3 Двенадцать «тело метода изменилось»

Пять из них мы вызываем.

| Метод | Что изменилось | Вывод |
|---|---|---|
| `session.list` (58 → 101) | принял параметр `title` — точный поиск по заголовку | **Прибавка, полезная нам** — задача 3C.4б |
| `prompt.submit` (554 → 567) | `_get_db()` → контекст `_session_db(session)` | Внутренняя перестройка доступа к БД, контракт тот же |
| `command.dispatch` (678 → 693) | то же | То же |
| `config.set` (758 → 759) | то же + `@_profile_scoped` | См. ниже |
| `plugins.manage` (112 → 134) | появилось умолчание `enable=True` | **Не касается**: умолчание на действии `install` — их каталог плагинов, исключён HX5. Мы зовём только `list` и `toggle`, и `enable` при `toggle` передаём сами |

**Общая перестройка, стоящая за тремя из пяти: `@_profile_scoped`.** Методы
теперь привязывают `HERMES_HOME` к `params['profile']` на время вызова. Их
докстринг называет сценарий дословно: «десктоп присылает `profile`, чтобы одна
серверная часть, обслуживающая все профили, попадала в дом нужного профиля» —
**это ровно наша архитектура**. Обратная совместимость полная: без `profile` в
параметрах `_profile_home(None)` возвращает `None` и обёртка ничего не делает.

Два метода профилей мы не вызываем напрямую, но роестр стоит на их данных:

- **`profiles.list` отдаёт новое поле `worker_session`** — самая свежая
  рабочая сессия (kanban/tool), которая в списках разговоров не показывается
  никогда. Их основание (#90268): роестр должен считать специалиста занятым,
  пока работает его воркер. У нас это «кто сейчас занят» из
  `specs/agent-roster.md` — мы его повторяем, и до этого поля видели не всё.
- **`profiles.list` отдаёт `ui_meta_revisions`, а `profiles.configure` принимает
  `ui_meta_expected_revisions`** — сравнение с ожидаемой версией при записи.
  Весь наш роестр живёт в `ui_meta.aecpilot`, и до сих пор две записи подряд из
  разных окон затирали друг друга молча. Их комментарий отдельно оговаривает,
  что **наличие поля и есть признак поддержки** — то есть проверка версии
  делается определяемой, а это ровно то, что нужно при удалённом ядре чужой
  версии (задача 3.12).

Обе позиции — задача 3C.4в.

## 3. Появилось — 10 позиций

### 3.1 Два метода, исключённые решением владельца

`tour.respond` и `preview.act.respond` — показ интерфейса агентом и нажатие
внутри предпросмотра. SPEC HX16 и HX17, задача 3.B1б ставит на них сторожевой
тест.

### 3.2 Поведение агента — под перепрогон эвала

- **`agent.execution_guidance` («auto»)** — **вставляет блок в системный
  промпт**: настойчивость с инструментами, обязательный инструмент для
  арифметики и системных фактов, чтение после внешней записи, сверка счёта,
  дословное сохранение идентификаторов, завершение только после проверки.
  Выбирается один раз на старте сессии по имени модели. Это изменение
  поведения ИИ в чистом виде (AGENTS §9), а не настройка.
- **`memory.nudge_interval` (10)** — периодический разбор встроенной памяти.
  Меняет содержание промпта раз в N ходов.
- `agent.reasoning_echo` (false) — согласие на сохранение `reasoning_content`
  на повторе, по провайдеру. Умолчание сохраняет прежнее строгое поведение.
- `agent.stall_guards`, `agent.run_budget_seconds` — разобраны в §2.1.

### 3.3 Веб без ключей — не касается сегодня, но записать

`web.keyless_fallback` (true), `web.keyless_rescue` (true), `web.provider_tier`
({}). Без настроенного бэкенда `web_search`/`web_extract` теперь ходят по кругу
через пять чужих бесплатных тарифов.

**Замерено:** в нашем профиле тулсет «Web Search & Scraping» **выключен**
(`hermes tools` показывает `[ ]`), значит инструментов у агента нет и ходить
некуда. Записано на день, когда веб-поиск включат: тогда умолчание означает
запросы к пяти чужим сервисам **без единой настройки**.

## 4. Чего в этом окне нет

- **Ни одной новой зависимости Python.** `uv.lock` — тот же набор пакетов,
  `requires-python` тот же. Переустановка заменила ровно один пакет:
  `hermes-agent 0.20.4 → 0.20.5`. Для сравнения: 0.20.0 → 0.20.4 тянуло за
  собой MCP 2.x отдельной задачей.
- **Ни одного удалённого метода и маршрута.** REST 229 → 229 набором, методы
  154 → 156 только прибавкой (счёт по `@method` в дереве; слепок считает 167,
  потому что берёт все модули, включая те, что не в `tui_gateway`).
- **Исправления подписи A2A нет.** `plugins/platforms/a2a/security.py` и
  `adapter.py` побайтово те же (сверены blob-хэши). Проба
  `runtime/a2a-push-probe.mjs` останется красной — ожидаемо, см. задачу 3.11.
