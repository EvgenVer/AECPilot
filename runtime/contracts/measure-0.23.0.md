# Замер ядра v0.23.0 до подъёма пина (задача T50)

2026-11-07. Ядро `v0.23.0` (`2bd378ed`) поставлено отдельно от рабочей копии: временный
`git worktree` этой ветки в каталоге сессии, `runtime/setup.mjs --no-payload` с пином
v0.23.0 (Python 3.14.6). Каждая проба шла на своей временной копии `runtime/e2e-profile`,
подготовленной как при старте приложения: умолчания профиля из `CORE_OPT_OUTS` плюс
`plugins.auto_apply: false`, `webapp.enabled: false`, `updates.check: false`, наш фильтр
секретов и плагин Mem0 (`installSecretFilterEverywhere`). Модель не вызывалась — всё
бесплатно. После каждого прогона ни `gateway run`, ни `serve`, ни `electron.exe` не осталось.

## Коротко

| Вопрос | Ответ |
|---|---|
| Кто владеет комнатами при одном `hermes serve --isolated` | Сам `serve`: `groups.capabilities` → `driver: true`, комнаты в корневом `shared-state.db` |
| …когда рядом работает наш `gateway run` (расписания включены) | **Шлюз.** Через ≈12 с после его готовности `serve` пересылает ему все вызовы `groups.*`, а комнаты, созданные без шлюза, передаёт ему (`hosted_room_gateway_handoffs`) |
| Что будет, если выключить расписания (шлюз остановлен) | **Все комнаты пропадают из списка.** Переданная комната отвечает «шлюз, который держит этот групповой чат, не запущен» (5124), созданная при шлюзе — «не найдена» (4114) |
| Возвращаются ли они | Да: шлюз запущен снова — видны все три комнаты, в том числе созданная без шлюза |
| Нужен ли шлюзу внешний порт | Нет: оба его порта — на `127.0.0.1` (сеансовый API `api_origin` и «свидетель» цикла, который был и в 0.22.2); управление — именованный канал |
| Как это делает их окно | Их Desktop 0.23 бэкендом поднимает не `serve`, а `hermes gateway ensure --json`: один шлюз — окно, сеансы, комнаты и расписания |
| `mcp-health-probe` | Все 8 инструментов `aec-sources` на месте через 210 с; `reload.mcp` — 0,9 с |
| Расписания под шлюзом | Тикают, как в 0.22.2 (`cron-gateway-tick-probe`); шлюз — ≈340 МБ памяти |
| `a2a-push-probe` | Дефект подписи на месте: получатель отвергает уведомление (известная особенность, T60) |
| Установка | `setup.mjs` падает на разрешении зависимостей: ядро держит версии через `[tool.uv] override-dependencies`, а мы передаём только свой файл замен |

## 1. Групповые комнаты — `runtime/group-owner-probe.mjs`

Комната собирается только из профилей этой машины (иначе 5111 «profile … is not local to
this gateway»), поэтому проба заводит в копии профиля четыре профиля-специалиста.
Окружение шлюза — как у нашего `cron-runner` (`cronRunnerSpawnEnv`: мультиплекс профилей,
свой каталог блокировок), остановка — как у него, `proc.kill()`.

| Шаг | `groups.capabilities` через `serve` | Список | Что ещё |
|---|---|---|---|
| A. Один `serve` | `driver: true`, `persistent_process: true`, RoomLink включён, 22 метода | 0 → комната A создана за 17 мс | A лежит в корневом `shared-state.db` |
| B. Запущен `gateway run` | готов через 12,3 с; дальше — ответ шлюза: 16 методов, RoomLink выключен (`canonical_driver_required`) | 1 (A); комната B создана за 66 мс | A передана шлюзу; порты шлюза — `127.0.0.1:<api_origin>` и `127.0.0.1:<свидетель>`, через 30 с те же |
| C. Шлюз остановлен | снова свой: 22 метода | **0** | A — 5124 «шлюз не запущен», B — 4114 «не найдена»; комната C создаётся локально |
| D. Шлюз снова запущен | готов через 12,4 с | 3 (A, B, C) | C тоже передана шлюзу |

Чтение кода это подтверждает (`tui_gateway/methods_groups_forward.py`): переданная шлюзу
комната «never written to the standalone store, so with its gateway down every call on it is
a retryable refusal». Ядро при остановке через `proc.kill()` пишет в журнал шлюза «Previous
gateway life … exited UNCLEANLY» — завершения без подготовки.

Вывод для T53: на нашей нынешней схеме (окно на `serve`, шлюз — по кнопке «Расписания»)
групповые чаты исчезают у человека, который выключил расписания. Это решение владельца:
варианты — в разделе «Вопрос владельцу».

## 2. MCP — `runtime/mcp-health-probe.mjs`

Профиль с зарегистрированным `aec-sources` (stdio, наш Python из `runtime/mcp`). Инструментов
через 20 с — 8, через 210 с (окно проверки здоровья прежней версии плюс запас) — те же 8;
`reload.mcp` три раза подряд — 904, 923 и 942 мс (у приложения предел 15 с). Вердикт пробы:
«all MCP tools survived the proof window». `tools/mcp_death_supervisor.py` в 0.23 удалён, и
строк «proved healthy» в журнале больше нет — проба опирается на `tools.show`, а не на них.
Имена инструментов — `mcp__aec_sources__sources_list`, как и в 0.22.2.

## 2а. Расписания — `runtime/cron-gateway-tick-probe.mjs`

Шлюз без единой платформы («No messaging platforms enabled») тикает: задача «каждую
минуту» сработала сама в первой половине пробы, `next_run_at` сдвинулся на следующий слот.
Путь решения [0011](../../docs/decisions/0011-schedule-tick-in-main.md) на 0.23 работает.

Память шлюза `gateway run` на копии профиля (наш фильтр, Mem0, четыре профиля-специалиста,
без MCP-серверов) — 340–347 МБ рабочего набора дерева процессов за первую минуту.

## 3. A2A — `runtime/a2a-push-probe.mjs`

Уведомление ушло (ответ приёмника HTTP 200), подпись в заголовке совпадает с HMAC строки,
которую подписали (`json.dumps(…, sort_keys=True, ensure_ascii=False)`), и не совпадает с
HMAC пришедшего тела (`json.dumps(payload)`). Получатель уведомление не принимает. Как в
0.22.2; по решению владельца 2026-11-07 — известная особенность (T60).

## 4. Установка и зависимости — для T51

- **`setup.mjs` должен передавать замены ядра.** В v0.23.0 `pyproject.toml` ядра держит
  `[tool.uv] override-dependencies`: `pynacl>=1.6,<1.7`, `cryptography==50.0.2`,
  `Pillow==13.0.0` (поверх `browser-harness==0.1.13`, который просит `pillow==12.3.0`) и
  снятие `spacy-curated-transformers`. `uv pip install` их не читает: без них резолюция
  невозможна («hermes-agent and pillow==13.0.0 are incompatible»). Замер прошёл с этими
  строками, добавленными к нашему `uv-overrides.txt`; в T51 `setup.mjs` берёт их из дерева
  ядра на пине, как уже берёт ограничения из `uv.lock`.
- **Состав venv ядра** (без самого ядра): было 103 пакета, стало 100. Новый один —
  `ruamel-yaml-clib`; ушли `jinja2`, `markupsafe`, `importlib-metadata`, `zipp`; остальное —
  подъёмы версий, среди них Pillow 12.3 → 13.0, MCP SDK 2.0 → 2.3, Starlette 1.3 → 1.9,
  uvicorn 0.41 → 0.54, openai 2.24 → 2.54, cryptography 50.0.1 → 50.0.2.
- **`agent-browser` их менеджер пакетов снял**: `pm/defaults.py` —
  `RETIRED_DEFAULTS = {"agent-browser": "chromium"}`; `chromium` в нашем `TOOLS` уже есть.
- Предупреждение `uv venv` «incompatible with the project's Python requirement `>=3.12,
  <3.14`» — это наш корневой `pyproject.toml` (каталог запуска), а не ядро; было и раньше.

## 5. Попутно

- `skills.external_dirs` в `runtime/e2e-profile` держал один и тот же каталог четыре раза:
  ядро переписывает `config.yaml` и снимает кавычки, а `mergeSkillsDirIntoConfigYaml`
  узнавала только свою форму с кавычками и дописывала путь снова. Исправлено с тестом
  (`runtime/register-aec-rag.test.mjs`, «recognises the directory the core rewrote without
  quotes» — красный до правки, зелёный после).

## Вопрос владельцу (для T53)

Пример: инженер при включённых расписаниях создал групповой чат «КЖ + КМ», затем выключил
расписания — чат пропал из списка и вернётся, только когда расписания снова включат. Причина:
на 0.23 комнатой владеет шлюз `gateway run`, а он у нас живёт, только пока включены
расписания.

| Вариант | Как работает | Плюсы | Минусы и цена |
|---|---|---|---|
| **А. Как у Hermes: один шлюз** | Ядро запускается как `gateway run` (у Hermes — `gateway ensure`) вместо `hermes serve`: окно, чаты, комнаты и расписания в одном процессе | Ровно логика ядра; один процесс и один владелец сеансов; расписания всегда работают | Переделка нашего слоя процессов: свой порт и вход по билету вместо фиксированного порта и токена, режим «сервер/клиент» (сетевой вход у шлюза требует их поставщика входа — не проверено), мок-шлюз e2e. Оценка 4–6 задач; риск в режиме «сервер» |
| **Б. Шлюз всегда рядом** | `serve` остаётся окну, `gateway run` поднимается при каждом старте, а не по кнопке; переключатель «Расписания» уходит — рутины ставятся на паузу по одной, как у Hermes; останавливаем шлюз корректно, а не `kill` | Комнаты не пропадают; почти без переделки (1–2 задачи) | Второй процесс всегда: ≈340 МБ памяти; два процесса ядра, `serve` пересылает комнаты шлюзу. Потолок: если шлюз упал, комнаты недоступны до его перезапуска (перезапускаем сами) |
| **В. Как сейчас + предупреждение** | При выключении расписаний окно предупреждает, что групповые чаты станут недоступны | Дешевле всего | Человек теряет доступ к чатам из-за несвязанной настройки; противоречит UR47 по смыслу |

Рекомендация — **Б**: самый простой вариант, который выполняет UR47 без потерь; путь к А
остаётся открытым, если второй процесс станет в тягость (например, на слабых ноутбуках) —
тогда цена перехода та же, 4–6 задач.
