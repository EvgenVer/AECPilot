Разбор `node runtime/contract-diff.mjs runtime/contracts/hermes-0.21.2.json
runtime/contracts/hermes-0.21.3.json`, выполнен 2026-09-15 **до установки ядра**: сторона
0.21.3 снята с рабочего дерева `git worktree` на `345cd2b0` ключом `--core` (формат 4, тот же
инструмент, что и для 0.21.2 — ловушка 4 из MEMORY не повторена). Правило прежнее: у каждого
расхождения либо решение, либо «нас не касается» с основанием. Счёт сходится:
**сломалось 14, появилось 18, молча сменило умолчание 16.**

Сводка ядра 0.21.3: методов **215** (было 225: −12 `*.respond`, +2), модулей 70, маршрутов
267, дефолтов конфига 877, событий 43, маркеров чекпойнтов 9. Наша поверхность: **41 из 45
методов на месте**, 12 из 12 маршрутов; четыре наших метода сняты ими намеренно (§1.1).

## 0. Уточнение после установки (2026-09-15) — две ловушки самого снимальщика

Слепок с УСТАНОВЛЕННОГО ядра (`hermes-0.21.3.json` перезаписан) разошёлся со слепком с
worktree в двух местах, и оба — дефекты `contract-snapshot.mjs`, а не ядра:

1. **Хеш тела метода с лямбдой в замыкании менялся от запуска к запуску.** Обработчики,
   собранные фабрикой `_passthrough` (`groups.log`, `groups.replica_state`,
   `learning.delete`, `learning.detail`), держат в замыкании кортеж `params=` с `lambda`;
   `repr` кортежа печатал `<function <lambda> at 0x…>` — адрес, разный в каждом процессе.
   Поэтому `groups.log` «менялся» и в 3.B4, и здесь (§2.2 — ложно), а два `learning.*`
   «менялись» между двумя слепками ОДНОГО коммита. Починено: `stable_repr` печатает функцию
   как `fn:<qualname>:<hash исходника>`; два подряд слепка одного дерева теперь побайтно равны.
2. **Под `--core` список зависимостей брался из метаданных УСТАНОВЛЕННОГО пакета**
   (`importlib.metadata.requires`), то есть worktree-слепок 0.21.3 нёс список 0.21.2 и не
   видел `pillow-heif` (его нашёл диф `pyproject.toml`, не инструмент). Починено: пины
   читаются из `pyproject.toml` дерева через `packaging.Requirement` в обоих режимах.

Базовый слепок 0.21.2 пересобран тем же починенным инструментом с worktree `939e45c9`
(`--core`, `--version 0.21.2`, `--sha`), чтобы обе стороны дифа считались одинаково.
**Итоговый счёт по установленному ядру: сломалось 14, появилось 20, молча сменило 21** —
те же 14 и 18 плюс две новые зависимости (`pillow-heif`, `google-cloud-pubsub` в extra
`google-chat`) и шесть переименований extra `google` → `google-chat` / подъём `slack-sdk`
3.43.0 → 3.44.1 в extra `slack`/`messaging`; ложный `groups.log` из §2.2 снят. Ни один из
новых пунктов нас не касается: extras `google-chat`/`slack`/`messaging` не ставятся,
`pillow-heif` — не ставится решением владельца (веттинг 3.B5е).

## 1. «Сломалось» — 14 из 14

### 1.1. Двенадцать методов `*.respond` и событие `approval.request` — протокол вопросов заменён

`clarify.respond`, `secret.respond`, `sudo.respond`, `terminal.read.respond` (**наши четыре**),
`mcp.setup.respond`, `preview.act.respond`, `preview.read.respond`, `tour.respond`,
`vault.code.respond`, `vault.save_login.respond`, `vault.unlock.respond`, `window.read.respond`;
событие `approval.request`.

Что пришло взамен — `tui_gateway/server_requests.py` (новый модуль, докстрока читается как
контракт): «Every "ask the renderer" bridge (clarify, approval, sudo, secret, vault prompts,
desktop GUI reads, MCP setup consent, the tour) is one `send` (blocking) or `send_async`
(queue-backed approvals) and one response frame from the client — no paired `*.request`
notification / `*.respond` method, no per-kind `*.expire`». Механика:

- ядро шлёт **JSON-RPC-запрос сервер→клиент** `{"jsonrpc":"2.0","id":"srq-<12 hex>",
  "method":"clarify"|"approval"|"secret"|"sudo"|"terminal.read"|"preview.read"|"preview.act"|
  "mcp.setup"|"tour"|…, "params":{"session_id":…, …}}` — id строковый, чтобы не пересечься с
  целыми id клиента;
- клиент отвечает **кадром-ответом** с тем же id: `{"jsonrpc":"2.0","id":"srq-…","result":{…}}`;
  ответ на закрытый id молча отбрасывается;
- таймаут/отмена (прерывание, закрытие сессии, остановка) — ОДНО уведомление
  `request.cancel {id, method, reason}` (появилось, §3.4);
- переподключение: неотвеченные вопросы возвращаются полем `open_requests` из
  `session.resume` / `session.activate` / `session.events.since` (последний — в §2.2);
- пакетное уточнение: `clarify.lock` (§3.1) запирает ответы по одному вопросу, последний
  замок разрешает запрос; `request.answer` — прокси для клиента, который запроса не получал
  (окно комнаты Bot Mode).

**Нас касается напрямую.** Наш `shared/gateway/client.ts` разбирает только уведомления
`event` и ответы с числовым id; кадр с `method` и строковым `id` он считает мусором и
выбрасывает (`parseFrame` → `undefined`). Значит на 0.21.3 без переделки **ни один вопрос
агента не дойдёт до экрана**: подтверждение разрушающей команды (R21) повиснет до таймаута,
уточнение и секрет — тоже. Решение: задача **3.B5в** — мост учится принимать запросы
сервер→клиент (новый слушатель + `respond(id, result)` + обработка `request.cancel` и
`open_requests`), main пересылает их в рендерер тем же IPC-каналом, что события, а ответы
человека едут кадром вместо вызовов `clarify.respond`/… (`main/index.ts` ~2590–2660);
`gateway-passthrough-pure.ts` помечает недоверенный текст страницы (R22) в **результате
ответа**, а не в параметрах метода; `shared/gateway/types.ts` — типы запросов; вендорный
`sdk/index.ts` (правка [1]) стыкуется с их `apps/shared/src/json-rpc-channel.ts`;
`store/server-requests.ts` и `…/gateway-event/server-requests.ts` приезжают вместо
`input-requests.ts`. `approval.respond` у ядра остался (в списке сломавшихся его нет) — на
0.21.3 это прокси, как `request.answer`; основной путь — кадр-ответ.

### 1.2. Ключ конфига `gateway.multiplex_profile_allowlist`

Снят миграцией 43 (`config_migrations.py`): мультиплексирующий шлюз теперь обслуживает все
профили под `profiles/`, ненужный профиль архивируется. Мы ключ не писали — **нас не
касается**; миграция `_config_version 42→44` пройдёт по нашему `config.yaml` без изменений
(ключа нет).
