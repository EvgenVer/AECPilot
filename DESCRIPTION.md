## Idea & intent
AECPilot — агентный инженерный workspace для строительного проектирования: «Claude Code / Codex, но для проектировщика». Инженер работает в кроссплатформенном desktop-приложении, где проект объединяет:
- **рабочую папку (vault)** — файлы как источник истины (стиль Obsidian): заметки, вики проекта, артефакты агента;
- **read-only источники** — подключаемые директории с исходными данными (задания смежников, ТУ, письма на сетевых дисках), агрегированные в единый проводник;
- **агента** (ядро hermes-agent), который читает источники, отвечает на вопросы со ссылками на документы, ведёт вики проекта, проверяет комплектность и противоречия исходных данных, готовит черновики документов.

Зачем: исходные данные проекта разбросаны по сетевым папкам; ответ на вопрос вида «какая установленная мощность в задании ЭОМ?» — это минуты и часы ручного перебора PDF и Excel; знание проекта живёт в головах и теряется между сессиями и людьми; новые редакции заданий легко пропустить. AECPilot превращает это в вопрос-ответ за секунды, накапливаемую вики и автоматический контроль изменений.

Платформенная ставка: это не один инструмент, а расширяемая система — сценарии оформляются как **skills** (стандарт agentskills.io), инструменты — как **MCP-серверы**, поэтому организация настраивает и наращивает систему под свои задачи, как это уже происходит в агентной разработке ПО.

## Target users / audience
- **MVP:** владелец продукта + несколько инженеров-проектировщиков его отдела (Windows; терминалом не пользуются — GUI обязателен с первого дня).
- **Перспектива:** проектные организации целиком (инженеры разделов, ГИП/РП); международный рынок — интерфейс en+ru с первого дня.

## Goals
- Четыре базовых сценария как предустановленные skills:
  1. **Q&A по исходным данным** со ссылками на файл/страницу — эталонный: полируется и эвалится первым;
  2. **вики проекта** (LLM Wiki по Карпаты; адаптация бандлового скилла Hermes `research-llm-wiki`);
  3. **проверка комплектности/противоречий** исходных данных;
  4. **генерация черновиков документов** по шаблонам.
- Все возможности Hermes из GUI: сессии, стриминг, approvals, skills, MCP, субагенты, память, выбор LLM-провайдера/endpoint.
- Просмотр PDF (вкл. сканы), DOCX, TXT, XLSX/CSV в приложении; .md — создание/редактирование с рендерингом; цитаты из ответов агента открывают документ на нужном месте.
- Фоновый детект изменений источников (по хэшам, без LLM) с предложением действий.
- Успех MVP: эвал-набор по эталонному проекту (точность + обязательные ссылки) **и** добровольное полевое использование на реальном проекте.

## Guardrails / Non-Goals
- Агент **никогда не изменяет файлы источников** — гарантия на уровне инструментов (записи в источники не существует как операции), а не договорённость.
- Не САПР и не BIM-редактор; инженерные решения не принимаются без человека в контуре.
- MVP не разбирает DWG/IFC (фаза 2+).
- Без серверной инфраструктуры: никаких отдельных СУБД и сервисов — всё embedded (SQLite, LanceDB), бэкап проекта = копия папки.
- Одновременная совместная работа с одним vault — вне MVP (источники общие, vault личный).
- Общая межпроектная база нормативки (СП/ГОСТ) — фаза 2; в архитектуре закладывается сразу.
- Только MIT/Apache-зависимости; AGPL исключён (модель распространения держим открытой, включая коммерческую).
- Автономных фоновых LLM-задач в MVP нет: агент меняет что-либо только по команде; фоновым может быть лишь детект изменений по хэшам.

## Domain context
- В проектных организациях исходные данные (задания смежных отделов, ТУ, письма заказчика, изыскания) хранятся в структурированных папках на файловых серверах; форматы — PDF (часто сканы), DOCX, XLSX. Документы первых внедрений — преимущественно русскоязычные: OCR и поиск обязаны хорошо работать с русским; кросс-языковые запросы — ценность для международной перспективы.
- Задания приходят новыми редакциями; пропущенное изменение — типовой источник проектных ошибок. Отсюда особый вес детекта изменений и провенанса (какая редакция, откуда взято).
- Vendor-независимость LLM обязательна: у организаций бывают закрытые контуры. MVP работает на облачных моделях (LLM и эмбеддинги — в контуре моделей пока нет); при переходе в контур эмбеддинг-индексы пересоздаются — осознанно принятая цена миграции.
- Ядро — hermes-agent (MIT, NousResearch): даёт harness, skills, MCP, субагентов, память и vendor-agnostic подключение моделей. AECPilot ядро **не форкает**: интеграция через его gateway-API (tui_gateway), расширение — свои skills и MCP-серверы (переносимый слой).
