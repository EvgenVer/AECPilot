# specs/agent-sessions.md — сессии, профили, палитра команд, YOLO

> Контракт поведения для батча 5 фазы 1.6. Ссылается на `SPECIFICATION.md`
> (UR10 — hub «Агент», UR13 — паритет с ядром), не копирует его. Каждый факт о
> ядре подписан источником: файл + функция установленного пакета hermes 0.19.0.
> Факты с пометкой **ИЗМЕРЕНО** сняты живой пробой `runtime/sessions-probe.mjs`
> (задача 1.6.B5.1), остальные прочитаны в коде — разница существенна и потому
> проставлена по месту.

## Что это за поверхности

Пять поверхностей, объединённые одним предметом — «какой разговор идёт и на
чём он идёт»:

- **Сессии** (раздел hub «Агент») — список разговоров текущего проекта,
  переключение, переименование, удаление, ветвление, параллельные живые сессии.
- **Детали сессии** — расход токенов, разбор контекста, сжатие, отмена хода.
- **Палитра команд** (Ctrl+K) — единая точка входа к командам ядра, сессиям и
  экранам оболочки.
- **YOLO** — молния в статус-баре: обход одобрений в пределах текущей сессии.
- **Профили** — где физически живут данные агента (единственная поверхность
  батча на REST, см. §Профили).

## Факты о ядре, определившие форму экранов

Одиннадцать фактов. Они меняют не оформление, а состав работ, поэтому стоят
выше сценариев.

1. **В строках `session.list` нет `cwd`.** **ИЗМЕРЕНО:** полей ровно шесть —
   `id, message_count, preview, source, started_at, title`. Значит скоупить
   сессии по проекту силами шлюза нельзя, и наша собственная привязка
   (`main/session-projects.ts`, задача 1.20) остаётся обязательной, а не
   временной.

2. **`session.active_list` богаче `session.list`** и отвечает про другое: не
   про историю в БД, а про живые сессии этого процесса шлюза
   (`_session_live_item`). **ИЗМЕРЕНО:** `current, id, last_active,
   message_count, model, preview, session_key, started_at, status, title`.
   Для группы «живые сейчас» это единственный источник: в `session.list` нет ни
   `status`, ни признака текущей.

3. **Поиска по сессиям в ядре нет вообще** — ни RPC, ни параметра у
   `session.list` (кроме `limit`). Поиск может быть только клиентский и только
   по тому, что уже пришло: `title` и `preview`. По телу сообщений он не идёт,
   и интерфейс обязан это сказать (§Поиск).

4. **Архива сессий нет** — ни RPC, ни поля наружу; решение владельца B5-2:
   архива не делаем, как у донора. Остаётся `session.delete`, а он необратим
   (`db.delete_session` + удаление файлов транскрипта, `tui_gateway/server.py`).

5. **`session.title` адресует ЖИВУЮ сессию, а не строку БД.** Обработчик
   резолвит сессию через `_sess_nowait`, то есть по live-sid из `_sessions`.
   Переименовать сессию, которая сейчас не поднята, одним вызовом нельзя — её
   надо сначала `session.resume`. Ответ: `{pending, title}`; `pending:true`
   означает, что строки в БД ещё нет и имя применится после первого сообщения —
   это не ошибка.

6. **`session.delete` отказывается удалять активную сессию** — код 4023
   «cannot delete an active session»; проверка идёт по `session_key` всех живых
   сессий процесса, а не только нашей.

7. **`session.branch` не отдаёт stored-id новой сессии.** Ответ —
   `{session_id, title, parent}`, где `session_id` это НОВЫЙ live-sid, а
   `parent` — stored-ключ РОДИТЕЛЯ. Метку проекта вешать не на что, поэтому
   stored-ключ ветки дочитывается из `session.active_list` по её live-sid (поле
   `session_key`, факт 2). На пустой сессии ветвление отклоняется — **ИЗМЕРЕНО:**
   4008 «nothing to branch — send a message first».

8. **`session.undo` снимает ход из памяти шлюза и не переписывает БД.**
   Обработчик срезает хвост `session["history"]` и увеличивает
   `history_version`; вызова `db.replace_messages` в нём нет — при следующем
   `resume` отменённый ход вернётся. Прочитано в коде, **пробой НЕ подтверждено**
   (на сессии без ходов отменять нечего): проба это честно печатает, и
   интерфейс обязан говорить о снятии хода как о временном. Во время хода —
   отказ 4009. Решение владельца B5-3: снимаем ровно `removed` элементов и
   пишем подсказку.

9. **`session.compress` отдаёт СЫРУЮ историю, а не ту форму, что `resume`.**
   `resume`/`history` прогоняют историю через `_history_to_messages`
   (`{role, text, name, context}`), а `compress` кладёт в `messages`
   внутренний список агента (`{role, content, tool_calls…}`). Перерисовывать
   ленту его ответом нельзя — она приедет пустой. Поэтому после успешного
   сжатия лента перечитывается вызовом `session.history`, а из ответа
   `compress` берутся только числа: `before_messages`, `after_messages`,
   `before_tokens`, `after_tokens`, `status`. Во время хода — отказ 4009.

10. **Индикатор сжатия приходит ДВУМЯ разными `kind`, а не одним.**
    `_status_update` (`tui_gateway/server.py`): ручное сжатие эмитит
    `status.update {kind:"compressing"}` и по завершении — `{kind:"status",
    text:"ready"}`; автоматическая компакция мид-хода приезжает как
    `lifecycle` и ПЕРЕТЕГИВАЕТСЯ в `{kind:"compacting"}` их же кодом.
    Задача 1.6.B5.14 названа по второму; реализуются оба, иначе ручное сжатие
    останется без индикатора.

11. **`config.set {key:"yolo"}` имеет два скоупа, и глобальный пишет мимо нас.**
    `scope:"session"` (умолчание) трогает только флаг живой сессии;
    `scope:"global"` переписывает `approvals.mode` в `config.yaml` значениями
    `off`/`manual`. Наш селектор режимов (задача 0.17) знает три режима, включая
    `smart`, — глобальный скоуп его молча потерял бы. Решение владельца B5-5=A:
    глобальный скоуп из интерфейса недостижим. Ещё одна причина: **без живой
    сессии** их обработчик уходит в ветку `os.environ["HERMES_YOLO_MODE"]`, то
    есть переключает переменную окружения всего процесса шлюза.

Плюс два факта про композер, пришедшие с обновлением ядра до 0.19.0:

- **`prompt.submit` больше не отклоняет сообщение во время хода.** До 0.18.0
  ответом было «session busy», и очередь держал клиент (наша задача 1.6.8).
  С 0.19.0 `_handle_busy_submit` применяет их политику `display.busy_input_mode`
  и отвечает `queued` / `steered` / `streaming`. То есть **все три режима уже
  реализованы ядром**, и наша локальная очередь стала вторым механизмом поверх
  первого.
- **`prompt.submit {truncate_before_user_ordinal}`** обрезает историю до
  N-го сообщения ПОЛЬЗОВАТЕЛЯ (нумерация только по ним) и переписывает БД
  (`db.replace_messages`). Их обработчик отвергает и отрицательные, и слишком
  большие ordinal кодом 4018 — без этой проверки отрицательный индекс молча
  срезал бы историю до последнего хода.

## Сценарии

### Список сессий

**Сценарий: список показывает сессии текущего проекта**
- Дано: открыт проект, в нём есть сессии
- Когда: пользователь открывает раздел «Сессии» в hub «Агент»
- Тогда: показаны только сессии, помеченные этим проектом
- И: у каждой видно имя (или превью), число сообщений и время начала

**Сценарий (негативный): сессия чужого проекта не показывается**
- Дано: в шлюзе есть сессия, помеченная другим проектом
- Когда: раздел открыт
- Тогда: этой строки в списке нет
- И: фильтрация выполняется в main тем же `sessionIdsForProject`, что и у
  селектора сессий, — второй копии правила не появляется

**Сценарий: пустой список объясняет себя**
- Дано: в проекте ещё не было ни одной сессии
- Когда: раздел открыт
- Тогда: сказано, что сессия появится после первого сообщения, а не показан
  пустой блок

### Переключение и удаление

**Сценарий: переключение на другую сессию**
- Когда: пользователь выбирает сессию из списка
- Тогда: уходит `session.resume`, лента перерисовывается из `messages` ответа
- И: активной становится сессия с live-sid ИЗ ОТВЕТА, а не тот id, который
  запрашивали (шлюз выдаёт новый live-sid)

**Сценарий: удаление сессии**
- Когда: пользователь удаляет сессию и подтверждает
- Тогда: подтверждение говорит, что удаление необратимо и стирает транскрипт
- И: подтверждение проверяется в main — без него запрос не уходит
- И: после успеха строка исчезает из списка

**Сценарий (негативный): активную сессию удалить нельзя**
- Когда: `session.delete` отвечает 4023
- Тогда: показан текст шлюза («сессия активна»)
- И: строка остаётся в списке — исчезнувшая строка соврала бы об удалении

### Поиск

**Сценарий: поиск по имени и превью**
- Дано: список сессий загружен
- Когда: пользователь вводит подстроку
- Тогда: остаются строки, у которых подстрока встречается в `title` или
  `preview`, регистр не важен

**Сценарий (негативный): ничего не найдено**
- Когда: выдача пуста
- Тогда: показано, что поиск идёт по имени и превью, а по тексту сообщений
  ядро искать не умеет (факт 3) — а не «ничего не найдено»

### Переименование

**Сценарий: переименование поднятой сессии**
- Дано: сессия сейчас активна
- Когда: пользователь задаёт новое имя
- Тогда: уходит `session.title {title}`, имя в списке меняется

**Сценарий: переименование неподнятой сессии**
- Дано: сессия есть в списке, но не поднята
- Когда: пользователь задаёт новое имя
- Тогда: сначала уходит `session.resume`, затем `session.title` — по факту 5
  иначе шлюз не найдёт сессию

**Сценарий: имя применится позже**
- Когда: ответ `{pending:true}`
- Тогда: показано «имя применится после первого сообщения», а не ошибка

**Сценарий (негативный): пустое имя**
- Когда: пользователь оставляет поле пустым
- Тогда: запрос не уходит (шлюз ответил бы 4021)

### Событие `session.title`

**Сценарий: заголовок обновился сам**
- Когда: приходит событие с `{session_id, title}`
- Тогда: меняется заголовок ровно той строки, которой он адресован
- И: событие перестаёт числиться «неизвестным»

### Параллельные сессии

**Сценарий: живые сессии видны отдельной группой**
- Когда: раздел открыт
- Тогда: живые сессии (`session.active_list`) показаны отдельно от
  исторических, у каждой виден статус и модель
- И: текущая помечена по полю `current`

**Сценарий: переключение между живыми сессиями**
- Когда: пользователь выбирает другую живую сессию
- Тогда: уходит `session.activate`, лента перерисовывается из `messages`
- И: прежняя сессия НЕ закрывается — она остаётся в группе живых

### Ветвление

**Сценарий: ветвление текущей сессии**
- Дано: в сессии есть хотя бы один ход
- Когда: пользователь ветвит сессию
- Тогда: уходит `session.branch`, новая сессия становится активной
- И: прежняя остаётся в списке живых
- И: новая сессия получает метку текущего проекта — её stored-ключ дочитывается
  из `session.active_list` (факт 7)

**Сценарий (негативный): ветвить нечего**
- Дано: в сессии нет ни одного хода
- Когда: раздел открыт
- Тогда: кнопка ветвления недоступна — иначе шлюз ответит 4008

### Детали сессии

**Сценарий: расход токенов**
- Когда: пользователь открывает «Детали сессии»
- Тогда: показаны вход, выход, размышления и число вызовов из `session.usage`

**Сценарий (негативный): заполненность контекста неизвестна**
- Когда: в ответе нет `context_used`/`context_max`
- Тогда: показано «неизвестно», а не 0 % — ядро опускает эти поля именно тогда,
  когда занятость окна ему неизвестна

**Сценарий: блок кредитов**
- Когда: `credits_lines` пуст или отсутствует
- Тогда: блок не показывается вовсе

**Сценарий: разбор контекста**
- Когда: пользователь открывает разбор контекста
- Тогда: показаны категории с числом токенов и долей
- И: поле `color` из ответа НЕ используется — это переменная их дизайн-системы;
  цвет берётся из наших токенов

**Сценарий (негативный): агент ещё не собран**
- Когда: `categories` пуст
- Тогда: сказано, что агент ещё не собран, а не показан пустой список

### Сжатие контекста

**Сценарий: ручное сжатие**
- Когда: пользователь запускает сжатие
- Тогда: после ответа лента перечитывается через `session.history` (факт 9)
- И: итог показывает было→стало по сообщениям и по токенам

**Сценарий (негативный): сжатие во время хода**
- Дано: идёт ход
- Тогда: кнопка сжатия недоступна — отказ 4009 не показывается пользователю как
  ошибка, потому что до него не доходит

**Сценарий: индикатор сжатия**
- Когда: приходит `status.update` с `kind:"compressing"` или `kind:"compacting"`
- Тогда: в статус-баре виден индикатор
- Когда: приходит `{kind:"status"}` («ready») или ход завершается
- Тогда: индикатор снимается
- И: `status.update` с другими `kind` (например `process`) по-прежнему ничего
  не меняет и не шумит

### Отмена хода

**Сценарий: отмена последнего хода**
- Когда: пользователь отменяет ход
- Тогда: из ленты снимается ровно `removed` последних элементов, считая
  карточки инструментов
- И: подсказка говорит, что запись в истории шлюза остаётся и вернётся при
  переоткрытии сессии (факт 8)

**Сценарий (негативный): отмена во время хода**
- Дано: идёт ход
- Тогда: кнопка отмены недоступна

### Подруливание

**Сценарий: подсказка агенту во время хода**
- Дано: идёт ход
- Когда: пользователь отправляет подсказку
- Тогда: уходит `session.steer {text}`
- И: ответ `{status:"queued"}` показан как принятая заметка
- И: ответ `{status:"rejected"}` показан как «агент не принял подсказку»

**Сценарий (негативный): агент не умеет steer**
- Когда: шлюз отвечает 4010
- Тогда: сообщение показано один раз, а элемент управления гаснет до конца
  сессии — повторять отказ на каждую попытку бессмысленно

### Композер во время хода

**Сценарий: сообщение во время хода уходит сразу**
- Дано: идёт ход
- Когда: пользователь отправляет сообщение
- Тогда: оно уходит `prompt.submit` немедленно, без локальной очереди
- И: ответ `queued` показан как «уйдёт следующим ходом», `steered` — как
  «влито в идущий ход», и оба считаются успехом, а не отказом

**Сценарий: режим занятости выбирает пользователь**
- Дано: в настройках «Поведение агента» выбран один из трёх режимов
- Тогда: политику применяет ядро (`display.busy_input_mode`), а приложение
  только показывает, что произошло
- И: неизвестное значение из `config.get` читается как `queue`, а не как
  `interrupt`

### Правка своего сообщения

**Сценарий: правка с перезапуском хода**
- Когда: пользователь правит своё сообщение и отправляет заново
- Тогда: уходит `prompt.submit {truncate_before_user_ordinal}` с порядковым
  номером ЭТОГО сообщения среди сообщений пользователя
- И: лента обрезается до него

**Сценарий (негативный): сообщения больше нет в истории**
- Когда: шлюз отвечает 4018
- Тогда: показан текст шлюза, лента не трогается

### Палитра команд

**Сценарий: открытие и закрытие**
- Когда: пользователь нажимает Ctrl+K
- Тогда: открывается оверлей палитры, фокус в поле ввода
- Когда: пользователь нажимает Ctrl+K ещё раз или Esc
- Тогда: палитра закрывается, фокус возвращается туда, откуда её открыли
- И: пока палитра закрыта, она не перехватывает никаких других клавиш

**Сценарий: наполнение палитры**
- Когда: палитра открыта
- Тогда: показаны команды ядра из `commands.catalog` (секции в порядке
  `categories`), сессии текущего проекта и экраны оболочки
- И: алиас из `canon` находит каноническую команду
- И: `warning` из ответа показан строкой, а не потерян молча

**Сценарий: запуск команды**
- Когда: пользователь выбирает команду
- Тогда: уходит `command.dispatch`, и результат разбирается по `type`:
  `send` — отправляется тем же путём, что текст композера; `exec` и `plugin` —
  показывается вывод; `skill` — отправляется собранное сообщение; `alias` —
  подставляется целевая команда

**Сценарий (негативный): неизвестный тип ответа**
- Когда: `type` не из пяти известных
- Тогда: показана ошибка с названием пришедшего типа
- И: НИЧЕГО не отправляется

### YOLO

**Сценарий: состояние молнии**
- Когда: приходит `session.info` с `yolo`
- Тогда: молния показывает именно это состояние — локального «включено» у
  приложения нет

**Сценарий: переключение**
- Когда: пользователь нажимает молнию
- Тогда: уходит `config.set {key:"yolo", value:"1"|"0"}` БЕЗ `scope:"global"`
- И: значение передаётся явными `'1'`/`'0'`, а не пустой строкой — на пустой
  строке их обработчик инвертирует текущее

**Сценарий (негативный): нет живой сессии**
- Когда: сессия не поднята
- Тогда: молния недоступна — иначе шлюз переключит переменную окружения всего
  процесса (факт 11)

**Сценарий (негативный): глобальный скоуп недостижим**
- Тогда: из интерфейса нет способа отправить `scope:"global"`
- И: наш селектор режимов одобрений остаётся единственным владельцем
  постоянной настройки, режим «умный» сохраняется

### Профили

Единственная поверхность батча на REST — решение владельца B5-1=C, разрешено
правилом R1 («REST точечно, там где RPC не дотягивается»): методов `profile.*`
в шлюзе нет вообще, а `/api/profiles*` отдаёт тот же наш процесс.

**Сценарий: список профилей**
- Когда: пользователь открывает «Профили»
- Тогда: показан список из `GET /api/profiles` с пометкой активного
  (`GET /api/profiles/active`)

**Сценарий: создание профиля**
- Когда: пользователь создаёт профиль с именем
- Тогда: уходит `POST /api/profiles`, список перечитывается

**Сценарий: переключение профиля**
- Когда: пользователь выбирает другой профиль
- Тогда: он передаётся параметром `profile` в `session.create`/`session.resume`
- И: сказано, что уже запущенный процесс ядра на другой профиль не
  переезжает — `POST /api/profiles/active` меняет только «липкий» профиль для
  будущих запусков (их собственный комментарий в `web_server.py`)

**Сценарий (негативный): удаление активного профиля**
- Когда: пользователь пытается удалить активный профиль
- Тогда: удаление отклоняется приложением, до REST дело не доходит

**Сценарий: удаление профиля**
- Когда: пользователь удаляет неактивный профиль и подтверждает
- Тогда: подтверждение проверяется в main, уходит `DELETE /api/profiles/{name}`

## Non-goals

- **Архив сессий** — решение B5-2: у донора его нет ни в движке, ни в десктопе;
  своя локальная метка завела бы второй источник правды о жизненном цикле
  сессии. Есть удаление, и оно честно называет свою цену.
- **Поиск по телу сообщений** — ядро такого не отдаёт (факт 3); собственный
  индекс транскриптов в батч 5 не входит.
- **Русские подписи команд палитры** — решение B5-4: палитра остаётся
  английской, как отдаёт ядро; ноль расхождений при обновлении ядра.
- **Глобальный скоуп YOLO** — решение B5-5=A (факт 11).
- **Кнопка «снять все процессы»** — решение R8, повторено здесь, потому что
  соседство с деталями сессии делает её соблазнительной.
- **Локальная очередь композера** — снимается задачей 1.6.B5.26: ядро с 0.19.0
  реализует все три режима само, дублирующая очередь была бы вторым механизмом
  поверх первого.
- **Переезд сессий между профилями** — их REST такого не предлагает, а копирование
  строк БД мимо их кода мы не делаем.
