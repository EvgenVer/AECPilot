# specs/agent-skills.md — скилы, обучение, куратор

> Контракт поведения для батча 3 фазы 1.6. Ссылается на `SPECIFICATION.md`
> (UR10 — hub «Агент»), не копирует его. Каждый факт о поведении ядра подписан
> источником: файл + функция установленного пакета hermes 0.18.0, а факты,
> помеченные **ИЗМЕРЕНО**, сняты живой пробой `runtime/skills-probe.mjs`
> (задача 1.6.B3.1), а не чтением кода.

## Что это за экраны

Два экрана в hub «Агент»:

- **Скилы** — что агент умеет сверх базовой поставки: список по категориям,
  просмотр и правка `SKILL.md`, архивирование, перечитывание с диска.
- **Обучение** — чему агент научился со временем: узлы (скилы и записи памяти)
  на шкале времени, раскрытие узла до содержимого.

Плюс одно системное сообщение в ленте чата, когда агент сохранил новый скил или
запись памяти.

## Факты о ядре, определившие форму экранов

Пять фактов, три из них — находки пробы. Они меняют не оформление, а состав
работ, поэтому стоят выше сценариев.

1. **`skills.manage {action:'list'}` отдаёт только имена.** `get_available_skills`
   (`hermes_cli/banner.py`) возвращает `{категория: [имена]}` — ни описания, ни
   признака «включён», ни пути. **ИЗМЕРЕНО:** ключ ответа один — `skills`.
   Богаче отвечает REST того же процесса: `GET /api/skills`
   (`hermes_cli/web_server.py:get_skills`) — **ИЗМЕРЕНО:** массив со списком
   полей `name, description, category, enabled`. Экран берёт список оттуда;
   решение R1 разрешает REST ровно там, где RPC не дотягивается.

2. **Куратор недостижим через `command.dispatch`.** **ИЗМЕРЕНО:**
   `command.dispatch {name:'curator', arg:'status'}` → ошибка 4018 «not a
   quick/plugin/skill command: curator». Их `_handle_curator_command` живёт в
   CLI-миксине (`hermes_cli/cli_commands_mixin.py`), диспетчер шлюза его не
   резолвит. Состояние куратора приходит из `GET /api/curator` — **ИЗМЕРЕНО:**
   `enabled, paused, interval_hours, last_run_at, min_idle_hours,
   stale_after_days, archive_after_days`.

3. **Списка архива нет нигде.** Ни RPC, ни REST-маршрута, отдающего
   заархивированные скилы, в сборке нет; архив живёт в `tools/skill_usage.py`
   и доступен только их CLI. Поэтому экран архива **не делается**, а
   архивирование честно говорит, чем восстанавливать (`hermes curator restore
   <name>`) — см. §Non-goals.

4. **`learning.frames` на Windows не работает.** **ИЗМЕРЕНО:** ошибка 5000
   «learning.frames failed: Invalid format string». Корень найден по коду:
   `agent/learning_graph_render.py:_period_label` зовёт `strftime("%-d %b")`, а
   `%-d` — расширение glibc, которого нет в Windows CRT; в `format_date` эта
   ошибка поймана, в `_period_label` — нет. Структурные данные того же графа
   отдаёт `GET /api/learning/graph` (`build_learning_graph`, без единого
   `strftime`) — **ИЗМЕРЕНО:** 200 и ключи `nodes, edges, clusters, memory,
   stats`. Экран «Обучение» строится на нём. Это совпадает с исходным замыслом
   задачи 1.6.B3.10 («ASCII-часть игнорируется»), просто источник другой.

5. **`learning.detail`/`edit`/`delete` не бросают на ошибку.**
   `agent/learning_mutations.py` ловит `ValueError`/`IndexError` и возвращает
   `{ok:false, message}` — **ИЗМЕРЕНО** на несуществующем скиле и на
   несуществующем узле памяти. То есть отказ приходит как успешный ответ RPC, и
   UI обязан читать `ok`, а не полагаться на отсутствие ошибки.

Ещё два факта из их кода, влияющих на тексты:

- **Скил архивируется, память удаляется.** `_delete_skill` зовёт
  `skill_usage.archive_skill` и возвращает подсказку «restore with: hermes
  curator restore <name>»; `_delete_memory` физически вырезает кусок из файла
  памяти (`agent/learning_mutations.py`). Последствия разные, значит и
  подтверждения разные.
- **Закреплённый скил не архивируется.** `_delete_skill` отвечает
  `{ok:false, message:"'X' is pinned — unpin it first (hermes curator unpin X)"}`.

## Сценарии

### Список скилов

**Сценарий: список показывает скилы по категориям**
- Дано: профиль, в котором есть хотя бы один скил
- Когда: пользователь открывает раздел «Скилы» в hub «Агент»
- Тогда: скилы сгруппированы по категориям, у каждого видно имя и описание
- И: рядом с заголовком видно общее число скилов

**Сценарий: пустой список объясняет себя**
- Дано: профиль без скилов
- Когда: раздел открыт
- Тогда: показан текст «агент пока ничему не научился» с пояснением, откуда
  берутся скилы
- И: пустого блока без объяснения не показывается

**Сценарий: состояние «включён/выключен» видно, но не редактируется**
- Дано: скил, выключенный в `skills.disabled`
- Когда: раздел открыт
- Тогда: скил показан с пометкой «выключен»
- И: переключателя нет — решение владельца B3-2 («экран только показывает»)

### Перечитывание

**Сценарий: перечитывание сообщает, что изменилось**
- Дано: раздел «Скилы» открыт
- Когда: пользователь нажимает «Перечитать скилы»
- Тогда: показан итог — сколько добавлено, сколько удалено, сколько всего
- И: список перерисован

**Сценарий (негативный): перечитывание не удалось**
- Когда: `skills.reload` отвечает ошибкой 5025
- Тогда: показан текст ошибки шлюза
- И: прежний список остаётся на экране

### Просмотр и правка

**Сценарий: просмотр SKILL.md**
- Когда: пользователь раскрывает карточку скила
- Тогда: показано содержимое `SKILL.md` как текст
- И: markdown не исполняется как HTML

**Сценарий (негативный): содержимое недоступно**
- Когда: `learning.detail` отвечает `{ok:false, message}`
- Тогда: показано сообщение шлюза
- И: пустое тело не рисуется (иначе читается как «скил пустой»)

**Сценарий: правка скила**
- Дано: содержимое скила открыто на просмотр
- Когда: пользователь правит текст и нажимает «Сохранить»
- Тогда: сначала запрашивается подтверждение
- И: подтверждение проверяется в main-процессе — без него запрос не уходит
- И: после успеха содержимое перечитывается с диска

**Сценарий (негативный): правка отклонена**
- Когда: `learning.edit` отвечает `{ok:false}`
- Тогда: текст в редакторе НЕ теряется
- И: показано сообщение шлюза

### Архивирование и удаление памяти

**Сценарий: подтверждения называют разные последствия**
- Когда: пользователь архивирует скил
- Тогда: подтверждение говорит «в архив, восстановить можно командой `hermes
  curator restore <имя>`»
- Когда: пользователь удаляет узел памяти
- Тогда: подтверждение говорит «удалится безвозвратно»

**Сценарий (негативный): закреплённый скил не архивируется**
- Когда: `learning.delete` отвечает `{ok:false, message:"… is pinned …"}`
- Тогда: сообщение показано как есть
- И: список не меняется

### Обучение

**Сценарий: таймлайн обучения**
- Дано: в профиле есть выученные скилы или записи памяти
- Когда: пользователь открывает раздел «Обучение»
- Тогда: узлы сгруппированы по датам, у каждой группы видно число скилов и
  памятей

**Сценарий: раскрытие узла**
- Когда: пользователь раскрывает узел памяти
- Тогда: тело записи показано без обращения к шлюзу (оно уже в графе)
- Когда: пользователь раскрывает узел скила
- Тогда: содержимое запрашивается через `learning.detail` ровно один раз

**Сценарий (негативный): графа нет**
- Когда: `GET /api/learning/graph` отвечает пустым списком узлов
- Тогда: показан текст «агент пока ничему не научился»

**Сценарий (негативный): REST недоступен**
- Дано: приложение подключено к внешнему шлюзу (e2e-режим)
- Когда: раздел открыт
- Тогда: показано, что интерфейс ядра недоступен, а не пустой экран

### Куратор

**Сценарий: честная плашка о кураторе**
- Когда: раздел «Скилы» открыт
- Тогда: видна плашка, что под `hermes serve` фоновый куратор не запускается и
  автоархивации по простою не происходит
- И: плашка видна независимо от того, что ответил `GET /api/curator`
- И: если состояние получено, названы фактические пороги (интервал, простой,
  срок архивации) — чтобы было видно, ЧТО именно не происходит

### Обучение в ленте чата

**Сценарий: агент сохранил скил**
- Когда: приходит событие `review.summary`
- Тогда: в ленте появляется постоянное системное сообщение о сохранённом
  скиле/памяти
- И: оно не исчезает после `message.complete` (в отличие от тоста)

### Запуск обучения из интерфейса

**Сценарий: `/learn` кнопкой**
- Когда: пользователь нажимает «Научить агента» и вводит тему
- Тогда: `command.dispatch {name:'learn'}` возвращает `{type:'send', message}`
- И: сообщение уходит тем же путём, что текст композера
- Когда: ответ имеет другой `type`
- Тогда: ничего не отправляется, показана ошибка

## Non-goals

- **Хаб скилов** (поиск/установка чужих скилов) — решение владельца B3-3:
  отложено в Phase 4+, установка чужого исполняемого кода одним нажатием сейчас
  не делается. Методы `skills.manage search|browse|install` работают
  (**ИЗМЕРЕНО**), но интерфейса к ним нет.
- **Экран архива скилов** — списка архива нет ни в RPC, ни в REST (факт 3).
  Восстановление возможно их CLI, и подтверждение архивации прямо называет
  команду.
- **Правка записей памяти** — решение владельца B3-4: память только
  показываем, правка приедет в фазе 4 вместе с новой спекой памяти. Удаление
  узла памяти при этом доступно (оно не требует новой модели памяти).
- **Выключение скилов** — решение владельца B3-2: экран только показывает.
  **Поправка по факту:** REST-маршрут `PUT /api/skills/toggle` существует и
  решению R3 («всё новое — только через их API») не противоречит; исходная
  посылка решения B3-2 («RPC нет, значит осталась бы прямая правка
  config.yaml») оказалась неверной. Решение оставлено в силе как решение
  владельца; переоткрывать его — его право.
- **Тик куратора нашими силами** — решение B3-1=A: оставляем как есть, честно
  говорим, что автоархивации нет.
