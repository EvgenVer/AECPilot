## Назначение и границы
- UR14: перед записью в файл и перед разрушительной командой ядро снимает состояние
  рабочей директории в отдельное теневое хранилище; пользователь видит список
  снимков, различия и может вернуть состояние.
- **Свой `.git` пользователя не затрагивается — гарантия обеспечена несколькими
  независимыми механизмами (все проверены по исходникам/тестам ядра):**
  1. Снимки живут в ОТДЕЛЬНОМ хранилище `<HERMES_HOME>/checkpoints/store/` — одном
     общем bare-репозитории на все проекты пользователя, а не внутри рабочей
     директории. В нашей сборке `HERMES_HOME` = `runtime/dev-profile`
     (`runtime/hermes-env.mjs`, `HERMES_HOME_DIR`), в проде — аналогичный
     изолированный профиль. Внутри самой рабочей директории `.git` не создаётся
     никогда — подтверждено тестом `test_no_git_in_project_dir`
     (`tests/tools/test_checkpoint_manager.py`).
  2. Все git-операции теневого хранилища явно перенаправлены переменными окружения
     `GIT_DIR`, `GIT_WORK_TREE` (= рабочая директория) и `GIT_INDEX_FILE` (свой индекс
     на проект) — функция `_git_env` в `tools/checkpoint_manager.py`. Git физически не
     смотрит на `<рабочая директория>/.git`, даже если он там есть.
  3. Хранилище не читает пользовательский `~/.gitconfig`/системный git-конфиг
     (`GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM=os.devnull`, `GIT_CONFIG_NOSYSTEM=1`,
     `commit.gpgsign=false`) — снимки не запускают пользовательские git-хуки и не
     всплывают GUI-подтверждения gpg (тест
     `test_checkpoint_works_with_global_gpgsign_and_broken_gpg`).
  4. `info/exclude` теневого хранилища явно исключает `.git/`/`.hg/`/`.svn/` из
     сканирования — даже если внутри рабочей директории окажется настоящий `.git`,
     его содержимое не попадёт в снимок.
- **Поправка к формулировке UR14 «снимает состояние рабочей директории» — фактический
  охват снимка ýже, чем «весь vault».** Ядро определяет «рабочую директорию» для
  каждой правки функцией `get_working_dir_for_path` (`tools/checkpoint_manager.py`):
  от папки правимого файла оно поднимается вверх и ищет один из девяти маркеров —
  `.git`, `pyproject.toml`, `package.json`, `Cargo.toml`, `go.mod`, `Makefile`,
  `pom.xml`, `.hg`, `Gemfile`. Если маркер найден — снимается директория с маркером;
  если нет ни одного до самого корня диска — **снимается только непосредственная
  директория правимого файла** (подтверждено тестом `test_falls_back_to_parent`).
  Список маркеров зашит в код и не настраивается: конструктор `CheckpointManager`
  принимает только `enabled/max_snapshots/max_total_size_mb/max_file_size_mb`
  (вызов — `agent/agent_init.py:1180-1185`).
  Наш vault (`specs/workspace-sources.md` §Data schemas: `wiki/`, `workspace/`,
  `templates/`, `.aecpilot/`, `AGENTS.md`) по умолчанию не содержит ни одного из
  девяти маркеров. Следствие: правка файла в `<vault>/wiki/…` или
  `<vault>/workspace/…` снимается как директория `<vault>/wiki` или
  `<vault>/workspace/…` — НЕ как весь `<vault>`. Это напрямую определяет, что увидит
  `rollback.list` — см. Open questions №1 (блокирующий вопрос для 1.6.C1/1.6.C2).
- Хранилище одно на пользователя (профиль), а не одно на проект: git-объекты
  дедуплицируются между всеми проектами, поэтому лимит `max_total_size_mb` —
  суммарный по ВСЕМ проектам пользователя, а не по одному vault (см. «Лимиты и
  уборка»).

## Что снимается и когда
Снимок берётся ДО выполнения операции (preflight), не после (оба места вызова
`ensure_checkpoint` в `agent/tool_executor.py` стоят перед исполнением инструмента):
- Файловые инструменты `write_file` и `patch` — причина снимка записывается как
  `"before write_file"` / `"before patch"`.
- Терминальная команда — только если она распознана как деструктивная по регэкспам
  `_DESTRUCTIVE_PATTERNS`/`_REDIRECT_OVERWRITE` (`agent/tool_dispatch_helpers.py`):
  `rm`, `rmdir`, `cp`, `install`, `mv`, `sed -i`, `truncate`, `dd`, `shred`,
  `git reset`/`clean`/`checkout`, и перезаписывающий редирект `>` (не `>>`). Причина —
  `"before terminal: <команда, обрезана до 60 символов>"`.
- **Не более одного снимка на директорию за один ход агента** — `new_turn()` сбрасывает
  дедуп-множество в начале хода, повторно та же директория в этом ходе не снимается
  (тест `test_dedup_same_turn`).
- Снимок пропускается (не создаётся), если: чекпойнты выключены; `git` не найден в
  PATH; директория — корень диска или домашняя папка; в директории больше 50 000
  файлов; с прошлого снимка в директории нет изменений (`git diff-index --quiet`).
- Восстановление (`rollback.restore`) само, ДО того как что-то менять на диске, берёт
  дополнительный снимок текущего состояния с причиной `"pre-rollback snapshot
  (restoring to <hash>)"` — встроенная страховка «отменить отмену», работает
  независимо от нашего UI (`CheckpointManager.restore`, тест
  `test_restore_creates_pre_rollback_snapshot`).
- Из снимка исключены (`info/exclude` теневого репозитория = `DEFAULT_EXCLUDES` в
  `tools/checkpoint_manager.py`): служебные каталоги разработки (`node_modules/`,
  `.venv/`, `__pycache__/` и т.п., для AEC-vault нерелевантны), файлы секретов
  `.env`/`.env.*`/`.env.local`, и в частности **`*.log`** — то есть
  `.aecpilot/logs/*.log` в снимок не попадает. Отдельный файл больше
  `max_file_size_mb` из снимка тоже исключается (см. «Лимиты и уборка»).

## Лимиты и уборка
Значения по умолчанию — из SPECIFICATION.md (UR14, решение владельца 2026-07-28):
«20 снимков на проект, общий потолок 500 МБ, проекты без обращений 7 дней
вычищаются». Сверено по исходникам — совпадает буквально с дефолтами ядра
(`CheckpointManager.__init__` и функция, которую вызывает `tui_gateway`,
`agent/agent_init.py:233-236`), а также с документированными дефолтами `checkpoints:`
в `website/docs/user-guide/checkpoints-and-rollback.md`:

| Параметр | Дефолт | Где реально применяется |
|---|---|---|
| `enabled` | `false` | ворота на каждый вызов `ensure_checkpoint` |
| `max_snapshots` | 20 на «рабочую директорию» (см. правило выше) | живо, при каждом успешном снимке — реальный rewrite ref + `git gc --prune=now` (`_prune`) |
| `max_total_size_mb` | 500, **общий на ВСЕ проекты пользователя** (одно хранилище) | живо, при каждом успешном снимке (`_enforce_size_cap`) — при превышении из каждого проекта по очереди вычищается самый старый снимок |
| `max_file_size_mb` | 10 — отдельный файл больше не входит в снимок | живо, при каждом снимке (`_drop_oversize_from_index`) |
| `retention_days` | 7 — «рабочие директории» без обращения дольше этого срока вычищаются целиком | **только через `maybe_auto_prune_checkpoints`, который вызывается лишь из их интерактивного CLI (`cli.py`) — см. Open questions №3** |

**Уточнение к записи PLAN §Phase 1.6 «поправка 5» («функция доступна нам „по
проводам“ сразу, как только включим флаг»).** В пути `tui_gateway` (наша интеграция —
SPECIFICATION.md C1) флаг `checkpoints.enabled` из `~/.hermes/config.yaml` НЕ
читается вовсе: включение идёт через переменную окружения `HERMES_TUI_CHECKPOINTS`
(источник: `tui_gateway/server.py:4383`, `checkpoints_enabled` строится через
`is_truthy_value(os.environ.get("HERMES_TUI_CHECKPOINTS"))`). Три числовых лимита
(`max_snapshots`/`max_total_size_mb`/`max_file_size_mb`) в этом пути вообще не
прокидываются в конструктор агента и молча берутся дефолтами ядра (20/500/10) —
они совпадают с нашими целевыми числами, но это не значит, что их можно изменить
правкой `config.yaml` в этом конкретном пути (см. Open questions №2).

## Behavior (BDD / Gherkin)
Scenario: Просмотр списка снимков
  Given чекпойнты включены и агент хотя бы раз менял файл в рабочей директории
  When пользователь открывает экран отката
  Then показан список снимков, новые сверху (порядок ядра — most recent first)
  And у каждого снимка виден хеш и время создания
  And текстовая причина снимка НЕ гарантированно доступна через `rollback.list` (см.
    Open questions №4) — экран не должен на неё полагаться как на обязательное поле

Scenario: Просмотр различий по снимку
  Given список снимков открыт
  When пользователь выбирает снимок и запрашивает различия
  Then показывается сводка изменений (stat) и построчный diff относительно текущего
    состояния рабочей директории этого снимка

Scenario: Восстановление снимка с подтверждением
  Given пользователь посмотрел различия и решил восстановить снимок N
  When он подтверждает восстановление (подтверждение — наше решение UI; ядро само его
    не запрашивает, только делает свою pre-rollback подстраховку)
  Then файлы рабочей директории приводятся к состоянию снимка N
  And перед этим ядро само создаёт ещё один снимок текущего состояния — «отменить
    отмену» доступна и без нашего вмешательства

Scenario: Отмена восстановления до подтверждения
  Given пользователь открыл диалог восстановления снимка
  When он отменяет, не подтвердив
  Then ничего не меняется ни на диске, ни в истории сессии

Scenario: Восстановление одного файла
  Given у снимка известен путь конкретного файла
  When пользователь восстанавливает только этот файл
  Then меняется только он, остальная рабочая директория не затрагивается
  And история чата не откатывается (в отличие от полного восстановления)

Scenario: Полное восстановление откатывает и последний ход чата
  Given агент только что закончил ход, что-то испортив
  When пользователь делает полное восстановление (без указания файла)
  Then файлы возвращены к снимку
  And из истории сессии удаляются последние сообщения ассистента/инструментов и
    предшествовавшее им сообщение пользователя — контекст агента синхронизирован с
    восстановленными файлами (ядро само «отменяет последний ход диалога»)

Scenario: Попытка полного отката во время незавершённого хода агента (негативный)
  Given агент ещё выполняет текущий ход (сессия «занята»)
  When пользователь запрашивает ПОЛНОЕ восстановление (без указания файла)
  Then запрос отклоняется с понятной причиной («сессию нужно прервать перед полным
    откатом»)
  And восстановление ОДНОГО файла в этой же ситуации не блокируется — это разрешено
    даже во время хода

Scenario: Агент испортил файл → откат вернул (сквозной, приёмка 1.6.C2)
  Given чекпойнты включены, агент правит файл vault и результат неудачный
  When пользователь открывает список снимков, находит снимок «до правки» и
    восстанавливает его
  Then содержимое файла возвращается к состоянию до правки агента

Scenario: Достигнут потолок числа снимков в директории
  Given в директории уже 20 снимков (дефолт `max_snapshots`)
  When берётся 21-й снимок
  Then самый старый снимок этой директории вычищается — в списке по-прежнему не
    больше 20 снимков, новый — сверху

Scenario: Достигнут общий потолок хранилища
  Given суммарный размер общего хранилища превысил 500 МБ (по любым проектам
    пользователя)
  When берётся очередной снимок
  Then из проектов хранилища по очереди вычищается самый старый снимок каждого, пока
    хранилище не уложится в потолок — это может затронуть и другой проект
    пользователя, не только текущий

Scenario: Чекпойнты выключены
  Given настройка чекпойнтов выключена
  Then экран отката явно показывает, что функция выключена, и это не выглядит как
    пустой список из-за отсутствия правок
  And `rollback.list` в этом состоянии всегда возвращает пустой список независимо от
    того, есть ли физически более ранние снимки в общем хранилище (см. Edge cases)

Scenario: В рабочей директории ещё не было ни одного снимка
  Given чекпойнты включены, но агент ещё не менял файлы в ней
  Then список снимков пуст, и это отличимо от состояния «чекпойнты выключены»
    (поле `enabled: true` + пустой список, а не `enabled: false`)

## API contracts
RPC ядра tui_gateway (проверено по `tui_gateway/server.py`, коммит указан в Overview).
Все три метода принимают идентификатор сессии (`session_id`, как и прочие
session-scoped методы шлюза — `_sess(params, rid)`); рабочая директория для операции
берётся ТОЛЬКО из `cwd` текущей сессии (`_session_cwd`, `server.py:1422-1425`) —
вызывающая сторона не может передать директорию отдельным параметром. У нас `cwd`
сессии = корень vault (`specs/workspace-sources.md`: «working dir агента = vault») —
с учётом «Назначение и границы» выше это прямо определяет, что реально увидит
`rollback.list`.

- `rollback.list(session_id)` → `{enabled, checkpoints}`, где `checkpoints` — массив
  `{hash, timestamp, message}`. Если чекпойнты выключены — `{enabled: false,
  checkpoints: []}` без обращения к хранилищу. Список — most-recent-first, не длиннее
  `max_snapshots`
  (`list_checkpoints` сам ограничивает `git log -n <max_snapshots>`). Транспортная
  ошибка — код `5020`.
  **Замечание по источнику.** Поле `message` в ответе шлюза всегда пустая строка —
  обработчик берёт `c.get("message", "")`, а `CheckpointManager.list_checkpoints`
  кладёт причину снимка в поле `reason`, не `message` (несовпадение имён полей,
  `tui_gateway/server.py:12954-12960` против `tools/checkpoint_manager.py:708-729`).
  Также не прокидываются `short_hash`, `files_changed`, `insertions`, `deletions` —
  они есть у ядра (ими пользуется их CLI-форматтер `format_checkpoint_list`), но до
  RPC-ответа не доходят. Наш экран может рассчитывать только на `hash` (полный) и
  `timestamp` (ISO 8601 со смещением).
- `rollback.diff(session_id, hash)` → `{stat, diff, rendered?}`. `hash` обязателен
  (иначе ошибка `4014`, «hash required»); можно передать либо полный хеш из
  `rollback.list`, либо 1-based номер по текущему списку — `_resolve_checkpoint_hash`
  парсит значение как индекс, если это целое число, иначе использует как хеш
  напрямую. `diff` обрезан сервером до 4000 символов БЕЗ маркера обрезки
  (`raw = r.get("diff","")[:4000]`) — длинный diff молча теряет хвост. `rendered` —
  опциональный ANSI-текст под ширину терминала сессии (`render_diff`, рассчитан на
  текстовый интерфейс, не предназначен напрямую для GUI-вьюера различий).
  Транспортная ошибка — код `5022`.
  **Замечание по источнику (важно для UI).** Если `mgr.diff()` возвращает неуспех
  (снимок не найден/хранилища ещё нет), обработчик `rollback.diff` НЕ прокидывает
  `success`/`error` из ответа менеджера — просто берёт `r.get("diff","")` и
  `r.get("stat","")`, которых в неуспешном ответе нет, и возвращает пустые строки, как
  будто различий нет. То есть **пустой ответ `rollback.diff` неотличим от «изменений
  нет» и от «снимок не найден»** — подтверждённая по коду асимметрия с
  `rollback.restore` (см. ниже), не догадка.
- `rollback.restore(session_id, hash, file_path?)` → результат `mgr.restore(...)`
  прокидывается ЦЕЛИКОМ, включая `success`/`error` — в отличие от `rollback.diff`.
  `hash` обязателен (иначе `4014`). Если `file_path` НЕ передан (полный откат) И
  сессия «занята» текущим ходом — ошибка `4009`, «session busy — /interrupt the
  current turn before full rollback.restore»; при указанном `file_path` это
  ограничение снято (одиночный файл можно восстановить и во время хода). Успешный
  ответ: `{success, restored_to, reason, directory, file?, history_removed?}`, где
  `restored_to` — короткий (8 символов) хеш, `reason` — причина снимка, к которому
  восстановили, `file` — только при восстановлении одного файла. `history_removed`
  появляется только при полном восстановлении — число сообщений (assistant/tool,
  затем один user), срезанных с хвоста истории сессии, чтобы контекст агента совпадал
  с восстановленными файлами. Неуспех менеджера (`success: false`) возвращается как
  есть, с полем `error` — например «Checkpoint '<hash>' not found» (снимок вычищен/не
  существует) или «No checkpoints exist for this directory» (для этой рабочей
  директории снимков не было вовсе). Транспортная ошибка — код `5021`.

Коды ошибок JSON-RPC уровня (не путать с `success:false` внутри полезной нагрузки
`rollback.restore`, которая приходит как штатный успешный ответ шлюза):
`4014` — не передан `hash`; `4009` — сессия занята, нужен полный откат; `5020`/`5021`/
`5022` — необработанное исключение в `rollback.list`/`rollback.restore`/
`rollback.diff` соответственно.

## Data schemas
Что реально долетает до нашего клиента через RPC (не то, что хранит ядро внутри):

| Поле | `rollback.list` | `rollback.diff` | `rollback.restore` |
|---|---|---|---|
| `hash` (полный) | да | параметр запроса | параметр запроса |
| `timestamp` | да | — | — |
| причина снимка | нет (см. замечание в API contracts) | — | да, как `reason`, только в ответе на восстановление |
| `stat`/`diff` | — | да (diff обрезан до 4000 симв.) | — |
| количество изменённых файлов/±строк | нет | нет структурировано (только внутри текста `stat`) | нет |
| `history_removed` | — | — | да, только при полном восстановлении |

## Edge cases
- Файл добавлен ПОСЛЕ снимка, затем выполнен откат к более раннему снимку — новый
  файл на диске НЕ удаляется (проверено экспериментом: `git checkout <hash> -- .`
  перезаписывает/создаёт пути, присутствующие в целевом дереве, но не трогает пути,
  которых там не было). После такого отката рабочая директория — это старое
  содержимое ПЛЮС файлы, появившиеся после снимка, а не буквально «как было».
- Файл удалён после снимка (например, деструктивной командой) — восстановление к
  снимку, где файл ещё существовал, воссоздаёт его с содержимым на момент снимка
  (`git checkout` пишет все пути целевого дерева).
- Файл переименован между снимками — `rollback.diff` показывает это как
  переименование (`rename from/to`, распознаётся автоматически даже без явного
  `-M`/`--find-renames` — проверено экспериментом на используемой версии git), а не
  как «удалён+добавлен». Но при ВОССТАНОВЛЕНИИ к снимку до переименования на диске
  останутся ОБА файла — старое имя воссоздаётся с прежним содержимым, новое имя не
  удаляется (то же правило, что и для добавленного файла выше).
- Двоичный файл в различиях — `rollback.diff` возвращает `Binary files … differ` и
  строку статистики размера (`Bin 0 -> N bytes`) без построчного содержимого;
  построчный diff для такого файла показать нечем.
- Снимок недоступен (хеш вычищен политикой `max_snapshots`/`max_total_size_mb`, либо
  просто неверный) — `rollback.restore` отвечает `success:false` с понятной причиной;
  `rollback.diff` в той же ситуации отвечает пустыми `stat`/`diff` (см. «Замечание по
  источнику» в API contracts) — экрану нельзя показывать это как «изменений нет» без
  дополнительной проверки.
- Снимок физически повреждён (битые git-объекты в общем хранилище) — **не
  подтверждено источником**: выделенных тестов/документации на этот случай нет; по
  общей структуре обработки ошибок ожидается непрозрачный `success:false` с текстом
  git-ошибки, а не отдельный код/сообщение. Открытый вопрос №5.
- Vault инициализирован (Obsidian-style, `specs/workspace-sources.md`) поверх уже
  существующей папки, в которой случайно есть один из девяти маркеров (например,
  `package.json` от смежного софт-проекта) — тогда охват снимка для файлов рядом с
  этим маркером неожиданно расширяется до директории с маркером, а не сужается до
  директории правимого файла, как по умолчанию (см. «Назначение и границы»).
- Vault сам по себе — репозиторий пользователя (внутри есть настоящий `.git`,
  например пользователь ведёт vault под своим git) — `.git` тоже входит в список
  маркеров, поэтому «рабочей директорией» для чекпойнта станет корень этого
  репозитория. Изоляция при этом не нарушается (см. «Назначение и границы» — теневой
  git всё равно работает через отдельные `GIT_DIR`/`GIT_INDEX_FILE` и не трогает
  `<vault>/.git`), но, кроме собственного `.git` пользователя, это единственный
  штатный способ без нашего вмешательства получить охват «весь vault», а не «папка
  файла».

## Security
- Секреты (`.env`, `.env.*`, `.env.local`, `.env.*.local`) исключены из снимков по
  умолчанию (`DEFAULT_EXCLUDES`, `tools/checkpoint_manager.py`) — чекпойнты их не
  захватывают и, соответственно, не могут случайно восстановить старое значение
  секрета поверх нового.
- Механизм — прозрачная инфраструктура на стороне ядра, не инструмент («это НЕ
  инструмент — LLM её не видит», вступление модуля `tools/checkpoint_manager.py`);
  у агента нет собственного инструмента для чтения содержимого снимков — доступ к
  ним только через путь `/rollback`-подобных команд пользователя.
- Изоляция от `.git`/git-конфига пользователя — см. «Назначение и границы»; это
  основной security-периметр фичи: агент/чекпойнты не должны получить доступ к
  истории пользовательского репозитория.

## Non-goals
- Откат файлов вне vault — источники (UR2) в принципе не пишутся агентом (N3,
  операций записи для них не существует в инструментальном слое), поэтому чекпойнты
  их не касаются; экран отката не показывает и не восстанавливает ничего за
  пределами рабочей директории агента.
- Ветвление истории снимков — у ядра линейная цепочка снимков на директорию (`_prune`
  перестраивает её как один линейный список, без веток); наш экран истории снимков
  ветвление тоже не вводит. Не путать с ветвлением СЕССИЙ чата (`session.*`, батч 5) —
  это отдельный, самостоятельный механизм.
- Работа с пользовательским git — не читаем, не пишем, не анализируем `<vault>/.git`,
  если он есть; чекпойнты — полностью отдельный механизм (см. «Назначение и
  границы»).
- Управление общим хранилищем через CLI ядра (`hermes checkpoints
  status/prune/clear/clear-legacy`) — вне контракта этой спеки: 1.6.C2 реализует
  экран строго по `rollback.list/diff/restore` (донора в их десктопе для этого экрана
  нет — PLAN §Phase 1.6 «Инвентарь их кода», поправка 4 — пишем против RPC ядра).
  Если ретеншен по факту не будет соблюдаться из-за пробела в Open questions №3, это
  отдельное решение/задача, не расширение этой спеки явочным порядком.
- Восстановление файлов, попавших под исключения снимка (`.env*`, `*.log`,
  `node_modules/` и т.п. из `DEFAULT_EXCLUDES`) — они не снимались, восстанавливать
  нечего.

## Open questions
1. ~~**Несовпадение охвата снимка и охвата `rollback.list`**~~ — **ЗАКРЫТ
   РЕШЕНИЕМ ВЛАДЕЛЬЦА 2026-07-31: кладём маркер.** Суть вопроса была в том, что
   ядро определяет «рабочую директорию» снимка по ближайшему из девяти
   маркеров, а `rollback.list/diff/restore` всегда опрашивают `cwd` сессии
   (корень хранилища), и без маркера эти две директории расходятся.
   **Измерено, что последствие хуже, чем предполагала эта спека:** когда поиск
   маркера доходит до домашней директории (у владельца там есть `.git`),
   срабатывает предохранитель ядра «слишком широкая директория» и снимок не
   берётся ВООБЩЕ — молча. То есть без маркера UR14 не «показывает пустой
   список», а не работает.
   **Решение:** `ensureCheckpointMarker()` кладёт в корень хранилища `Makefile`
   при создании проекта и при каждом открытии; если в корне уже есть любой из
   девяти маркеров, не делается ничего. `Makefile` выбран как самый инертный из
   девяти: его не сканирует ни один менеджер пакетов и ни один редактор, `make`
   запускается только вручную. Файл содержит объяснение, зачем он нужен.
   Проверено вживую (`runtime/checkpoint-probe.mjs` и прямой вызов
   `get_working_dir_for_path`): без маркера — домашняя директория и `taken=false`,
   с маркером — корень хранилища и снимок в списке.

2. **Способ включения под tui_gateway.** `checkpoints.enabled` из `config.yaml`
   читается только их интерактивным CLI (`cli.py`); наш путь (`tui_gateway`) слушает
   переменную окружения `HERMES_TUI_CHECKPOINTS`, а три числовых лимита в этом пути
   вообще не настраиваются через `config.yaml` — используются дефолты ядра. 1.6.C1
   должен явно выставлять эту переменную при старте нашего процесса (например, в
   `runtime/serve.mjs`), а не только прописывать `checkpoints:` в
   `runtime/dev-profile/config.yaml`. Это уточнение к PLAN §Phase 1.6 «поправка 5».
3. **Ретеншен по неактивности (7 дней) не запускается в пути tui_gateway.** Живые
   лимиты (`max_snapshots`, `max_total_size_mb`, `max_file_size_mb`) применяются при
   каждом снимке независимо от интеграционного пути; чистка «директории без
   обращений N дней» (`retention_days`/`delete_orphans`/`auto_prune`) вызывается
   только из их `cli.py`-стартапа — в `tui_gateway/server.py` такого вызова нет
   вовсе. Часть UR14 («проекты без обращений 7 дней вычищаются») не выполнится сама
   собой под нашей интеграцией — 1.6.C1 должен решить, как её обеспечить (например,
   самим периодически дёргать `hermes checkpoints prune`), либо явно снять это
   требование.
4. **`rollback.list` не даёт причину снимка и статистику изменений.** Поле `message`
   в ответе всегда пустое (несовпадение имени поля на стороне шлюза),
   `files_changed`/`insertions`/`deletions` не прокидываются вовсе. Если 1.6.C2
   должен показывать «до правки агентом / N файлов, +X/-Y» подобно их CLI — этих
   данных через RPC сейчас нет; нужно решить, показывать ли список только по
   хешу+времени, или добывать эти данные иначе (например, дополнительным
   `rollback.diff` по каждому снимку — дорого).
5. **Повреждённый снимок** — поведение не подтверждено ни исходным кодом (нет
   отдельной обработки), ни тестами, ни документацией. Предполагается общая ветка
   ошибок git-команды, но напрямую это не проверено.
6. **`rollback.diff` на несуществующий/повреждённый снимок неотличим от «нет
   изменений»** (см. Edge cases) — нужно решить, опирается ли 1.6.C2 на
   дополнительную сверку с `rollback.list` перед показом diff, чтобы не вводить
   пользователя в заблуждение пустым результатом.
