## Overview & requirement link
Ref: SPECIFICATION.md — UR4 (чат: стриминг ответов, вывода инструментов и хода
рассуждений), G4 (паритет с Hermes Desktop), UR10 (hub «Агент» — смежная активность).
Контракт того, ЧТО показывает лента чат-дока по ходу работы агента и как это
сворачивается/разворачивается. Визуальный эталон — утверждённый макет
`design/screens/Chat.html` §5.9 «Чат-док · все типы карточек» (dark + light).

Задача 1.5.D1 реализует подмножество §5.9: **рассуждение** и **инструмент**
(выполняется / завершён). Остальные типы карточек §5.9 — отложены (см. Non-goals).

дефекта представления и уточнил источник истины. Фактическая поправка к прежнему

## Behavior (BDD / Gherkin)
Scenario: Ход рассуждений сворачивается по умолчанию
  Given агент отвечает и присылает события хода рассуждений
  When в ленте появляется блок рассуждения
  Then он показан СВЁРНУТЫМ: иконка, подпись «Рассуждение», мета и шеврон
  And он не перебивает и не подменяет текст ответа
  When пользователь разворачивает блок
  Then показывается накопленный текст рассуждения целиком

Scenario: Мета рассуждения не выдумывается
  Given блок рассуждения показан
  When мета («N шагов · X с») выводима из реально полученных событий
  Then она показывается
  And если данных для меты нет — мета опускается (пустые/поддельные значения не рисуются)

Scenario: Карточка инструмента в работе
  Given агент вызвал инструмент и вызов ещё не завершён
  Then карточка показывает индикатор выполнения, имя инструмента и статус «выполняется…»
  And если сервер прислал описание вызова — оно показано одной строкой с усечением

Scenario: Карточка инструмента завершена и разворачивается
  Given вызов инструмента завершился
  Then карточка показывает имя, статус завершения и (при наличии) длительность
  When пользователь разворачивает карточку
  Then показываются аргументы и результат вызова

Scenario: Карточка инструмента всегда подписана (негативный, регресс 1.5.2)
  Given от сервера пришёл вызов инструмента с пустым или отсутствующим именем
  When карточка рендерится
  Then она ВСЁ РАВНО имеет читаемую подпись (запасную)
  And она не выглядит пустым безымянным прямоугольником

Scenario: Уточняющий вопрос агента
  Given агент задал уточняющий вопрос с вариантами ответа
  Then появляется карточка «Уточнение» с вопросом и вариантами
  And она ЗАКРЕПЛЕНА над полем ввода (как карточка approvals), а не помещена в
    ленту: агент заблокирован до ответа, а лента не прокручивается автоматически
    и могла бы спрятать запрос
  When пользователь выбирает вариант
  Then ответ уходит агенту, и он продолжает работу
  And карточка исчезает

Scenario: Открытый уточняющий вопрос без вариантов
  Given агент задал уточняющий вопрос, не предложив вариантов
  Then карточка показывает поле свободного ввода
  When пользователь вводит ответ и подтверждает
  Then ответ уходит агенту

Scenario: Ответ на устаревший запрос (негативный)
  Given запрос уже истёк по таймауту на стороне ядра
  When пользователь всё же отвечает
  Then шлюз отклоняет ответ (нет ожидающего запроса)
  And ошибка показывается на карточке, а карточка не исчезает молча

Scenario: Запрос повышения прав (sudo)
  Given агент запросил повышение прав
  Then появляется закреплённая карточка запроса (см. размещение в сценарии уточнения)
  When пользователь подтверждает либо отклоняет
  Then решение уходит агенту

Scenario: Запрос секрета
  Given инструмент запросил секрет (токен/пароль)
  Then появляется закреплённая карточка ввода с маскированным полем
  And текст подсказки объясняет, кто и зачем запрашивает
  When пользователь вводит значение и подтверждает
  Then значение уходит агенту напрямую и НЕ попадает ни в журнал, ни в состояние ленты,
    ни в историю сессии на нашей стороне

Scenario: Интерактивный запрос без ответа (негативный — почему это важно)
  Given агент прислал уточнение / запрос секрета / запрос прав
  When интерфейс НЕ показывает карточку
  Then ядро агента блокируется до таймаута (уточнение и секрет — 300 с, права — 120 с)
  And для пользователя это выглядит как зависание — поэтому такие события
    обязаны распознаваться и отображаться

Scenario: Неизвестное событие не теряется молча
  Given сервер прислал событие, которого наш редьюсер не знает (например, после
    обновления Hermes)
  Then лента не ломается
  And в режиме разработки факт фиксируется (только тип события, без полезной нагрузки)

Scenario: Порядок в ленте сохраняется
  Given за один ход агента были и рассуждение, и вызовы инструментов, и текст ответа
  Then элементы идут в порядке их поступления
  And текст ответа не «прыгает» при появлении новой карточки

Scenario: Обе темы
  Given включена светлая либо тёмная тема
  Then карточки читаемы в обеих (цвета — только токены `design/tokens.css`)

### Phase 1.6 — паритет представления (новые сценарии)

Scenario: Ответ агента рендерится как markdown
  Given агент присылает текст ответа с markdown-разметкой
  When текст показан в ленте
  Then заголовки, списки, выделение и блоки кода отрисованы как разметка
  And служебные символы разметки (`**`, `#`, `` ` ``) в глаза не бросаются
  And разметка корректно достраивается по ходу стрима, а не мигает

Scenario: Ход рассуждений сохраняет переводы строк и разметку
  Given рассуждение приходит абзацами с markdown-подзаголовками
  When пользователь разворачивает блок рассуждения
  Then абзацы разделены, подзаголовки видны как разметка
  And текст не слипается в одну строку

Scenario: Карточки хода остаются в ленте после ответа
  Given в ходе было рассуждение и вызовы инструментов
  When агент закончил ответ (`message.complete`)
  Then карточки рассуждения и инструментов остаются на своих местах
  And их можно развернуть и посмотреть
  And повторный ход в той же сессии не удаляет карточки предыдущих ходов

Scenario: Перезагрузка истории сессии не теряет ход
  Given лента содержит карточки рассуждения и инструментов
  When история сессии перечитывается (переключение сессии и возврат)
  Then восстановлено то, что отдаёт gateway; потерянное отсутствует явно
  And карточки не подменяются пустыми полосами

### Phase 1.6 — подагенты, MoA и композер (задачи 1.6.A1–1.6.A5)

Scenario: Подагент запускается, и его ход виден в реальном времени
  Given агент вызвал делегирование и породил подагента
  When гейтвей присылает событие запуска подагента (семейство `subagent.*`)
  Then в ленте появляется карточка, показывающая, что подагент запущен
  When приходят его собственные текст, рассуждение и вызовы инструментов
  Then они накапливаются в этой же карточке, а не в карточках родительского агента
  And видно, что это ход именно подагента, а не родителя

Scenario: Подагент завершается
  Given карточка подагента показывает его ход
  When приходит событие завершения этого подагента
  Then карточка показывает статус «завершён»
  And дальнейшие события по этому подагенту в неё уже не добавляются

Scenario: Дерево порождённых агентов
  Given агент породил несколько подагентов, и один из подагентов породил ещё одного
  When лента показывает их карточки
  Then видно, какой подагент кем порождён — это дерево, а не плоский список без связи
  And карточки разных подагентов не путаются между собой

Scenario: Прерывание подагента
  Given один из подагентов выполняет ход
  When пользователь прерывает именно этого подагента
  Then его карточка отражает, что он остановлен
  And родительский агент и остальные подагенты продолжают работать как ни в чём не бывало

Scenario: Подагент завершился ошибкой (негативный)
  Given подагент выполнял ход
  When событие его завершения сообщает об ошибке, а не о штатном результате
  Then карточка ВСЁ РАВНО показывает статус ошибки, а не тихо становится «завершён»
  And текст ошибки, если он пришёл в событии, показан на карточке

Scenario: Карточка «совет моделей» появляется
  Given агент отвечает через MoA — несколько моделей участвуют в одном ответе
  When приходит событие `moa.reference`
  Then в ленте показана карточка «совет моделей»
  And она не подменяет и не задерживает обычный текст ответа

Scenario: Карточка «совет моделей» показывает сведение ответов
  Given карточка «совет моделей» уже показана
  When приходит событие `moa.aggregating`
  Then карточка отражает, что ответы участников сводятся в один
  And итоговый текст ответа по-прежнему приходит обычным потоком `message.*`

Scenario: Автодополнение пути по `@`
  Given пользователь печатает `@` и продолжает вводить часть имени файла или папки
  When ввод уходит на автодополнение через `complete.path`
  Then под полем ввода появляется список подходящих путей vault и источников
  And список сужается по мере ввода

Scenario: Вставка ссылки на файл подставляет его содержимое
  Given список автодополнения показан
  When пользователь выбирает файл из списка
  Then в сообщение вставляется ссылка на этот файл вместо сырого пути, и автодополнение
    закрывается
  When пользователь отправляет сообщение
  Then вместе с текстом агенту уходит содержимое указанного файла

Scenario: Ссылка на папку
  Given список автодополнения показан
  When пользователь выбирает папку, а не файл
  Then в сообщение вставляется ссылка на папку
  And она визуально отличима от ссылки на файл

Scenario: `@`-ссылка на путь, которого нет (негативный)
  Given пользователь напечатал `@` и текст, для которого `complete.path` не находит
    совпадений ни в vault, ни в источниках
  Then список автодополнения пуст, без ошибки и без зависания ввода
  When пользователь всё равно отправляет сообщение с этим текстом
  Then сообщение уходит обычным текстом, без ссылки, и без попытки подставить содержимое
    несуществующего пути

Scenario: Вставка изображения из буфера обмена
  Given в буфере обмена есть изображение (например, скриншот)
  When пользователь вставляет его в поле композера (`clipboard.paste`)
  Then в композере появляется превью вложения-изображения
  And напечатанный текст сообщения не портится вставкой

Scenario: Прикрепление изображения файлом
  Given пользователь прикрепляет файл изображения (`image.attach`)
  Then в композере появляется превью вложения с именем файла
  When пользователь отправляет сообщение
  Then изображение уходит агенту как вложение

Scenario: Прикрепление PDF файлом
  Given пользователь прикрепляет PDF-файл (`pdf.attach`)
  Then в композере появляется вложение, по виду отличимое от изображения (имя файла,
    не превью-картинка)
  When пользователь отправляет сообщение
  Then PDF уходит агенту как вложение

Scenario: Открепление изображения
  Given к ещё не отправленному сообщению прикреплено изображение
  When пользователь его открепляет (`image.detach`)
  Then вложение исчезает из композера
  And сообщение можно отправить без него

Scenario: Вложение неподдерживаемого типа (негативный)
  Given пользователь пытается прикрепить файл, который не является ни изображением, ни PDF
  When композер отклоняет вложение
  Then пользователь видит понятное сообщение, что этот тип не поддерживается
  And набранный текст сообщения не теряется — сообщение можно отправить без вложения

Scenario: Индикатор активной цели появляется
  Given пользователь задаёт агенту цель командой `/goal`
  When цель принята
  Then в интерфейсе виден бейдж «цель активна»
  And он остаётся видимым, пока цель не приостановлена или не сброшена

Scenario: Пауза активной цели
  Given бейдж «цель активна» показан
  When пользователь ставит цель на паузу
  Then бейдж отражает, что цель на паузе, а не активна
  And агент не запускает новый автономный ход по этой цели, пока пауза не снята

Scenario: Сброс цели
  Given бейдж «цель активна» либо «на паузе» показан
  When пользователь сбрасывает цель
  Then бейдж исчезает
  And агент больше не продолжает автономно без обращения пользователя

Scenario: Цель сброшена во время хода (негативный)
  Given агент выполняет ход, начатый автономным продолжением цели
  When пользователь сбрасывает цель, пока этот ход ещё идёт
  Then бейдж перестаёт показывать «цель активна» сразу, не дожидаясь конца хода
  And после сброса агент не запускает новый ход по этой цели

## API contracts
События tui_gateway, из которых собирается лента (инвентарь — PLAN §Data/API):
- `message.start` / `message.delta` / `message.complete` — текст ответа (уже реализовано).
- `tool.start` | `tool.started` → `{tool_id, name, context}` — начало вызова.
- `tool.generating` → `{tool_id, text?, context?}` — обновление описания.
- `tool.complete` → `{tool_id, name, args, duration_s, result}` — завершение.
- `thinking.delta` → `{text}` — поток «мышления».
- `reasoning.delta` → `{text, verbose?}` — поток рассуждения.
- `reasoning.available` → `{text, verbose?}` — готовый блок рассуждения.

**Блокирующие интерактивные запросы** (гейтвей реализует их через `_block(...)` —
ядро агента ОСТАНАВЛИВАЕТСЯ до ответа либо до таймаута; в payload приходит `request_id`,
ответ обязан его вернуть):
- `clarify.request` → `{request_id, question, choices}` ⇄ метод `clarify.respond` — таймаут 300 с.
- `secret.request` → `{request_id, ...}` ⇄ метод `secret.respond` — таймаут 300 с.
- `sudo.request` → `{request_id}` ⇄ метод `sudo.respond` — таймаут 120 с.
- `approval.request` ⇄ `approval.respond` — уже реализовано (задача 0.13).

Замечания по источнику (проверено по исходникам hermes 0.18.0, задача 1.5.2):
- `tool.*` и `reasoning.available` подавляются, если `display.tool_progress = off`;
  `thinking.delta`/`reasoning.delta` идут независимо от этой настройки.
- у MCP-инструментов `context` приходит пустым (hermes не строит preview для MCP) —
  поэтому подпись карточки не может опираться только на `context`.

## Data schemas
Элемент ленты (renderer, in-memory; на диск не пишется):
```
ChatItem =
  | { kind: 'message',   role: 'user'|'assistant', text, status? }
  | { kind: 'tool',      toolId, name, context, args?, result?, durationS?, status }
  | { kind: 'reasoning', turnId, text, segments, startedAt, endedAt? }
```
`reasoning` накапливает текст хода; `segments` — число полученных блоков/дельт-групп
(основание для меты «N шагов»); длительность — из `startedAt/endedAt`.

## Edge cases
- Событие рассуждения пришло без предшествующего `message.start` — блок всё равно создаётся.
- `tool.complete` без парного `tool.start` — карточка создаётся сразу завершённой.
- Пустое/отсутствующее имя инструмента — запасная подпись (регресс 1.5.2).
- Очень длинный текст рассуждения/результата — свёрнутое состояние не растёт; в развороте
  длинный результат усечён с возможностью показать полностью (как сейчас в ToolCallCard).
- Смена проекта/сессии — лента сбрасывается целиком (существующее поведение).
- `display.tool_progress = off` — tool-карточек нет; рассуждение продолжает работать.

## Security
- Значение секрета (`secret.request`) — «секретное содержимое» по `docs/SECURITY.md`:
  не логируется (в т.ч. в предупреждении о неизвестных событиях логируется ТОЛЬКО тип
  события), не пишется в состояние ленты и историю сессии, не попадает в снимки/скриншоты
  отчётов. Поле ввода маскировано. Реализация карточек `secret`/`sudo` — операция с
  секретами и правами → отдельный Vibe Diff и прогон `security-review` перед сборкой
  (AGENTS.md §7).
- Windows: `sudo.request` в нашей среде маловероятен (нет sudo), но событие обрабатывается
  — иначе агент молча простоит 120 с.

## Non-goals (в 1.5.D1 не делаем)
Отложено отдельными задачами: субагент (`subagent.*`, 7 событий), MoA-референсы,
`tool.progress`, рестайл существующей карточки approvals (работает с задачи 0.13) и
карточка ошибки инструмента (надёжного per-tool сигнала ошибки в инвентаре событий не
