## Overview & requirement link
Ref: SPECIFICATION.md — UR4 (чат: стриминг ответов, вывода инструментов и хода
рассуждений), G4 (паритет с Hermes Desktop), UR10 (hub «Агент» — смежная активность).
Контракт того, ЧТО показывает лента чат-дока по ходу работы агента и как это
сворачивается/разворачивается. Визуальный эталон — утверждённый макет
`design/screens/Chat.html` §5.9 «Чат-док · все типы карточек» (dark + light).

Задача 1.5.D1 реализует подмножество §5.9: **рассуждение** и **инструмент**
(выполняется / завершён). Остальные типы карточек §5.9 — отложены (см. Non-goals).

## Behavior (BDD / Gherkin)
Scenario: Ход рассуждений сворачивается по умолчанию
  Given агент отвечает и присылает события хода рассуждений
  When в ленте появляется блок рассуждения
  Then он показан СВЁРНУТЫМ: иконка, подпись «Рассуждение», мета и шеврон
  And он не перебивает и не подменяет текст ответа
  When пользователь разворачивает блок
  Then показывается накопленный текст рассуждения целиком

Scenario: Мета рассуждения не выдумывается
  Given блок рассуждения показан
  When мета («N шагов · X с») выводима из реально полученных событий
  Then она показывается
  And если данных для меты нет — мета опускается (пустые/поддельные значения не рисуются)

Scenario: Карточка инструмента в работе
  Given агент вызвал инструмент и вызов ещё не завершён
  Then карточка показывает индикатор выполнения, имя инструмента и статус «выполняется…»
  And если сервер прислал описание вызова — оно показано одной строкой с усечением

Scenario: Карточка инструмента завершена и разворачивается
  Given вызов инструмента завершился
  Then карточка показывает имя, статус завершения и (при наличии) длительность
  When пользователь разворачивает карточку
  Then показываются аргументы и результат вызова

Scenario: Карточка инструмента всегда подписана (негативный, регресс 1.5.2)
  Given от сервера пришёл вызов инструмента с пустым или отсутствующим именем
  When карточка рендерится
  Then она ВСЁ РАВНО имеет читаемую подпись (запасную)
  And она не выглядит пустым безымянным прямоугольником

Scenario: Порядок в ленте сохраняется
  Given за один ход агента были и рассуждение, и вызовы инструментов, и текст ответа
  Then элементы идут в порядке их поступления
  And текст ответа не «прыгает» при появлении новой карточки

Scenario: Обе темы
  Given включена светлая либо тёмная тема
  Then карточки читаемы в обеих (цвета — только токены `design/tokens.css`)

## API contracts
События tui_gateway, из которых собирается лента (инвентарь — PLAN §Data/API):
- `message.start` / `message.delta` / `message.complete` — текст ответа (уже реализовано).
- `tool.start` | `tool.started` → `{tool_id, name, context}` — начало вызова.
- `tool.generating` → `{tool_id, text?, context?}` — обновление описания.
- `tool.complete` → `{tool_id, name, args, duration_s, result}` — завершение.
- `thinking.delta` → `{text}` — поток «мышления».
- `reasoning.delta` → `{text, verbose?}` — поток рассуждения.
- `reasoning.available` → `{text, verbose?}` — готовый блок рассуждения.

Замечания по источнику (проверено по исходникам hermes 0.18.0, задача 1.5.2):
- `tool.*` и `reasoning.available` подавляются, если `display.tool_progress = off`;
  `thinking.delta`/`reasoning.delta` идут независимо от этой настройки.
- у MCP-инструментов `context` приходит пустым (hermes не строит preview для MCP) —
  поэтому подпись карточки не может опираться только на `context`.

## Data schemas
Элемент ленты (renderer, in-memory; на диск не пишется):
```
ChatItem =
  | { kind: 'message',   role: 'user'|'assistant', text, status? }
  | { kind: 'tool',      toolId, name, context, args?, result?, durationS?, status }
  | { kind: 'reasoning', turnId, text, segments, startedAt, endedAt? }
```
`reasoning` накапливает текст хода; `segments` — число полученных блоков/дельт-групп
(основание для меты «N шагов»); длительность — из `startedAt/endedAt`.

## Edge cases
- Событие рассуждения пришло без предшествующего `message.start` — блок всё равно создаётся.
- `tool.complete` без парного `tool.start` — карточка создаётся сразу завершённой.
- Пустое/отсутствующее имя инструмента — запасная подпись (регресс 1.5.2).
- Очень длинный текст рассуждения/результата — свёрнутое состояние не растёт; в развороте
  длинный результат усечён с возможностью показать полностью (как сейчас в ToolCallCard).
- Смена проекта/сессии — лента сбрасывается целиком (существующее поведение).
- `display.tool_progress = off` — tool-карточек нет; рассуждение продолжает работать.

## Non-goals (в 1.5.D1 не делаем)
Остальные карточки §5.9 макета — отдельными задачами позже, вместе с hub «Агент» (UR10):
субагент (`subagent.*`), уточнение (`clarify.*`), ввод секрета (`secret.*`), режим sudo
(`sudo.*`), MoA-референсы, а также рестайл существующей карточки approvals (работает
с задачи 0.13) и карточка ошибки инструмента (надёжного per-tool сигнала ошибки в
инвентаре событий не подтверждено — нужен отдельный recon).

## Feature-level acceptance & validation
- vitest: редьюсер (накопление рассуждения, порядок, tool без start, смена хода) и чистые
  модули (запасная подпись, мета рассуждения).
- Ручной прогон владельца: реальный ход с MCP-вызовами — карточки подписаны, рассуждение
  сворачивается/разворачивается, обе темы.
- Эвалы не требуются: изменяется только представление, промпты и поведение агента не трогаются.
