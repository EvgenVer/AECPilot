### Два слоя и почему их два

Разделение не архитектурное украшение, а следствие того, как устроены сами слои.

| | Слой 1 — записка ядра | Слой 2 — Mem0 (`oss`) |
|---|---|---|
| Что это | два файла в профиле, `memories/MEMORY.md` и `memories/USER.md` | локальное векторное хранилище плюс LLM-извлечение фактов |
| Как попадает к модели | текст **целиком** вклеивается в системный промпт каждый ход | подставляются только релевантные вопросу факты |
| Область | **профиль** — то есть человек; общая для всех его проектов | задаётся нами (см. §Скоупы) |
| Объём | предел в символах, ключи `memory.memory_char_limit` / `memory.user_char_limit` | предела нет |
| Метаданные факта | нет | дата, сессия-источник, канал |
| Правка человеком | текстом | списком с поиском и удалением |

Из этого следует распределение обязанностей, и оно же — граница ответственности слоёв:

- **Слой 1 держит то, что должно действовать всегда:** предпочтения человека («я веду
  раздел ОВ», «отвечай короче») и небольшое число оперативных фактов, которые нужны на
  каждом ходу. Это и есть та роль, которую сам автор ядра описывает для встроенного
  хранилища при активном внешнем провайдере — «reserved for explicit high-frequency
  operational facts».
- **Слой 2 держит накопленное знание проекта:** то, чего за месяцы работы становится
  сотни фактов и что нужно не всегда, а по делу.

Пределы слоя 1 остаются на умолчаниях ядра (2200 и 1375 символов). Они **настраиваемы**
— это обычные ключи конфига, — но при активном слое 2 поднимать их незачем: слой 1 по
замыслу маленький, а весь его текст платит контекстом на каждом ходу.

## Behavior (BDD / Gherkin)

Scenario: Автозапись проектного факта
  Given идёт диалог в открытом проекте
  When в диалоге зафиксирован устойчивый проектный факт («заказчик просил закладывать резерв мощности 20%»)
  Then факт попадает в память проекта (слой 2, автоизвлечение)
  And он виден в журнале памяти UI с датой и сессией-источником

Scenario: Автозапись пользовательского предпочтения
  When факт касается человека, а не проекта («я веду раздел ОВ», «отвечай короче»)
  Then он сохраняется в слой 1 (`USER.md` профиля)
  And действует во всех проектах этого человека без переноса

Scenario: Изоляция проектов (негативный)
  Given в проекте A запомнен проектный факт
  When открыт проект B
  Then этот факт не подставляется в контекст и не находится поиском по памяти проекта B

Scenario: Использование памяти (recall)
  Given в памяти есть релевантные текущей задаче факты
  When агент выполняет новый запрос
  Then релевантные факты учитываются
  And ответ согласуется с ними (например, применяет резерв 20%)

Scenario: Управление памятью
  When пользователь открывает экран памяти
  Then он видит записку слоя 1 как текст и правит её текстом
  And видит список фактов слоя 2 с поиском и удалением
  And может отключить автозапись переключателем
  And удалённый факт больше не участвует в recall

Scenario: Фильтр секретов (негативный)
  Given в диалоге встречается строка, похожая на секрет (ключ API, пароль, токен)
  Then она не сохраняется **ни в одном из слоёв**

Scenario: Локальность
  Then содержимое памяти хранится только на этой машине
  And наружу уходят лишь штатные вызовы того endpoint, который настроен у ядра
  And ни один вызов не уходит на адрес, который человек не настраивал

Scenario: Провайдер недоступен
  Given слой 2 не поднялся (нет ключа, недоступен endpoint, не установлен пакет)
  Then разговор продолжается, слой 1 работает
  And человек видит явное сообщение о том, что расширенная память выключена, а не тишину

## API contracts

### Слой 1 — инструмент ядра, наш код его не подменяет

`memory` с действиями `add` / `replace` / `remove` и целью `memory` | `user`. Правка
адресуется **подстрокой**, не идентификатором. При переполнении ядро отказывает и требует
сначала consolidate — это его поведение, мы его не меняем.

### Слой 2 — инструменты плагина Mem0

Регистрируются самим плагином (`mem0_*`), схемы приходят от него. Наш код их не
объявляет и не переименовывает.

### Что настраиваем мы, и почему это код, а не инструкция

Три значения обязаны стоять в коде регистрации провайдера. Каждое из них молча ломает
обещание этой спеки, если о нём забыть, — и ни одно не диагностируется по ошибке.

| Ключ | Значение | Что ломается без него |
|---|---|---|
| `memory.provider` | `mem0` | слой 2 просто не включается |
| `mode` в `mem0.json` | `oss` | уходит в облачный режим и требует чужой ключ |
| `oss.llm.openai_base_url`, `oss.embedder.openai_base_url` | endpoint ядра | **молча** уезжает на `https://api.openai.com/v1` — сценарий «Локальность» нарушен, ошибки нет |
| `MEM0_TELEMETRY` | `false` | их телеметрия шлёт отпечаток машины на posthog с первого запуска; событие `mem0.init` обходит выборку |

## Data schemas

**Слой 1.** `$HERMES_HOME/memories/{MEMORY,USER}.md` — профиль ядра, то есть человек.
Пути и формат принадлежат ядру; мы их не выбираем.

**Слой 2.** Хранилище qdrant во **встроенном режиме** — путь на диске, без сервера и без
слушающего порта (`oss.vector_store.config.path`). Конфиг — `$HERMES_HOME/mem0.json`.

Факт слоя 2: `{id, text, created_at, metadata: {session, channel}}` — форма плагина.

### Скоупы: что где живёт и почему это наша работа

**У ядра проектной оси памяти нет.** Провайдер получает при инициализации профиль,
сессию, канал и личность пользователя — но не каталог проекта. Оба файла записки живут в
профиле, а профиль по PLAN §«Что оставляем открытым для многопользовательского сервера» —
единица разделения **между людьми**; проект, документы и индекс при этом общие. Чтение
Mem0 фильтруется только по `user_id` — «by design», чтобы recall доставал факты, записанные
из любого канала.

Отсюда две вещи:

- **Пользовательский скоуп получается сам собой.** `USER.md` профильный, а профиль от
  проекта не зависит — предпочтение человека действует во всех его проектах без переноса.
- **Проектный скоуп существует только если мы его сделаем.** Иначе факт проекта A
  всплывает в проекте B, и сценарий «Изоляция проектов» проваливается.

Механизм изоляции выбирает задача 5.2 из двух названных кандидатов: ключ разделения,
который Mem0 и так применяет к чтению, либо отдельное хранилище на проект. Требование к
любому из них одно: **изоляция не должна опираться на дисциплину модели.** Ни один
кандидат не меняет чужой код.

## Edge cases

- Дубликат факта → консолидация на стороне слоя 2 (обновление, не второй факт).
- Противоречащий факт («резерв теперь 15%») → замена; журнал показывает изменение.
- Автозапись выключена → память пополняется только явной командой («запомни…»).
- Переполнение слоя 1 → отказ ядра с требованием consolidate; человек видит это как
  сообщение, а не как молчаливую потерю факта.
- Слой 2 не поднялся → см. сценарий «Провайдер недоступен». Отказ конструктора Mem0 без
  ключа — обычный случай, а не авария.
- Секрет в тексте, который человек **сам** просит запомнить → фильтр всё равно срабатывает;
  это негативный сценарий, а не удобство.

## Feature-level acceptance & validation

**Детерминированное (pytest / vitest):**
- скоупы: факт проекта A не читается в проекте B; факт пользователя читается в обоих;
- персистентность обоих слоёв после рестарта;
- фильтр секретов на диалогах-фикстурах — ни один слой не сохранил;
- три обязательных ключа настройки выставлены (гейт, как у донорских глаголов): тест
  падает, если `openai_base_url` или `MEM0_TELEMETRY` потеряются при правке.

**Smoke-эвал ≥5 сценариев** (задача 5.6): факт извлечён в правильный слой; recall влияет
на ответ; удаление исключает из recall; секрет не записан; противоречие консолидировано.
Прогон при изменении правил автозаписи или модели.

**Ручная проверка:** экран памяти — правка записки текстом, поиск и удаление в списке,
переключатель автозаписи.
