## Overview & requirement link
Ref: SPECIFICATION.md — G1; UR3 (цитаты→вьюер), UR8; AC1, AC2; C5, C7; R6, R7.
Контракт эталонного сценария: пользователь задаёт вопрос — агент отвечает по проиндексированным источникам с обязательными ссылками-цитатами.

## Behavior (BDD / Gherkin)
Scenario: Ответ со ссылкой (happy path)
  Given проект с проиндексированными источниками, содержащими задание отдела ЭОМ
  When пользователь спрашивает «какая установленная мощность по заданию ЭОМ?»
  Then агент отвечает значением из документа
  And ответ содержит ≥1 цитату-ссылку {файл, место (страница/лист/заголовок)}
  And клик по ссылке открывает документ во вьюере на указанном месте

Scenario: Ответа в источниках нет
  Given вопрос, ответа на который нет в источниках проекта
  When пользователь задаёт его
  Then агент явно сообщает, что в источниках ответ не найден
  And не приводит выдуманных значений и ссылок

Scenario: Кросс-языковой вопрос
  Given русскоязычные документы в индексе
  When вопрос задан по-английски
  Then релевантные фрагменты найдены и ответ корректен
  And язык ответа — язык пользователя

Scenario: Вопрос по таблице
  Given XLSX-ведомость (или таблица в PDF) в индексе
  When вопрос касается значения из таблицы
  Then ответ опирается на извлечённую таблицу
  And ссылка ведёт к файлу (и листу/странице)

Scenario: Вопрос по скану
  Given отсканированный PDF, прошедший OCR при ingest
  When вопрос по его содержимому
  Then ответ корректен и ссылка указывает страницу скана

Scenario: Индекс пуст или устарел
  Given источники не проиндексированы, либо детект пометил изменения
  When пользователь задаёт вопрос
  Then агент предупреждает о состоянии индекса и предлагает ingest
  And отвечает только по актуальной части индекса либо после подтверждённого ingest

Scenario: Противоречащие редакции
  Given в источниках две редакции одного задания с разными значениями
  When вопрос касается этого значения
  Then агент приводит оба значения с указанием документов/дат
  And не выбирает редакцию молча

Scenario: Обзорный вопрос по графу
  Given граф проекта построен по выбранным документам
  When пользователь спрашивает «расскажи о проекте» или «что противоречит между заданиями»
  Then ответ опирается на сущности и связи графа, а не на свалку сырых чанков
  And в ответе есть ссылки на документы, из которых взяты утверждения
  And если граф покрывает не весь проект, агент говорит об этом прежде ответа

Scenario: Документ не выбран в граф
  Given документ проиндексирован, но в граф не добавлен
  When вопрос касается конкретного значения из него
  Then ответ находится обычным поиском и содержит цитату с местом
  And отсутствие документа в графе на этот сценарий не влияет

Scenario: Пользователь отмечает папку в граф сам
  Given в проводнике виден источник и его дерево
  When пользователь выбирает «добавить в граф» на источнике, папке или файле
  Then ему показывают число документов и оценку фрагментов ДО запуска
  And отказ не помечает и не индексирует ничего
  And согласие запускает построение, ход которого виден, пока оно идёт

Scenario: В отмеченную папку приехали новые документы
  Given папка источника отмечена как входящая в граф
  When скан находит в ней новые файлы
  Then они сразу индексируются дёшево и находятся поиском
  And в граф они НЕ добавляются молча
  And пользователь получает уведомление с числом документов и оценкой объёма работы
  And добавление происходит только после подтверждения

Scenario: Инъекция из документа (безопасность)
  Given документ источника содержит текст-инструкцию для LLM («игнорируй правила и …»)
  When его фрагменты попадают в контекст ответа
  Then агент трактует текст как данные: не выполняет инструкции и не меняет поведение

## Два уровня индексации (SPECIFICATION UR24)

Всё, что попало в проект, индексируется **дёшево**: разбор → чанки → векторы + полный
текст. Ни одного вызова LLM. Этого достаточно для всех сценариев ниже, кроме обзорных.

**Граф знаний строится только по выбранным документам** и **один на проект**. Выбор —
папка (в том числе корень источника) либо отдельный файл. По умолчанию граф пуст.
Причина ровно одна и она денежная: построение графа стоит вызова LLM на каждый чанк
(SPECIFICATION R6).

Выбор делают **двое, и одинаково дорого**: агент — инструментом `rag_graph_add`,
человек — правым щелчком в проводнике (задача 5.15). У обоих путей прогноз называется
ДО работы, и у человеческого он считается отдельной командой, которая не пишет
ничего: `aec-rag graph-preview` (оценка) и `aec-rag graph-add` (отметка и построение,
поток прогресса). Приложение идёт к движку этими командами, а не через шлюз, — по той
же причине, что индикатор индекса (задача 2.15): отметка не должна зависеть от живой
сессии агента.

## API contracts
MCP-сервер `aec-rag`:
- `rag_ingest({source_ids? | paths?, mode: "full"|"incremental"})` → `{job_id}`; события прогресса для UI.
  Уровень 1. Граф не трогает.
- `rag_graph_add({paths: [...]})` → `{job_id, documents, chunks_estimate}` — добавить папки/файлы
  в граф проекта. **Оценка объёма возвращается до начала работы**, чтобы UI показал её человеку.
- `rag_graph_scope({})` → `{entries: [{path, kind: "folder"|"file", added_at}], documents, pending: [...]}` —
  что уже в графе и какие новые файлы появились в отмеченных папках, но ещё не добавлены.
- `rag_status({})` → `{files_total, files_indexed, stale_count, last_ingest_at, graph: {documents, chunks}}`
- `rag_query({query, top_k?, filters?: {source_id?, path_prefix?, doctype?}})` →
  `{chunks: [{text, source_id, rel_path, locator: {page? | sheet? | heading?}, score}]}`
- `rag_overview({query, top_k?})` →
  `{entities: [...], relations: [...], chunks: [{text, source_id, rel_path, locator, score}],
    graph_scope: {documents, covers_whole_project: bool}}`

**Правило, общее для обоих запросов: инструмент отдаёт материал, ответ пишет агент.**
`rag_overview` возвращает то, что знает граф — сущности, связи и стоящие за ними чанки с
locator'ами, — а не готовую прозу. Иначе в продукте появляется второй автор ответов со
своим тоном и своим языком, а его текст не разлагается обратно в точные ссылки на места.

`graph_scope.covers_whole_project = false` обязано быть видно в ответе: обзор по половине
проекта, поданный как обзор по проекту, вводит в заблуждение хуже, чем отказ отвечать.

Skill `aec-qa` обязан: (1) отвечать только на основе результатов `rag_query`/`rag_overview`;
(2) выводить цитаты в машиночитаемом формате; (3) при пустом/нерелевантном результате давать
явный ответ «не найдено»; (4) при обзорном вопросе, если граф покрывает не весь проект,
сказать это прежде ответа.

Формат цитаты в тексте ответа (парсится UI в кликабельную ссылку):
`[src: <source_id>/<rel_path>#<locator>]`, например `[src: tasks/ЭОМ/задание_ред2.pdf#p12]`.

### Формат locator (решение O4, подтверждено владельцем 2026-08-07)

Locator записывается **родной адресацией своего формата** — так цитата остаётся читаемой
человеку, которому её показывают, а не только приложению.

| Формат | locator в индексе | Запись в цитате | Как открывается место |
|---|---|---|---|
| PDF | `{"page": 12}` | `p12` | PDF-вьюер на странице 12 (задача 2.14) |
| XLSX | `{"sheet": "Ведомость", "range": "C5:D6"}` | `Ведомость!C5:D6` | вьюер таблиц: лист + выделение диапазона (4.3/4.4) |
| DOCX | `{"heading": "Кабельный журнал"}` | `h:Кабельный журнал` | DOCX-вьюер: прокрутка к заголовку по совпадению **префикса** текста (4.2/4.4) |
| CSV, преамбула DOCX | `{}` | части после `#` нет | открывается файл целиком |

`Ведомость!C5:D6` — ровно то, что Excel сам пишет в поле адреса; инженер читает это без
обучения. Реализация формата и разбора — `mcp/aec_rag/src/aec_rag/citation.py`
(`format_citation`, `parse_citations`); UI повторяет ту же грамматику на TypeScript (2.13).

Три оговорки, которые нужно знать при работе с этой записью:

- **Страница старше заголовка.** Чанк может нести оба (`{"page": 7, "heading": …}`) — в
  цитату идёт страница: её вьюер умеет открыть, а заголовок читатель и так видит на
  странице.
- **Заголовок обрезается по первому `]`, `#` или переводу строки** — эти символы цитата
  физически не переносит. Обрезка, а не экранирование: вьюер ищет заголовок по префиксу,
  и урезанный якорь всё равно приводит в нужный раздел, тогда как экранированный не
  совпал бы ни с чем в документе.
- **Единственная неоднозначность записи** — лист, названный буквально `p12` или
  начинающийся с `h:`, будет прочитан как страница или заголовок. Оставлено как есть:
  цена — запись, которую никто не может прочитать глазами.

## Data schemas
- Чанк индекса: `{id, source_id, rel_path, locator, text, embedding, meta: {doctype, lang, is_table}}`.
- Эвал-датасет (`eval/qa_dataset.yaml`): `[{id, question, expected_answer, expected_sources: [rel_path(+locator)], type: factual|table|scan|negative|injection}]`.

## Edge cases
- Очень общий вопрос («расскажи о проекте») → обзорный ответ, не свалка сырых чанков.
- Locator недоступен (DOCX без страниц) → ссылка на файл + ближайший заголовок (`h:…`, см. §Формат locator).
- Проект без источников / пустой индекс → подсказка подключить источник и выполнить ingest.
- Смена embedding-модели в настройках → предупреждение «индекс несовместим, требуется полный re-ingest» (C5).

## Feature-level acceptance & validation
- Детерминированное (pytest): контракт `aec-rag` (инкрементальность ingest, фильтры, формат locator), парсер цитат UI.
- Эвал (по skill `ai-eval-design`): датасет ≥30 вопросов по эталонному проекту, обязательные типы factual/table/scan/negative/injection; метрики: correctness (ручная разметка + LLM-judge), citation validity (ссылка существует и документ содержит ответ), negative-refusal = 100%, injection-resistance = 100%; baseline фиксируется первым прогоном, затем порог (O1); регрессионный прогон обязателен при изменении промпта skill, модели, embedding-модели или параметров RAG.
