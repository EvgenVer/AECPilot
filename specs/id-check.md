## Behavior (BDD / Gherkin)
Scenario: Комплектность по чек-листу
  Given в vault лежит чек-лист состава ИД (checklists/id-checklist.yaml) и источники проиндексированы
  When пользователь командует «проверь комплектность ИД»
  Then агент сопоставляет каждый пункт чек-листа с документами источников (по правилам match пункта)
  Then выдаёт отчёт: пункт → статус (найден [src:…] / отсутствует / частично, с пояснением)
  And отчёт сохраняется в workspace/reports/ с датой

Scenario: Пункт не найден (анти-галлюцинация)
  Given пункта чек-листа нет в источниках
  Then пункт помечается «отсутствует»
  And агент не притягивает нерелевантный документ: статус «найден» допустим только с валидной ссылкой [src:…]

Scenario: Поиск противоречий
  Given документы содержат пересекающиеся параметры (мощности, расходы, отметки, диаметры…)
  When пользователь командует «найди противоречия в ИД» (опционально: по теме/разделу)
  Then агент извлекает сопоставимые значения и сравнивает их
  And каждое противоречие содержит: параметр, значения сторон, документы [src:…] каждой стороны, серьёзность (high/medium/low), комментарий
  And разные единицы измерения нормализуются до сравнения (кВт/МВт, л/с – м³/ч) — не считаются противоречием

Scenario: Редакции одного документа
  Given в источниках две редакции одного задания
  Then расхождение между ними помечается как «изменение редакции» (с датами), а не как противоречие смежников

Scenario: Человек в контуре
  Then отчёт — рекомендация; никаких автоматических действий (письма, правки вики, re-ingest) без отдельной команды

## Data schemas
`checklists/id-checklist.yaml` (шаблон-дефолт генерируется при создании проекта; организация редактирует под себя):
```yaml
items:
  - id: geo-survey
    title: "Отчёт об инженерно-геологических изысканиях"
    discipline: "общие"          # опционально
    required: true
    match:
      keywords: ["геологические изыскания", "ИГИ"]
      filename_patterns: ["*ИГИ*", "*геолог*"]
    note: ""                      # опционально
```
Отчёт: `workspace/reports/id-check-<date>.md` + машиночитаемый `id-check-<date>.json` (`items[]`, `contradictions[]`).

## API contracts
Использует `aec-rag` (rag_query с фильтрами) и `aec-sources`; запись — только в vault (workspace/reports/). Отдельный MCP не требуется.

## Edge cases
- Чек-лист отсутствует/невалиден → понятная ошибка со ссылкой на шаблон.
- Слишком общий пункт (матчится на всё) → предупреждение в отчёте.
- Значения в таблицах и сканах → опора на table/scan-извлечение aec-rag; при низкой уверенности — пометка «проверить вручную», не догадка.
- Пустой список противоречий → явное «противоречий не найдено в проверенном объёме» с перечнем, что проверялось.

## Feature-level acceptance & validation
- Детерминированное (pytest): парсер/валидатор чек-листа, нормализация единиц, генерация отчётов (md+json).
- Smoke-эвал ≥5 сценариев (AC4): фикстурный мини-проект с заложенными дефектами — 2 отсутствующих пункта, 2 настоящих противоречия, 1 ложное (разные единицы), 1 смена редакции. Метрики: найдены все заложенные дефекты (recall, порог с baseline), нет выдуманных находок (precision), 100% статусов «найден» — с валидными ссылками. Прогон при изменении промпта/модели.
