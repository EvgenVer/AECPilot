## Overview & requirement link
Ref: SPECIFICATION.md — G2; UR6 (агент обновляет вики только по команде; сырые источники в обход индекса); AC3; C7 (язык вики — настройка проекта).
Базис: встроенный навык ядра `llm-wiki` v2.1.0 (`skills/research/llm-wiki`, MIT). **С 2026-09-28 (решение владельца) `aec-wiki` — его адаптация, а не пересказ:** текст навыка — их текст на английском с шапкой происхождения (версия, коммит ядра, список правок), разделы и правила сохранены, меняется только то, что у нас устроено иначе. Прежняя редакция навыка была написана заново и потеряла пять их правил — «сориентируйся перед работой», «проверь, что уже есть», правило имени файла, «дополняй существующую страницу», «спроси перед правкой 10+ страниц»; отсюда D-139, D-143, D-151.

**Что у нас иначе (правки к их тексту):**
- Сырьё двух видов (см. §Data schemas): снимки документов из индекса пишет инструмент (`wiki_snapshot`), а не агент своим `web_extract`; внесённое в обход индекса пишет инструмент `wiki_add_raw`.
- Ссылка на факт — наш формат `[src: <source_id>/<rel_path>#<locator>](#cite)`, дословная выдержка — через `rag_check_quote`; «не вычисляй значений, которых нет в документах».
- Защита правок человека (`wiki_edited`, `wiki_write_page`, `wiki_checkpoint`) — у них её нет.
- Обновление по изменениям — `wiki_stale`; проверка — кодом (`wiki_lint`), а не обходом страниц.
- Только по команде (UR6): их «сохраняй ценный ответ в `queries/`» — только по просьбе.
- Имя файла — **заголовок страницы как есть, кириллицей**, без транслита (их правило «lowercase, hyphens» рассчитано на латиницу).
- Выброшено: `WIKI_PATH`, Obsidian Sync, systemd, `raw/` сбор через `web_extract` по URL агентом без инструмента.
- Их `llm-wiki` в продукте выключен (UR42), чтобы агент не видел два навыка про одно.

## Behavior (BDD / Gherkin)
Scenario: Первичное построение вики
  Given проект с проиндексированными источниками
  When пользователь командует «построй вики проекта»
  Then агент создаёт страницы в <vault>/wiki/ согласно SCHEMA.md
  And каждая страница имеет YAML-frontmatter (title, type, tags, sources, updated)
  And каждый содержательный факт снабжён провенансом [src: ...] на источник
  And index.md (каталог) и log.md (журнал) обновлены

Scenario: Инкрементальное обновление
  Given вики построена, детект пометил изменённые файлы источников
  When пользователь подтверждает «обновить вики по изменениям»
  Then агент повторно обрабатывает только изменённые источники
  And обновляет затронутые страницы, фиксируя изменения в log.md
  And при конфликте нового и старого значения оформляет блок «противоречие» (обе версии, документы, даты) — молчаливой перезаписи нет

Scenario: Ручная правка сохраняется
  Given инженер вручную отредактировал страницу вики
  When агент позднее обновляет эту страницу
  Then правки человека не затираются: обновление аддитивное/точечное с учётом текущего содержимого
  And при невозможности совместить — конфликт выносится в блок «противоречие» и упоминается в отчёте агента

Scenario: Язык вики
  Given settings.wiki_lang = "auto" и русскоязычные источники
  When агент создаёт страницы
  Then страницы пишутся по-русски; при wiki_lang = "en" — по-английски (термины оригинала в скобках при необходимости)

Scenario: Lint
  When пользователь командует «проверь вики»
  Then агент выдаёт отчёт по серьёзности: битые wikilinks, страницы-сироты, устаревшие страницы (sha источника изменился после updated), незакрытые противоречия, нарушения frontmatter

Scenario: Query по вики
  Given вики содержит страницы по теме
  When пользователь задаёт обзорный вопрос («что известно про электроснабжение объекта?»)
  Then агент отвечает по страницам вики со ссылками на страницы (и транзитивно — на источники)

Scenario: Ориентация перед работой (их правило)
  Given вики уже есть
  When агент получает команду построить, обновить или дополнить вики
  Then до первой записи он читает SCHEMA.md, index.md и последние записи log.md
  And перед созданием страницы ищет существующую по index.md и по файлам
  And если предмет уже описан — дополняет существующую страницу, а не заводит вторую

Scenario: Массовая правка — с вопросом (их правило, D-151)
  Given выполнение команды затронуло бы 10 и больше существующих страниц
  Then агент называет число и список и спрашивает, прежде чем писать

Scenario: Сырой источник в обход индекса
  Given файл, ссылка, вставленный текст или протокол, которых нет в индексе
  When пользователь командует «добавь это в вики»
  Then инструмент `wiki_add_raw` кладёт текст в wiki/raw/<вид>/ с отпечатком и пометкой происхождения
  And для PDF/DOCX/XLSX/скана текст получается тем же разбором Docling, что у индекса, с номерами страниц; сам файл не копируется, в raw/ записан путь к нему
  And в индекс и поиск по документам источник НЕ попадает; добавить его туда — отдельная явная команда
  And агент строит или дополняет страницы, ссылаясь на сырой файл

Scenario: Решение пользователя в вики
  Given в разговоре принято решение («резерв мощности 10 % на ЩС-1 — согласовано с заказчиком»)
  When пользователь командует «занеси в вики»
  Then решение сохраняется сырым источником «решение пользователя от <дата>» через `wiki_add_raw`
  And страница темы получает факт со ссылкой на этот источник
  And без команды решение в вики не попадает (оно остаётся в памяти проекта)

Scenario: Запись только в свои папки (D-143)
  When агент пытается записать страницу вне entities/, concepts/, comparisons/, queries/, index.md, log.md
  Then `wiki_write_page` отказывает и перечисляет разрешённое
  And отказ — обычный ответ инструмента, а не ошибка (D-142): предохранитель ядра не выключает сервер

## Data schemas (структура и SCHEMA)
```
<vault>/wiki/
  SCHEMA.md      # правила домена: таксономия, типы страниц, правила линковки
                 # (генерируется из дефолта, редактируется владельцем)
  index.md       # каталог страниц, по строке на страницу
  log.md         # журнал действий агента (append-only)
  raw/           # сырьё; не редактируется ни агентом, ни человеком. Два вида:
                 # (а) снимки документов ИЗ ИНДЕКСА (wiki_snapshot): markdown после Docling;
                 #     frontmatter: source_id/rel_path, sha256, ingested_at.
    user/        # (б) внесённое В ОБХОД индекса (wiki_add_raw), подпапки по виду:
                 #     files/, links/, notes/ (вставленный текст, протоколы), decisions/;
                 #     frontmatter: origin (user), kind, added_at, sha256 тела,
                 #     source_path или source_url (если есть). Файл-оригинал не копируется.
  entities/      # объект, здания/сооружения, системы (ОВ/ВК/ЭОМ/…), смежники, ТУ-документы
  concepts/      # требования и ограничения (нормативные, площадки, заказчика), принятые решения
  comparisons/   # сводки противоречий и редакций
  queries/       # сохранённые содержательные ответы
```
Дефолтная AEC-таксономия тегов: `object, building, system/<марка>, discipline, tu, task, constraint, decision, contradiction, site`.
Правила страниц: создание — при упоминании в ≥2 источниках или центральности в одном; ≥2 исходящих wikilink; страница >200 строк — сплит на подтемы; каждый факт — с [src: ...].
Снапшоты raw/ — текстовые (markdown), их sha256 связан с index.db → детект дрейфа источника и офлайн-провенанс.

## API contracts
Инструменты `aec-rag` (MCP): `wiki_init`, `wiki_snapshot`, `wiki_stale`, `wiki_edited`, `wiki_write_page`, `wiki_checkpoint`, `wiki_lint`, плюс поиск `rag_query`/`rag_overview`/`rag_check_quote`/`rag_status`. **Новый (2026-09-28):** `wiki_add_raw(kind, name, text | source_path | source_url)` — пишет сырьё вида (б), разбирает файл Docling без индексации, возвращает путь в raw/ для ссылок. Штатные файловые инструменты — только чтение страниц и запись вне `wiki/`. Интенты: build / update / lint / query / **add-raw**.
Отказы инструментов, которые являются ответом по существу (чужой абзац, путь вне папок вики, пустой запрос), возвращаются результатом `{ok: false, refused: "<причина>"}`, а не ошибкой (D-142).

## Edge cases
- Страница удалена человеком → lint помечает осиротевшие ссылки; агент не восстанавливает без команды.
- Источник отключён (detached) → страницы остаются с пометкой «источник отключён» (см. specs/workspace-sources).
- Очень большой источник (сотни страниц ТУ) → несколько страниц по разделам, не одна простыня.
- Смешанные языки при wiki_lang=auto → язык большинства источников.
- Сырой источник (б), чей оригинал изменился на диске → `wiki_stale` сравнивает отпечаток с файлом по `source_path` и помечает его `changed`; у вставленного текста и решения оригинала нет — они не устаревают.
- Имя страницы совпадает с существующим после приведения (регистр, пробел/`_`/`-`, `№`) → по правилу навыка агент дополняет существующую; запрета в инструменте нет (решение владельца 2026-09-28), вернёмся, если дубли останутся на Gemini.

## Feature-level acceptance & validation
- AC3 SPECIFICATION — сквозной ручной сценарий на эталонном проекте.
- Детерминированное (pytest/юниты): генератор структуры wiki/ и дефолтной SCHEMA; парсер frontmatter; lint-проверки (фикстуры: битая ссылка, сирота, дрейф sha, незакрытое противоречие).
- Smoke-эвал (≥5 сценариев): построение на мини-фикстуре 5–8 документов → рубрика: покрытие ключевых фактов, валидность провенанса (каждый [src:] существует и подтверждает факт), отсутствие выдумок; обновление с конфликтом → противоречие оформлено явно. Прогон обязателен при изменении промпта скилла или модели. **Отказ владельца 2026-09-28 для переписывания навыка на основе llm-wiki и перехода на Gemini: «пока не с чем сравнивать» (AGENTS §9, вариант B).** Вместо эвала — блок вики автоприёмки (22, 39) трижды на Gemini; что останется красным — замер и правка навыка (D-144, D-151).
- pytest на новое: `wiki_add_raw` (виды, отпечаток, разбор без индексации, отказ вне raw/user), отказ-ответ вместо ошибки, запрет записи вне папок вики, `wiki_stale` по сырью (б).
