## Смена курса 2026-08-05 — что изменилось и почему

Вышел Hermes 0.20.0 («The Herald Release», тег `v2026.8.3`, ~3650 коммитов). Разбор релиза
и интервью с владельцем дали пять решений, переписывающих курс:

| # | Решение | Что отменяет |
|---|---|---|
| **D1** | **Канал поставки ядра — git по SHA.** Автор прекратил публикацию в PyPI и Homebrew; поддерживаются только shell-установщик, Docker и Nix. Их установщик клонирует репозиторий и ставит editable — мы делаем то же самое, но в свой изолированный venv и по неизменяемому SHA. | Прежнее правило «ставим только из PyPI ради неизменяемости и подписи происхождения» — у него больше нет носителя |
| **D2** | **Берём их UI-стек целиком**: Tailwind v4, shadcn/Radix, nanostores, React Query, Codicon, их форма i18n. | Решение 10 фазы 1.6 («вариант C: Tailwind в наш рендерер не добавляется ни на одном батче») |
| **D3** | **Где функционал совпадает — ставим их компонент, наш выбрасываем.** Цель — получать их оптимизацию (60 fps, виртуализация, 14× стриминг markdown) и их тесты, а не воспроизводить поведение. | Правило «батчи 2–7: их код читаем как спецификацию, разметку пишем свою» |
| **D4** | **Правило объёма перевёрнуто: берём всё, кроме закрытого списка** (SPEC §Non-Goals «Исключения из Hermes»). | Прежние non-goals N7, N11, N12, N13, N15 и половина N14 |
| **D5** | **Внешний вид — их, как есть.** Наш дизайн-слой (`design/tokens.css`, макеты Claude Design) перестаёт быть обязательным артефактом и удаляется из репозитория. | «`design/` — источник истины для оболочки» |

Что **не** изменилось и является рамкой всего остального: приложение остаётся нашим
(SPEC C8) — мы не форкаем их десктоп и не живём плагином внутри их приложения. Основание:
только так сохраняется право не включать то, чего нет в списке исключений. Проверено, что
альтернативы этого не дают: плагин не может убрать ни одной их поверхности, а форк с
перестройкой UI делает вливание их же обновлений дороже, а не дешевле.

## Architecture

Слои (сверху вниз):

1. **AECPilot Desktop** (Electron + React + TypeScript) — единственный UI.
   - **Рендерер — на стеке донора** (D2): Tailwind v4 с их темой, примитивы shadcn/Radix,
     состояние в nanostores, серверное состояние в React Query, иконки Codicon, i18n в их
     форме с каталогами `en`/`ru`.
   - **Оболочка — их система размещения**: виджет-грид, плавающие панели, несколько окон,
     вкладки сессий (UR12). Наши активности встраиваются в неё как вклады.
   - **Наши собственные поверхности** (их у донора нет): проводник vault + источники,
     вьюеры PDF/DOCX/XLSX/CSV, вики, docgen, статус индексации.
2. **hermes-agent** (Python, пин по SHA) — агентное ядро **без модификаций**; приложение
   запускает его локальным процессом (`hermes serve`) и общается по tui_gateway JSON-RPC/WS
   **плюс REST того же процесса** (тот же хост, порт и токен). Персона и язык агента —
   SOUL.md профиля; проектные правила — AGENTS.md в vault.
3. **AEC-расширения** (наш переносимый слой):
   - MCP `aec-sources` — read-only доступ к источникам (контракт: `specs/workspace-sources.md`).
   - MCP `aec-rag` — Docling-парсинг + LightRAG-индекс per-project + запросы с цитатами
     (контракт: `specs/qa-over-sources.md`); сюда же файловый индексер (sha256, детект изменений).
   - Память — без собственного MCP: слой 1 — записка ядра (`MEMORY.md`/`USER.md`),
     слой 2 — их провайдер Mem0 локально (Phase 5).
   - Skills: `aec-qa` (эталон), `aec-wiki`, `aec-docgen`; `aec-id-check` — post-MVP.
4. **Хранилище** — files-first: vault + `.aecpilot/` (SQLite+FTS5 `index.db`, векторное
   хранилище LightRAG в `.aecpilot/lightrag/`, конфиг, логи). Серверов нет (C4).

   **Векторное хранилище — NanoVectorDB (решение владельца 2026-08-15).** LanceDB из
   PLAN отменён по факту: **в LightRAG 1.5.6 такого бэкенда не существует вовсе**. Из
   его семи бэкендов без сервера работают только три, и два из трёх нам не годятся:
   - **Faiss — исключён.** Пишет и читает индекс через `faiss.write_index/read_index`,
     принимающие `char*`; [faiss#3073](https://github.com/facebookresearch/faiss/issues/3073)
     («если путь содержит Unicode, read_index и write_index не работают») закрыт
     мейнтейнером **без исправления**. Индекс лежит внутри vault, а vault у наших
     пользователей называется `D:\проекты\ЖК …` — сломался бы там же, где Docling (R16).
     Плюс Faiss тоже держит индекс в памяти, то есть проблему и не решает.
   - **Milvus Lite — исключён.** По-настоящему дисковый и LightRAG сам подставляет путь к
     файлу, но `pymilvus` объявляет `milvus-lite>=2.4.0; sys_platform != "win32"` —
     официально поддерживаемый путь исключает Windows. Их `milvus_impl.py` вдобавок
     ставит `pymilvus` через `pipmaster` в рантайме (R15).
   - Qdrant, PostgreSQL, Mongo, OpenSearch требуют сервер — против C4.

   То есть внутри LightRAG выбора нет. Цена NanoVectorDB на нашем масштабе измерена и
   мала: 464 чанка × 3072 измерения ≈ 5,7 МБ. Настоящая слабость другая — пакет
   `nano-vectordb` не обновлялся с ноября 2024. **Точка пересмотра — нагрузочная проверка
   2.18**; запасной путь — не Faiss, а свой слой поиска на **sqlite-vec** (векторы рядом с
   чанками и FTS5 в том же `index.db`, на диске, единственный вариант, структурно
   защищённый от кириллических путей). Смена хранилища = полный повторный ingest, поэтому
   решается по числам.

   Отдельно и важно: в встраиваемой конфигурации LightRAG **в памяти не только векторы** —
   KV-хранилище (полные тексты, чанки, кэш ответов LLM) это JSON-файлы, читаемые целиком,
   а граф — NetworkX. Смена одного векторного бэкенда всей картины не меняет; нагрузочная
   проверка 2.18 обязана мерить всё три, а не только векторы.

   **Результат 2.18 (2026-08-15, `eval/load-report.md`): остаёмся на NanoVectorDB, но
   точка пересмотра переезжает.** Замер на 1622 чанках: диск 110 МБ, RAM 303 МБ, открытие
   11,3 с, запрос 1,03 с (из них почти всё — сеть за эмбеддингом вопроса). Векторы в
   памяти занимают 20 МБ из 303: узкое место — KV-джсоны, читаемые целиком и хранящие
   текст дважды (`full_docs` + `text_chunks`). То есть запасной путь «перейти на
   sqlite-vec» лечит не ту половину. Порог, за которым надо действовать, — около 5000
   чанков (≈1 ГБ RSS); первый шаг тогда — убрать `full_docs`, который мы не читаем ни в
   одном сценарии, второй — заменить KV-бэкенд на SQLite, и только третьим — векторный.

5. **Двухуровневая индексация** (SPECIFICATION UR24, решение владельца 2026-08-15).
   - **Уровень 1, всегда:** разбор → чанки → векторы + FTS5. Ноль вызовов LLM. Покрывает
     эталонный сценарий целиком.
   - **Уровень 2, по выбору:** граф знаний, **один на проект**, растёт по мере добавления
     документов; единица выбора — папка либо файл. По умолчанию пуст.
   - Механизм — штатный флаг LightRAG: `process_options="!"`
     (`PROCESS_OPTION_SKIP_KG`) пропускает извлечение сущностей, оставляя чанки в
     векторном хранилище. Проброс идёт через `apipeline_enqueue_documents` +
     `apipeline_process_enqueue_documents`; `ainsert()` этот параметр намеренно не
     принимает.
   - **Locator доносится через `chunk_id`.** Их сборщик чанков уважает явный `chunk_id`
     из хука чанкера, а `aquery_data()` возвращает его в результате — кладём туда наш ключ
     из `index.db` и джойним обратно за locator'ом. Произвольные метаданные не годятся:
     на выходе LightRAG пропускает только белый список из четырёх полей.
   - Модели: эмбеддинги `text-embedding-3-large`, извлечение сущностей
     `gpt-5.4-mini-2026-03-17` (датированный снимок — иначе baseline эвала поедет сам).

Границы модулей (monorepo):
```
apps/desktop/            # Electron + React (TypeScript)
  src/main/              # main-процесс: мост к шлюзу, файловые операции, safeStorage
  src/renderer/src/
    donor/               # ИХ код с указанием происхождения (см. §Слой донора)
    aec/                 # наши поверхности: проводник, источники, вьюеры, вики, docgen
    shared/              # адаптеры: мост шлюза, i18n, наши атомы
mcp/aec_sources/         # Python, MCP-сервер (stdio)
mcp/aec_rag/             # Python: индексер + Docling + LightRAG + MCP-сервер
skills/                  # skill-паки
runtime/                 # установка и запуск ядра, слепки контрактов, пробы
eval/                    # эвал-датасеты и раннер
specs/                   # поведенческие контракты
```

Ключевые решения:
- Working dir агента = vault; источники агенту доступны **только** через `aec-sources`
  (N3/AC6 обеспечиваются конструкцией инструментального слоя).
- Детект изменений — наш индексер (sha256 по интервалу), без LLM; действия — по подтверждению.
- **Рендерер не открывает WebSocket к шлюзу сам** (SPEC C9). Их клиент шлюза (`@/hermes`)
  адаптируется к нашему IPC-мосту — это единственный шов, который мы правим обязательно.
- Embedding-модель фиксируется в конфиге проекта; смена = полный re-ingest.

## Слой донора — как именно берётся их код

Это операционное ядро нового курса. Правила обязательны: от их соблюдения зависит, будет
ли следующее обновление Hermes стоить часы или недели.

**Точка съёмки.** Коммит донора фиксируется константой `DONOR_SHA` в `runtime/donor-env.mjs`
вместе с версией их десктопа. `DONOR_SHA = HERMES_SHA` (`3c27eb62…`, тег `v2026.8.3`):
десктоп донора лежит в том же репозитории, что и ядро, поэтому одна точка съёмки на оба —
перенесённые компоненты написаны ровно против того контракта шлюза, который отдаёт
установленное ядро. Версия их десктопа в этом коммите — `0.17.0` (их `package.json` отстал
от релизного поезда ядра; это запись факта, а не второй пин).

**Откуда читаем.** Из `runtime/.hermes-src/apps/desktop` — установка ядра уже держит там
detached-чекаут того же репозитория ровно на `DONOR_SHA`. Отдельный клон
`D:\my program\Hermes\hermes-agent` для этого не нужен и не трогается: он вне воркспейса
(правило AGENTS §2.6) и стоял на июльском коммите. `node runtime/donor-env.mjs` сверяет
дерево с пином и падает, если оно не то.

**Вендорная зона.** Их файлы живут в `renderer/src/donor/**`, повторяя их структуру путей.
Каждый файл начинается заголовком: исходный путь, `DONOR_SHA`, лицензия MIT, перечень
внесённых правок. Файл `LICENSE` донора сохраняется в поставке.

**Разрешены ровно четыре вида правок их файлов.** Всё остальное не правим — иначе повторный
перенос при их обновлении превращается в слияние:
1. их путь к бэкенду → наш. Обычный случай — клиент шлюза (`@/hermes`) →
   `shared/gateway-bridge`; тот же вид правки покрывает ОДИН вызов, который обязан
   уехать в другое место ради ограничения SPEC (их поле ключа провайдера писало ключ
   открытым текстом в конфиг ядра — правило R2 отправляет его в наш safeStorage);
2. импорт их i18n → наш каталог (ключи их, строки наши);
3. **таблицы регистрации** — что именно зарегистрировано: снять вклад, который SPEC
   исключает (§Non-Goals либо ограничение вроде R2, запрещающее сам механизм), или
   зарегистрировать наш (локаль, поверхность). Таблица, никогда не логика;
4. снятие импортов, которых у нас нет (их облако, их бренд, их телеметрия).

Фактический счёт: **24 правки в 22 файлах** на 750+ перенесённых (23 в фазе 1.8, одна
в фазе 2 — задача 2.13 регистрирует наш вклад цитаты в таблице разбора ссылок
`MarkdownLink`), каждая записана в заголовке своего файла и находится командой
`grep -rn "EDIT \[" donor/`.

**Слой состояния.** Их атомы (nanostores) переносятся вместе с экраном, который их читает.
Атомы, обращающиеся к шлюзу, перенаправляются на мост; атомы, хранящие настройки — на наш
`storage`. Свой параллельный стор для тех же данных не заводим: две модели состояния хуже
любой одной.

**Тесты.** Их тесты переносятся вместе с файлом, если не тянут их сторы. Наши тесты на
чистые функции (`*-pure.ts`) сохраняются как есть — они пиннят измеренные контракты ядра и
от стека не зависят.

**Обновление.** При переходе на новую версию донора файл переносится заново с нового SHA, а
не патчится. Дифф наших четырёх правок восстанавливается по заголовку файла.

**Синхронность с релизом донора — правило, введённое 2026-08-16.** Точка съёмки одна на всю
зону, поэтому «взять новый экран, оставив базу старой» невозможно физически, а не только по
правилу: измерено, что новые экраны 0.20.2 сидят на изменившихся модулях —
`app/hud/hud-shell.tsx` 8 импортов из 8, `right-rail/preview-reader.ts` 2 из 2,
`app/cron/cron-actions.ts` 2 из 2, `app/skills/mcp-tab.tsx` 14 из 27 (изменились
`store/session.ts` +350, `lib/chat-messages.ts` +326, `store/layout.ts` +342). Отсюда правило:

> **Не переносим поверхность, которая у донора переписана в версии, которую мы ещё не
> подняли.** Иначе платим за перенос дважды, а промежуточный результат ещё и не собирается.

Критерий «переписана» — измеримый, а не на глаз: churn файлов поверхности между нашим
`DONOR_SHA` и головой их релизного поезда. Ноль изменений = переносим сейчас, файл будет
побайтово тем же. Заметный churn = ждём подъёма пина. Инструмент замера — задача 3.0
(`runtime/donor-report.mjs`), он же выдаёт план повторного переноса при самом подъёме.

Обратное тоже верно и важнее: **решения принимаются по новому дереву сразу**, не дожидаясь
пина. Их код читается из клона по любому тегу — задача 3.1 генерирует реестр паритета с
параметром ref. Тогда состав работ фиксируется один раз, по финальному дереву, а не
переписывается после каждого релиза.

**Их интерфейс — ОДНО приложение, а не набор экранов** (решение владельца 2026-08-05, по
ходу фазы 1.8). `ChatView` монтируется их оболочкой и берёт от неё полтора десятка колбэков,
а сама оболочка живёт внутри их роутера. Поэтому перенос сделан одним заходом: смонтировано
их `app/index.tsx` со всем стеком провайдеров, а таблицы регистрации сужены до нашего объёма
(правка вида 3). Практическое следствие для любого будущего переноса: **экран не вынимается
из их оболочки поштучно** — берётся узел целиком, а лишнее снимается регистрацией.

**`@xterm/*` стоит в зависимостях, и это НЕ нарушение HX7.** Их `useAgentTerminal` — это
xterm без `node-pty` и без ввода: средство просмотра вывода агента, то есть ровно UR17.
Живая оболочка (`node-pty`, их `persistent.tsx`) не переносилась и не переносится. Проверять
при каждом обновлении донора: если ввод в их терминал появится, это станет нарушением.

**Язык интерфейса хранится у НАС** (`localStorage`), а не в `display.language` ядра: ядро
поддерживает en/zh/ja/de/es/fr/tr/uk и на `ru` молча падает в `en`, то есть его поле
физически не может выразить наш выбор. Умолчание — русский; английский остаётся фолбэком
для непереведённого ключа (это разные вещи). Русский каталог намеренно частичный — строки
писались под экраны, которые ещё не приехали; полный проход — задача 6.7. Строки наших
поверхностей живут в своём пространстве имён на их механизме `plugin-i18n`.

**Наши поверхности** (`renderer/src/aec/**`) пишутся в том же стеке, но их кодом не
являются: проводник, источники, вьюеры, вики, docgen, индексация. У донора аналогов нет.

**Мастер первого запуска — список, а не шесть своих экранов** (задача 3.20). Два его шага
у донора уже есть: `donor/components/onboarding` вместе с вендоренным
`donor/store/onboarding.ts` поднимается сам, когда `setup.runtime_check` отвечает «нечем
отвечать», и ведёт провайдер → ключ → модель (ключ уходит в наш safeStorage — EDIT [1],
правило R2). Свой второй такой экран был бы не «нашей поверхностью», а копией их. Поэтому
мастер показывает шесть шагов, но своих действий у него четыре (проект, папка с
документами, индексация, первый вопрос), а на ключ и модель он открывает их же экран.
Общее правило, к которому это сводится: **у донора нет аналога — пишем свой; аналог есть —
ведём на него, а не повторяем.** Состояние шагов выводится из фактов ядра, а не хранится:
подключённый в панели «Источники» каталог закрывает шаг сам собой. Хранится только то, у

**Почему пин по SHA, а не по тегу.** Релиз в PyPI был неизменяем и подписан происхождением;
git-тег автор может передвинуть. SHA фиксирует содержимое криптографически — это не слабее
хэша колеса. При установке проверяем, что тег релиза указывает на этот SHA.

**Нужен ли ядру Node 26** (ответ задачи 1.7.3: **нет**). Строка «Hermes requires Node >=26»
из релиз-нот живёт в `scripts/install.sh` как текст предупреждения; реальные пороги там же
и в их манифесте другие: `engines.node = ">=22.22.0"`, функция `node_satisfies_build()`
пропускает всё от 22.22, а сам установщик кладёт себе `NODE_VERSION="22"`. Node ядру нужен
только для двух поверхностей, которых у нас нет (`hermes_cli/dep_ensure.py`: «required for
browser tools and TUI») и для сборки их веб-дашборда — мы запускаем `hermes serve` с
`--skip-build`. Проверено на живом ядре: `serve.mjs smoke` на Node 22.22.3 (наша машина)
проходит, шлюз отдаёт `gateway.ready`. **Пин Node не поднимаем.**

Отдельная ловушка на будущее: их `engines.npm = "<11.10.0 || >=11.17.0"` при
`engine-strict=true` исключает штатный npm Node 24 (11.16.0). Нас это не касается, пока мы
не запускаем `npm ci` внутри их дерева (мы пользуемся pnpm в своём приложении), но если
такой шаг когда-нибудь появится — он упрётся именно сюда, а не в версию Node.

**Почему установка editable, а не из git-URL** (измерено задачей 1.7.2). Их `setup.py`
отказывается собирать wheel или sdist в принципе — любой `pip install <git-url>` падает с
`RuntimeError: Building wheels or sdists for hermes-agent is not supported`, и единственный
предложенный путь — `uv pip install -e .`. Поэтому `runtime/setup.mjs` делает shallow-fetch
ровно нужного коммита в `runtime/.hermes-src` (detached, gitignored, не рабочая копия) и
ставит оттуда editable. Следствия: каталог исходников — часть установки и не удаляется;
`site-packages` не содержит их модулей, поэтому всё, что читает ядро с диска (снимальщик
контракта), адресует `HERMES_SRC_DIR`, а не `site-packages`.

## Сверка выдержек (SPEC UR26) — чей код и где стоит

Матчер — **их**: `quote_in_evidence` из скила `grounded-citations`, который ставится вместе
с ядром (`$HERMES_HOME/skills/research/grounded-citations/scripts/sources.py`). Не копируем
и не переписываем: функция нечувствительна к регистру, переносам и markdown-разметке, и это
ровно та тонкость, ради которой чужой отлаженный код и берут. Наше — только два места, где
он вызывается, и то, что делается с ответом «не совпало».

| Рубеж | Где | Что делает |
|---|---|---|
| Инструмент агента | `aec_rag.server.rag_check_quote` | сверяет выдержку с текстом того чанка, на который ссылается ответ; агент зовёт его ДО того, как выдержка попадёт в ответ, и может взять другую фразу |
| Проверка при показе | `aec-rag check-quotes` → main → рендерер | сверяет заново всё, что дошло до экрана; непрошедшая выдержка помечается |

Два рубежа, а не один, потому что это измерено (3.22): инструмент модель пропускает именно
там, где он бы её не пропустил, а проверка при показе ничего не сообщает агенту и не даёт
ему исправиться. Порознь каждый оставляет дыру ровно в том случае, ради которого заводился.

**Текст выдержки берётся из индекса, а не из ответа.** Доказательством не может быть то, что
прислала сама модель, — иначе проверка сводится к сверке текста с самим собой.

**Скила нет на машине — проверка не «проходит», а честно отвечает «недоступна».** Молчаливое
«ок» при отсутствующем матчере — худший исход из возможных: гарантия исчезает, а вид
гарантии остаётся.

## Data / API / integrations

- **tui_gateway (JSON-RPC/WS)** — основной контракт. В 0.19.1 шлюз разрезан: `server.py` +
  `methods_{complete,config,prompt,session,tools}.py`. Ссылки вида `server.py:NNNN` в наших
  документах и комментариях после этого указывают в никуда — адресуем по **модулю и имени
  метода**, а не по строке.
- **REST того же процесса** — `hermes serve` = алиас `dashboard`, поднимает FastAPI на том же
  хосте/порту/токене (`X-Hermes-Session-Token`). Часть маршрутов вынесена в
  `hermes_cli/web_routers/{cron,git,mcp,profiles,sessions,skills,tools}.py`, остальное — в
  монолите `web_server.py`. Правило: что есть в RPC — идёт по RPC; REST только там, где RPC
  не покрывает (история сохранённых сессий, граф обучения).

  **Профили и MCP CRUD выехали из этого списка в 0.20.2** (замер 2026-08-16): появились
  `methods_profiles.py` (`profiles.list/create/describe/configure/get_asset/set_asset`) и
  восемь методов `mcp.*` (`catalog`, `servers.add/list/remove/test/set_api_key`,
  `servers.oauth.start/poll`). Их мотив — их же плагины ходят только в ws-дверь; наш выигрыш
  в том, что оба экрана перестают быть особым случаем. **Удаления профиля в RPC нет**,
  поэтому обход D-14 (`explainProfileDeleteFailure` в нашем main) остаётся на месте.
- **Ядро умеет спрашивать клиента** (новое в 0.20.2). Раньше поток событий был односторонним;
  теперь три инструмента агента блокируются на ответе рендерера — `mcp.setup.request` →
  `mcp.setup.respond` (карточка согласия на установку MCP-сервера, таймаут 600 с),
  `preview.read.request` → `preview.read.respond` (текст активной вкладки предпросмотра, 45 с),
  `window.read.request` → `window.read.respond` (окно ОС под нашим окном, 30 с). Механика та
  же, что у давно известного `clarify.request`. Третий у нас **не реализуется** — SPEC HX12;
  на запрос отвечаем отказом, а не молчанием, иначе агент ждёт таймаут.
- **Второй сокет — потоковая речь (3.7a, 2026-08-17).** `/api/audio/speak-stream` держит
  **main**, как и основной. Причина не в симметрии: в нашем режиме (loopback, без
  OAuth-гейта) ядро авторизует WebSocket параметром `?token=<_SESSION_TOKEN>` — тем же
  токеном, что открывает любой метод RPC и любой REST-маршрут. Отдельного ключа «только на
  речь» у ядра нет, значит «пустить рендерер к одному безобидному сокету» не существует как
  вариант; C9 здесь не строгость, а единственная форма. Рендерер получает кадры через IPC и
  шлёт в канал только три их формы (`{text}` / `{done}` / `{stop}`) — разбор в
  `main/speech-stream-pure.ts`, чтобы канал не стал обобщённым сокетом.
  Измеренные особенности, которые стоит помнить при подъёме пина (проба
  `runtime/speech-stream-probe.mjs`): отказ по токену приходит как HTTP 403 на рукопожатии
  (их `close(4401)` до провода не доходит); встроенный WebSocket-клиент Node теряет кадр,
  за которым сервер сразу закрывает соединение, — поэтому PCM без предшествующего
  управляющего кадра main считает потерей `start` и отвечает ошибкой, а не тишиной.
- **Голос по умолчанию — `ru-RU-SvetlanaNeural`** (решение владельца 2026-08-17). Голос ядра
  `en-US-AriaNeural` на кириллице даёт ПУСТОЙ поток и ответ 400, то есть на чистой установке
  речь молчит; русский голос читает оба языка, английский — только свой. Дописывается в
  `tts.voice` конфига при старте, если не задан, и после этого не трогается никогда
  (`main/speech-voice-pure.ts`).
- **Разрешения окна заданы явно** (3.7a): микрофон и запись картинки в буфер — да, всё
  остальное — отказ. До этого обработчика не было вовсе, а Electron без него выдаёт странице
  любое разрешение, о котором та попросит.
- **OAuth-вход провайдеров (3.19)** идёт через системный браузер: `openExternal` шима отдаёт
  URL в main, где действует `decideExternalLink` (http/https/mailto и ничего больше), а весь
  поток — старт, опрос, отзыв — ведёт ядро своим REST. Токен при этом остаётся у ядра
  (SPEC C10): в `auth.json` профиля открытым текстом, а у провайдеров `external` — в файле
  чужого CLI. Отключение таких провайдеров требует их же командной строки, которой у нас нет
  (HX7), поэтому команда показывается, а не выполняется.
- **Ключи провайдеров — только в нашем safeStorage** и в spawn-env процесса ядра. Их
  `model.save_key` и `POST /api/env/reveal` не используются никогда: оба работают с открытым
  текстом. В 0.20.0 появился `${env:VAR}` SecretRef в `config.yaml` и MCP — это разрешённый
  способ сослаться на переменную окружения вместо значения.
- **Approvals (UR11)** — три значения `approvals.mode` в `config.yaml` профиля; ядро
  перечитывает конфиг на каждой команде, смена применяется живо.
- **MCP-контракты наших серверов** — в `specs/` (`sources_*`, `rag_*`).

**Конвейер слежения за ядром** (обязательная часть каждого обновления):
1. `runtime/contract-snapshot.mjs` — снимает слепок установленного ядра: набор `@method`
   (теперь по пяти `methods_*.py`), эмитируемые события, REST-маршруты (`web_routers/` +
   монолит), дефолты `hermes_cli/config.py`, `Requires-Dist`.
2. `runtime/contract-diff.mjs` — **новый**: сравнивает два слепка и выдаёт «сломалось /
   появилось / **молча сменило умолчание**». Третья категория — главная: урок 0.18→0.19
   (`model.options` перестал форсировать `include_unconfigured`, ответ ужался с 41 провайдера
   до 3 без единой ошибки).
3. `runtime/parity-registry.mjs` — **новый**: генерирует реестр паритета (AC9) из ядра и
   из дерева донора, сверяет со списком исключений SPEC и с нашими вкладами.

## Удалённый режим (UR20) — что работает, что отключено и почему

Решения владельца 2026-08-17, интервью по каждой поверхности (задача 3.13a). Реализация —
3.13b в фазе 3B; здесь записано, что мы обещаем.

Рамка. Приложение состоит из двух половин: одна разговаривает с ядром по сети (чат, сессии,
чекпойнты, настройки) и в удалённом режиме работает без правок, вторая трогает **файлы** в
нашем main-процессе на локальном диске. Именно вторая половина и разбиралась. Ядро отдаёт
файлы по сети само — `/api/fs/list`, `/api/fs/read-text`, `/api/fs/read-data-url` (замерено
2026-08-17), — поэтому «работает удалённо» это реальный вариант, а не пожелание.

| Поверхность | Решение | Основание |
|---|---|---|
| Проводник vault | **Работает удалённо** через `/api/fs/*` | Видеть, что правит агент, — базовая вещь; локальное дерево показывало бы ЧУЖИЕ файлы, выглядя исправным |
| Источники и сканер/индекс | **Серверная установка** | Наши расширения — MCP-серверы, которых запускает само ядро, то есть они живут там же, где оно. Индекс строится рядом с документами, по локальным для той машины путям; сети в горячем пути нет. Индексация по REST отвергнута: часы и трафик на тысячах файлов |
| Вьюеры документов и клик по цитате | **Работают удалённо** через `read-data-url` с лимитом размера | Цитата, которая не открывается, ломает главный сценарий продукта. «Показать в проводнике» выключается — локального пути нет |
| Чекпойнты и откат | **Работают удалённо** | Уже идут по RPC и касаются файлов на машине ядра. Переписать надо только нашу диагностику «почему список пуст» (`checkpoint-scope-pure`), которая сейчас смотрит на локальный путь |
| Артефакты | **Работают урезанно** | Просмотр и скачивание через файловый API ядра; «показать в проводнике» выключено и объясняет почему |
| Вложения (скрепка) | **Файл закачивается на машину ядра** | Сегодня мы шлём ПУТЬ, а читает его ядро у себя — удалённо это другой файл или ничего, причём выглядит как успех. Требует мультипарт-загрузки, которой наш мост сейчас не имеет (шим отказывает на `api({upload})`) |

**Следствие, выходящее за рамки 3.13b:** «серверная установка» — это второй профиль поставки
(сервер: ядро + наши расширения + индекс рядом с документами; клиент: только приложение), то
есть изменение архитектуры и упаковки. Идея владельца, принята как курс; оформляется
отдельной задачей фазы 6 через planning gate, а не внутри удалённого режима.

## Профили поставки «сервер / клиент» (SPEC UR25) — как это устроено

Решения владельца 2026-08-17 (интервью): транспорт — SSH-туннель, серверная ОС — Windows,
пользователь один, установка — тем же инсталлятором с выбором режима. Реализация — фаза 6,
задачи 6.12–6.17; до их утверждения ничего из этого не пишется.

**Почему это вообще возможно и почему это дёшево.** Наши расширения — MCP-серверы, которых
запускает САМО ядро (`mcp_servers:` в его `config.yaml`). Значит там, где стоит ядро, они и
работают, и все пути для них локальные. Никакого «индексировать по сети» не возникает: это
свойство архитектуры, а не функция, которую надо писать.

**Что где живёт.**

| | Сервер (машина с документами) | Клиент (ноутбук) |
|---|---|---|
| Ядро `hermes serve` | да, только на 127.0.0.1, автостарт при входе в систему | нет |
| Наши MCP-расширения + Docling/LightRAG | да | нет |
| vault, документы, индекс `.aecpilot/` | да | нет |
| Приложение (Electron) | опционально (режим «всё на этой машине») | да |
| Ключи провайдеров | в safeStorage серверной машины (их читает ядро) | токен шлюза в safeStorage клиента |

**Что придётся изменить в нашем коде — это и есть объём задач:**

1. `runtime/setup.mjs` сегодня ставит всё и всегда. Нужен режим: полный / только сервер /
   только клиент.
2. `runtime/register-aec-*.mjs` прописывают в конфиг ядра АБСОЛЮТНЫЕ пути нашей машины
   (`<repo>/.venv/Scripts/aec-rag.exe`, `--project <путь к project.json>`). В серверном
   профиле это верно по построению — регистрация выполняется на той же машине при установке.
   Открытый вопрос не в этом, а в **смене проекта**: сегодня приложение переписывает конфиг
   ядра на диске, а клиент этого сделать не может. Путь — их же RPC `mcp.servers.add/remove`
   (появились в 0.20.2, замерены), то есть переcборка записи расширения через ядро.
3. `main/index.ts` в клиентском режиме не запускает `hermes serve`, а подключается к концу
   туннеля. Смыкается с 3.12 (реестр подключений, токен в safeStorage) — 6.12 без 3.12 не
   имеет смысла.
4. Файловые поверхности — по решениям 3.13a (см. раздел выше), реализация 3.13b.
5. **Сканирование по расписанию сегодня крутится в нашем main-процессе.** В серверном профиле
   это неверно: ноутбук закрыт — пересканирования нет, хотя документы на сервере меняются.
   Значит планировщик переезжает на серверную машину (задача ОС при входе в систему либо
   периодический вызов инструмента), а панель клиента показывает его состояние, а не владеет им.
6. Деинсталлятор (6.11) должен знать про два профиля: на сервере удаляется ядро, расширения и
   индексы, но НЕ vault и не документы; на клиенте — только приложение и его настройки.

**Токен шлюза.** Мятится на серверной машине при старте (`serve.mjs`), клиент получает его
один раз руками через экран подключений (3.12) и хранит в safeStorage. Автоматическую выдачу
токена по SSH в объём не берём: это ещё один канал доверия, а выигрыш — одно копирование при
настройке.

**Что оставляем открытым для многопользовательского сервера (указание владельца 2026-08-17).**
В объём это не входит (SPEC N16), но закрывать путь нельзя, а закрыть его легко — тремя
разными способами, поэтому они названы поимённо:

1. **Единица разделения уже существует — профиль ядра.** У профиля свои ключи, сессии, память
   и свой набор MCP-серверов; проект, документы и индекс при этом общие, ради чего сервер и
   заводится. То есть многопользовательский режим — это не новая архитектура, а несколько
   профилей на одном сервере плюс аутентификация. Значит **имя профиля передаётся явно** в
   регистрации расширений (6.14), в подключении (6.16) и в создании сессий — там, где сегодня
   «он всё равно один», завтра будет чужой.
2. **Личность подключающегося не выводится из токена шлюза.** Сегодня токен один на процесс, и
   он доказывает только то, что клиенту его дали; кто именно пришёл — знает SSH. Поэтому ни
   одна наша проверка прав не должна опираться на «у него есть токен, значит это владелец». Для
   нескольких людей ответ уже есть у ядра — его гейт аутентификации (`auth_required` +
   одноразовые тикеты), и переход туда не должен требовать переписывания наших экранов.
3. **Пользовательское не пишется в общемашинное.** Настройки интерфейса, недавние проекты и
   ключи клиента живут на клиенте; на сервере общими остаются вещи про машину (автостарт,
   расписание сканирования), а не про человека.

Чего это стоит сегодня: практически ничего — параметр `profile` мы и так передаём в
`session.create`. Чего это стоило бы потом: переписывания регистрации расширений и экрана
подключения, то есть двух из шести задач блока.

**Проверка (AC11).** Сквозной прогон на двух машинах: сервер ставится на машину с
документами, клиент на вторую, проект открывается с клиента, вопрос с цитатой получает ответ,
клик по цитате открывает документ. Доказательство разделения — `.aecpilot/` есть на сервере и
отсутствует на клиенте.

**Риск, принятый явно (SPEC R17).** Кто получил SSH-доступ к серверной машине, получает
агента с его правами на файлы проекта. Безопасность продукта здесь сводится к безопасности
SSH-доступа; шлюз при этом остаётся на 127.0.0.1 (C11), а многопользовательский режим
исключён (N16).

## Validation strategy

- Детерминированное: `uv run pytest` (MCP-серверы, индексер, RO-негативные), `pnpm test`
  (vitest: `*.test.tsx` → jsdom + @testing-library, `*.test.ts` → node), `pnpm e2e`
  (Playwright smoke).
- Перенесённые тесты донора идут в общий прогон и считаются нашими.
- Эвалы (`ai-eval-design`): `eval/qa_dataset.yaml` (≥30, baseline → порог O1/AC2); smoke-эвалы
  `aec-docgen` и памяти; обязательный прогон при изменении skill-промптов, модели,
  embedding-модели, RAG-параметров — иначе оформленный waiver.
- **Чужой скил перед принятием меряется плечами на эталонном наборе** — правила каждого
  плеча лежат отдельным файлом в `eval/variants/`, чтобы разница была ровно одна и была
  видна. Первый такой замер — `grounded-citations` (задача 3.22). Он и дал правило, по
  которому теперь берутся чужие скилы: **брать вместе с его механикой, а не пересказывать
  правилами.** Перенесённое ТРЕБОВАНИЕ без его же ПРОВЕРКИ дало 59 % дословных выдержек из
  обещанных 100 %; их скрипт в цепочке — 7 из 7. Плечо без механики — не «облегчённый
  вариант», а видимость гарантии, и меряется оно затем, чтобы это было числом, а не мнением.
- Безопасность: `security-review` в конце Phase 2 и Phase 6; отдельно — проверка UR19
  (внешние каналы выключены по умолчанию, AC10) и R11 (каталог плагинов ядра).
- Контракт ядра: `contract-diff` без непрочитанных расхождений + `serve.mjs smoke`,
  `aec-sources-check`, `checkpoint-probe`, `skills-probe`, `hermes-event-diff`.

## Risks & tradeoffs

- **Канал поставки ядра (R1).** Установка из исходников по SHA вместо подписанного колеса.
  Цена: сборка требует git и сети, подпись происхождения PyPI утрачена. Компенсация: SHA
  неизменяем, сверяется с тегом релиза; при необходимости офлайн-воспроизводимости фаза 5
  собирает колесо один раз и фиксирует его хэш.
- **Стек донора без гарантий (R12).** Их SDK «always-current», версионирования нет; Tailwind
  и shadcn дрейфуют. Принято ради того, чтобы их код переносился копированием. Контроль —
  вендорная зона с указанием происхождения, четыре разрешённых правки, повторный перенос
  вместо патчей.
  **Дополнено 2026-08-16: патч-релизы выходят без нот.** 0.20.1 и 0.20.2 (656 и 397 PR)
  описаны одной строкой «свёртка окна», разбор обещан к 0.21.0. Значит читать ноты как
  источник истины нельзя в принципе — только дерево. Отсюда обязанность задачи 3.0: замер
  churn становится штатной процедурой перед каждым подъёмом пина, а не разовым разбором.
  Второе следствие того же замера — темп: за 13 дней у донора изменились 247 из 721
  перенесённого нами файла, то есть треть зоны стареет за две недели. Это цена курса D3,
  и она подтверждает правило «повторный перенос, а не патч» цифрой.
- **Замена ~16 000 строк нашего рендерера.** Переписывается разметка и CSS
  (10 626 `.tsx` + 5 360 `.css`); выживают 7 124 строки чистой логики, 6 231 строка тестов
  на неё, 13 389 строк main/preload/project/shared и весь Python. Работа идёт под сеткой:
  наши компонентные тесты писались с утверждениями по отрисованному дереву, а не по классам.
- **Внешние каналы (R10).** Проектные данные получают путь наружу, а агент — путь внутрь.
  Принято решением владельца; удерживается тем, что каналы выключены по умолчанию, включение
  явное и показывает уходящие данные (AC10).
- **Каталог плагинов ядра (R11).** Существует независимо от нашего решения его не
  использовать; агент умеет писать файлы. Свой загрузчик не заводим (HX5), каталог держим
  вне рабочей папки агента.
- **Удалённый режим (R13).** Ломает все файловые поверхности; каждая обязана либо работать
  удалённо, либо явно отключаться с объяснением.
- **Docling требует C++-компилятора, если не запретить `torch.compile` (R14).** Замер
  2026-08-07: по умолчанию Docling компилирует модель разметки через `torch.compile`, а тот
  на Windows зовёт MSVC — без Visual Studio любая конвертация падает
  (`InductorError: InvalidCxxCompiler: Compiler: cl is not found`). Установка Visual Studio
  не может быть условием открытия PDF у инженера-непрограммиста, поэтому
  `aec_rag.parse.build_converter` ставит их же штатный флаг
  `settings.inference.compile_torch_models = False`. Цена — инференс в eager-режиме;
  измеренная скорость на этой машине: ~12 с загрузка модели разметки в процесс + ~6,5 с на
  документ. Проверять при каждом обновлении Docling и torch.
- **Качество OCR по русским сканам (R4) — закрыт замером 2026-08-14.** Дефолт:
  `rapidocr` на бэкенде `onnxruntime` с моделью **`eslav`** (PP-OCRv5,
  восточнославянская). Сходство с текстовым слоем 0,71 при 5,5 с на страницу скана.
  `easyocr` точнее косметически (0,77), но **в 12 раз медленнее** (66 с/стр.) — на
  проекте с сотнями сканов это часы вместо минут. Модель `cyrillic` (PP-OCRv3), которая
  доступна без доустановок, негодна: 0,23 и латинско-кириллическая каша в выдаче.
  Цена — зависимость `onnxruntime` (~15 МБ); через экстру docling её брать нельзя, на
  Windows она резолвится в `onnxruntime-gpu` с CUDA. Методика, числа и оговорки —
  `eval/ocr-report.md`. Главная оговорка: настоящий скан в образцах ОДИН, поэтому
  «слепой набор» мерил в основном скорость; при появлении плохой бумаги замер повторить
  (`uv run python eval/ocr_bench.py`).
- **LightRAG ставит пакеты в рантайме (R15).** Он тянет `pipmaster` и подгружает
  недостающие привязки (например `openai`) `pip install`-ом на лету. Для нас это дыра и в
  воспроизводимости, и в поставке: окружение меняется само, мимо lock-файла. Митигация —
  объявлять такие пакеты самим (`openai` уже в зависимостях `aec-rag`); при обновлении
  LightRAG проверять, не появился ли новый ленивый импорт.
- **Docling не открывает пути с не-ASCII символами (R16).** Замер 2026-08-14 на настоящих
  проектных документах: их PDF-бэкенд `docling-parse` падает («could not load document»)
  на любом пути с кириллицей — и в имени файла, и в имени любого каталога выше. У наших
  пользователей документы называются `02-ПЗ-Нагатинская 297-1.pdf` и лежат в
  `D:\проекты\ЖК …`, то есть по пути не проиндексировалась бы бОльшая часть проекта.
  Митигация: `aec_rag.parse._convert` отдаёт Docling **поток**, а не путь — качество
  `docling-parse` сохраняется, обходной бэкенд не нужен. Цена — файл читается в память
  целиком (ограничено потолком индексера в 200 МиБ). Закреплено тестом с кириллицей и в
  имени каталога, и в имени файла.
- **Двойной рантайм (Node + Python)** → сложнее упаковка (R5); принято ради ядра и
  python-экосистемы RAG.
- **Embedded-хранилища** → пределы масштаба (R3); принято ради «без серверов» (C4).
  Запасной путь — sqlite-vec своим слоем, НЕ Faiss (см. §Architecture: кириллические пути).
- **Стоимость графа (R6)** → снята из умолчания: граф строится только по выбранным
  документам (UR24). Остаточная цена — интерфейс обязан показывать, что в графе, и
  спрашивать перед добавлением новых файлов из отмеченной папки. Фактический расход
  токенов снимается замером на ОДНОМ документе до любого полного прогона.
- **Облачные эмбеддинги в MVP** → быстрый старт; цена — полный re-ingest при переходе в
  закрытый контур (C5).
- **3 skills в MVP** → риск распыления снижен выводом `aec-id-check` (N9); эталонный только
  `aec-qa`.

Каждая фаза заканчивается: тесты зелёные → self-review → коммит → сверка планов.
